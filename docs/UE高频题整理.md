## 一、Gameplay 框架与反射

### 1. GameMode、GameState、PlayerController、PlayerState 与 Pawn 分别负责什么？

**答案：**

| 类 | 存在位置 | 职责 |
| --- | --- | --- |
| GameMode | 仅服务器 | 匹配规则：能否加入、出生点与职业选择、胜负与阶段流转、作弊与调试开关 |
| GameState | 服务器并复制 | 全局共享状态：比分、回合阶段、倒计时，供所有客户端读 |
| PlayerController | 服务器与所属客户端 | 玩家意志：输入处理、相机、与 UI/Pawn 的绑定；RPC 常经它中转 |
| PlayerState | 服务器并复制 | 单个玩家的公开数据：名字、分数、队伍、ping |
| Pawn／Character | 服务器与相关客户端 | 被控制的实体；Character 额外带胶囊与 CharacterMovementComponent |

记忆主线：规则在 GameMode（服务器），结果状态在 GameState（人人可见），个人输入在 PlayerController（只属于本人），个人公开数据在 PlayerState，身体是 Pawn。 PIE 与单机模式下 GameMode 在客户端也存在一份，此时按 NetMode 判断，不要把"GameMode 客户端一定没有"说死。

### 2. UPROPERTY 和 UFUNCTION 有什么区别？

**答案：**

两者都是给 UnrealHeaderTool（UHT）看的标记宏，UHT 解析后生成 `.generated.h` 与注册代码，把成员登记进 UClass 的反射数据。

- `UPROPERTY` 修饰属性，使其参与：GC 引用追踪（对象指针成员靠它被 GC 识别，否则会被当作无引用）、序列化、网络复制（配合 `Replicated`／`ReplicatedUsing`）、编辑器细节面板（`EditAnywhere` 等）。
- `UFUNCTION` 修饰函数，使其可被反射调用：`BlueprintCallable`／`BlueprintPure` 供蓝图调用，`BlueprintImplementableEvent`／`BlueprintNativeEvent` 允许蓝图重写，`Server`／`Client`／`NetMulticast` 声明 RPC，`Exec` 挂控制台命令。

一句话：UPROPERTY 让属性被引擎系统（GC／序列化／复制／编辑器）感知，UFUNCTION 让函数获得蓝图、RPC 与反射调用能力。普通 C++ 成员不加宏就不进入这套系统。

### 3. UE 的反射系统是什么？如何支撑 C++ 与蓝图交互？

**答案：**

UE 自建了一套反射：编译期 UHT 扫描 `UCLASS`／`USTRUCT`／`UPROPERTY`／`UFUNCTION` 标记，生成注册代码；运行时 UClass／UScriptStruct 保存属性链（FProperty）与函数（UFunction）描述，每个 UClass 还有 CDO（类默认对象）承载默认值。

蓝图与 C++ 的互转依赖这套数据：

- C++ 暴露给蓝图：UHT 为 `BlueprintCallable` 函数与 `UPROPERTY` 生成 thunk 与蓝图字节码可见的函数描述，蓝图 VM 调用时走 `UFunction::Invoke` 进入原生代码。
- 蓝图被 C++ 调用：`BlueprintImplementableEvent`／`BlueprintNativeEvent` 在 C++ 侧只有 UFunction 声明，若蓝图重写过则由蓝图 VM 执行，否则回落到 C++ 默认实现。
- 动态委托、序列化、网络复制、编辑器面板、GC 引用扫描全部读取同一份反射数据。

与 C#／Java 的语言级反射不同，C++ 本身没有运行时类型信息支撑这套能力，所以 UE 用"代码生成＋运行时注册"模拟。回答时点出 UHT 与 CDO 通常是与纯八股拉开差距的点。

### 4. UE 的 GC 是什么机制？需要注意什么？

**答案：**

UE 对 UObject 采用标记—清除：从 RootSet 出发，沿反射数据（UPROPERTY 里登记的对象指针）遍历引用图，可达则保留，不可达则在清理阶段销毁。非分代、默认非压缩；UE5 可开启增量 GC 把可达性分析拆帧，降低单次卡顿。

工程上高频注意点：

- UObject 指针成员必须加 `UPROPERTY` 才被 GC 追踪；非 UObject 类持有 UObject 引用要走 `FGCObject::AddReferencedObjects`，否则对象可能被回收成悬垂。
- 引用成环不会泄漏（标记清除不怕环），但无意的强引用会让对象"该死不死"，内存驻留要靠 `TWeakObjectPtr` 或梳理持有链解决。
- 大容器（如 `TMap<int32, UObject*>` 加 UPROPERTY）会把所有元素纳入扫描，对象数量直接放大 GC 耗时；控制 UObject 数量、使用 Cluster 合并销毁是常见优化。
- 非 UObject 的 C++ 对象不走这套 GC，用 UE 智能指针或标准智能指针管理（见第 5、6 题）。

与 C# 的对比：C# 是分代压缩式 GC 且托管一切对象；UE 的 GC 只管 UObject、不移动对象、靠开发者声明引用。参考：[UE 对象处理](https://docs.unrealengine.com/5.0/en-US/unreal-object-handling/)。

## 二、内存与智能指针

### 5. TSharedPtr、TSharedRef、TWeakPtr 如何选择？

**答案：**

UE 智能指针用于非 UObject 的 C++ 对象（Slate 控件、任务对象等）：

| 类型 | 语义 | 要点 |
| --- | --- | --- |
| `TSharedPtr<T>` | 强引用，可为空 | 引用计数归零即销毁 |
| `TSharedRef<T>` | 强引用，保证非空 | 可隐式转 `TSharedPtr`，接口参数常用它表达"必须存在" |
| `TWeakPtr<T>` | 弱引用 | 不增加强计数，`Pin()` 临时升级为 `TSharedRef` 使用 |

引用计数默认非原子，跨线程共享要用 `TSharedPtr<T, ESPMode::ThreadSafe>`，且只保证计数线程安全，对象本身的并发访问仍需自行同步。循环引用同样要靠 weak 打破，原理与 `std::shared_ptr` 一致，控制块（强／弱计数）机制见 [C++ 专题](C++高频题整理.md)第 85 题。ToSharedRef／Pin 前先 `IsValid`，避免悬垂。

### 6. UObject 为什么不用 TSharedPtr 管理？

**答案：**

UObject 的生命周期已由引擎 GC 统一管理，再套一层引用计数会形成双重所有权：GC 认为可达的对象被计数归零提前删掉，或引用计数还在而 GC 已将其清除，两套机制互相打架。正确姿势是：

- 类成员持有：`UPROPERTY`＋裸指针或 `TObjectPtr<T>`，交给 GC 追踪。
- 非成员短期持有或观察：`TWeakObjectPtr<T>`，用时 `Get()`／`IsValid()` 检查。
- 永不失效的全局对象：`GEngine` 等 RootSet 对象可直接裸指针。

`TObjectPtr<T>` 是模板化的 UObject 指针，UPROPERTY 场景下提供编辑器访问检查等能力，打包构建中等价于裸指针；非 UPROPERTY 场景没有收益。底层库代码仍常见裸指针，遵守"UPROPERTY 或 WeakObjectPtr 二选一"的团队规范即可。

## 三、网络与多人

### 7. Listen Server 与 Dedicated Server 有什么区别？

**答案：**

- Listen Server（监听服务器）：第一个玩家同时当服务器，游戏逻辑与某个客户端同进程。优点是零额外部署、主机延迟最低；缺点是主机有作弊与掉线风险，主机视角不参与公平的网络裁剪，适合合作与小型对战。
- Dedicated Server（专用服务器）：无本地玩家的独立服务器进程（无渲染的 `-server` 构建）。公平、稳定、可运维，是竞技对战与上线手游的标准方案；代价是服务器集群的部署与运维成本。

代码层通过 `GetNetMode()`（NM_Standalone／NM_ListenServer／NM_DedicatedServer／NM_Client）区分环境；GameMode 只在服务器端存在，两个模式一致。面试常把"你项目怎么联机的"接到这题，直接点明自己项目用的模式与理由即可。

### 8. 属性复制（变量复制）与 RPC 有什么区别？分别适合什么场景？

**答案：**

| 维度 | 属性复制 | RPC |
| --- | --- | --- |
| 语义 | 持续状态最终一致 | 一次性事件／函数调用 |
| 方向 | 服务器 → 相关客户端（`Replicated`）；`RepNotify` 触发 OnRep | Server／Client／NetMulticast 三向 |
| 触发 | 服务器改值，引擎同步 | 显式调用 |
| 可靠性 | ActorChannel 内可靠有序 | 可选 Reliable／Unreliable |

场景划分：血量、子弹数、队伍、开关等"状态"用属性复制，客户端 OnRep 做表现；技能释放通知、爆炸特效、一次性伤害结算、请求服务器做事等"事件与命令"用 RPC。误用方向：用 RPC 高频同步连续状态（自己造状态同步），或用属性复制表达一次性动作（OnRep 丢失语义）。相关引擎实现见第 9、10 题，帧同步／状态同步的方案级对比见 [网络专题](网络高频题整理.md)第 9 题。

### 9. 属性同步在引擎层是如何实现的？

**答案：**

主干流程（Actor 复制）：

1. 服务器 NetDriver 按相关性（距离裁剪、bAlwaysRelevant 等）筛选每个连接可见的 Actor，为其维护 ActorChannel。
2. `GetLifetimeReplicatedProps` 注册的属性构成 FRepLayout；每个属性有生命周期条件（`DOREPLIFETIME_CONDITION`）。
3. 每次复制时对比属性是否变化（Push Model 开启的属性改为手动 `MARK_PROPERTY_DIRTY` 直接标脏，省掉轮询比较的 CPU），变化量经序列化压缩打包成 bunch 发送。
4. 客户端按序应用，调用 `OnRep_XXX` 回调做表现逻辑；休眠（NetDormancy）的 Actor 跳过更新直到被唤醒。

要点：属性复制是服务器权威，客户端本地改 `Replicated` 属性不会同步且会被服务器覆盖；有序可靠由 ActorChannel 保证，所以同一属性的多次修改可能合并为一次到达（最新值生效），不能依赖"每次修改都触发一次 OnRep"。

### 10. FastArraySerializer 与 Push Model 分别解决什么问题？

**答案：**

- FastArraySerializer：普通 `TArray` 的 UPROPERTY 复制是整个数组变化即整体重发。FastArray 把数组拆成元素级增量同步：增／删／改只标记对应元素（`MarkItemDirty`／`MarkArrayDirty`），配合 baseline 做差量，背包、房间列表这类大数组用它能把带宽降一个量级。元素建议带稳定的 RepKey／ID。
- Push Model：默认复制每帧轮询比较所有属性找变化，属性多时比较本身就是 CPU 热点。Push Model 让代码在修改处手动标脏，引擎只发送标脏属性，用调用侧纪律换比较开销。

网络波动下的正确性：ActorChannel 可靠有序，FastArray 有 baseline 校验，客户端 baseline 不匹配或丢失时引擎会请求完整重同步，因此"同步出错"多数源于绕过标记宏直接改数据、元素 ID 不稳定或自行实现了无基线协议。排查方向是确认所有修改走 `MarkItemDirty`、key 稳定、必要时 `ForceBaseline` 重发。

## 四、动画系统

### 11. Root Motion 是什么？什么场景使用？

**答案：**

Root Motion 把动画根骨骼的位移旋转"提取"出来应用到胶囊体／Actor 上，让角色实际位移由动画数据驱动，而不是由移动输入直接驱动。优点是脚步与移动严格对齐，攻击距离、翻滚落点精确符合动画制作。

适用场景：近战连段、处决、翻滚、交互动作等对位移精度敏感的表现型动作，通常配合蒙太奇播放。代价与边界：位移被动画锁死，转向与变速不如程序移动灵活；联网下 CharacterMovementComponent 通过 Root Motion Source 把动作位移纳入移动预测与服务器校验，但高频常规移动仍建议用普通移动输入，Root Motion 只给关键动作。不勾选 Root Motion 的动画只原地播放根骨骼位移。

### 12. Motion Warping（运动扭曲）是什么？

**答案：**

Motion Warping 在播放带 Root Motion 的动作时，按注册的 Warp Target 动态缩放／旋转根运动轨迹，使同一段动画适配不同实际距离与方向。典型场景：翻越不同深度的掩体、与不同体型目标的对峙处决、上马上车——动画只做一条，落点由运行时目标决定。

使用方式：动画内用 Motion Warping 通知划出窗口，代码在窗口前 `AddOrUpdateWarpTarget`（位置＋朝向），插件在窗口内把根运动曲线拉伸到目标。注意扭曲只改轨迹不改节奏感知，目标过远时动作会被明显拉伸，需要限制最大扭曲距离并做失败回退（改用普通移动接近）。

### 13. 动画蒙太奇与 Slot 插槽如何配合？

**答案：**

蒙太奇（Montage）把多段动画组织成 Section，可配置跳转、混合与通知，是技能动作的常用载体；Slot 是 AnimGraph 里的"插座"节点，决定蒙太奇姿势从主状态机的哪个位置混入。

配合关系：播放蒙太奇时，其姿势输出到同名 Slot（如 DefaultSlot），Slot 节点有姿势就覆盖该分支，没有就透传原姿势，从而实现"上半身放技能、下半身继续跑"的分层混合。Character 上 `PlayAnimMontage` 自动做网络复制（客户端看得到别人放技能），蒙太奇内的 AnimNotify 可挂伤害判定、音效与特效。技能系统（GAS 或自制）普遍以"逻辑窗口＋蒙太奇表现"的方式组织：Montage 管表现与节奏，技能逻辑管判定与效果。

## 五、AI 与技能

### 14. 行为树中 Selector 节点下的子任务都会被执行到吗？

**答案：**

不会。Selector（选择节点）从左到右依次尝试子节点：某个子节点成功则 Selector 直接返回成功，右侧剩余子节点本轮不再执行；全部失败才返回失败。所以左侧是高优先级，顺序即优先级，靠排序表达"先尝试 A，不行再 B"。

追问延伸：

- Sequence（顺序节点）相反：全部成功才成功，中途失败即短路返回失败。
- 装饰器可中断运行中分支：Lower Priority Abort 能打断右侧正在运行的低优先级子树，让高优先级条件重新抢占。
- 因此把纯条件节点放 Selector 左侧、有副作用的动作放右侧，避免"条件判断也会被跳过"导致的逻辑歧义。

### 15. 敌人技能是扇形，如何用数学判断技能有没有打中目标？

**答案：**

在水平面（忽略 Y 或投影到地面）做两步判定：

```text
向量 to = 目标位置 - 施法者位置
1. 距离：dot(to, to) <= (R + 目标半径)^2        // 平方比较，免开方
2. 角度：dot(施法者朝向, normalize(to)) >= cos(半角)
```

两步同时满足即命中；用点乘与预计算 `cos(halfAngle)` 可完全避免 `acos`，角度接近 180° 时改用叉积判方向更稳。边界与追问：

- 目标是胶囊而非点：用目标中心或把 R 扩大一个目标半径近似；要求更准就对扇形与胶囊做分离轴或采样判定。
- 距离为零（目标在脚下）：视为命中，避免 normalize 除零。
- 预判定可以做手感预瞄（施法瞬间定扇形）还是实时跟随朝向，属于设计口径，先和策划对齐。

### 16. GAS 是什么？如果自己设计一套技能框架，怎么做？最难的是什么？

**答案：**

GAS（Gameplay Ability System）是 Epic 的技能框架：GameplayAbility 承载技能逻辑，GameplayEffect 用修改器改变 Attribute（属性集），GameplayTag 做状态门控与打断，GameplayCue 做表现，AbilitySystemComponent 负责授予、激活与网络预测。

自行设计的最小骨架（借鉴 GAS 分层思想）：

1. 数据驱动：技能配置表／DataAsset 定义消耗、CD、前摇时长、判定体、效果列表与表现资源。
2. 阶段状态机：前摇 → 生效（判定结算）→ 后摇，明确可打断点与不可打断点。
3. 效果层：属性修改器（瞬时／持续／无限）统一走一个结算入口，天然支持叠层与免疫规则。
4. Tag／事件门控：眩晕、沉默用标签阻断技能激活，打断用事件驱动，不写死在技能里。
5. 表现分离：逻辑只发"事件＋参数"，表现层（特效、音效、蒙太奇）订阅执行，便于换皮与减配。

公认难点：一是打断与效果叠加的规则组合爆炸（互斥、刷新、叠加优先级），规则不先收敛后期必乱；二是网络预测与回滚一致性（客户端预判表现、服务器权威结算、失败回滚的表现清理）。没学过 GAS 时答出这个分层与难点，比背名词更有效。

## 六、UI、文本与适配

### 17. UMG 和 Slate 是什么关系？

**答案：**

Slate 是引擎底层 UI 框架：SWidget 树、声明式构建语法、绘制与失效（invalidation）、输入路由，编辑器本身就是 Slate 写的。UMG 是游戏层的 UObject 包装：UWidget 持有并按需构建底层 SWidget（`TakeWidget()`），暴露细节面板、绑定、动画时间线，让策划美术能在编辑器里拖 UI。

分层记忆：UMG 管数据与编辑工作流，Slate 管绘制与输入。UMG 控件属性修改通常触发重建或同步到 SWidget；做深度定制（自定义绘制、性能敏感列表）时会下沉写 Slate 控件。两者失效机制都遵循"改属性只标脏，绘制帧才重算"，高频重建是 UI 卡顿常见来源（见第 20 题）。

### 18. UI 系统框架如何设计？所有 UI 都需要异步加载吗？

**答案：**

一套常见的客户端 UI 框架包含：

- 分层：世界层、HUD 层、弹窗栈（可返回）、Loading 层、引导层、调试层；层级决定遮挡与输入优先级。
- 管理器：Open／Close／返回栈管理，参数用结构体传递，生命周期回调（预打开、打开完成、关闭前、关闭后），弹窗去重与互斥。
- 加载：控件类与资源用软引用异步加载，请求队列＋同类请求合并；常驻 UI 用对象池复用。
- 数据与视图分离：Widget 只订阅数据变化刷新，不在 Tick 里轮询绑定。

不是所有 UI 都要异步。判断依据是"加载成本 × 打开频率 vs 卡顿预算"：高频小控件（血条、快捷栏）预加载或常驻池化，同步打开无感；低频大界面（商城、背包大图集）异步加载＋遮罩过渡。全异步反而带来回调时序与状态管理复杂度，按预算分级即可。

### 19. 手游多分辨率下如何做 UI 适配与渲染优化？

**答案：**

适配：

- DPI 缩放规则（按短边曲线或自定义曲线）统一缩放基准，锚点＋对齐处理不同宽高比；刘海与安全区用 SafeZone 包裹。
- 特殊比例（刘海屏、折叠屏）定义最小安全边距与可拉伸区域，背景类元素允许溢出裁切，信息类元素锚定安全区内。
- 手柄／触屏输入差异用 CommonUI 类方案处理焦点导航切换。

渲染优化：

- 控件数量与层级是第一成本：合并重复结构，动效控件单独隔离，不用时 Collapsed 而非移到屏幕外。
- 图集合批减少 draw call，避免大量不同贴图小图标；九宫格减少碎图。
- 避免 UPROPERTY 绑定与 Tick 每帧求值，改事件驱动刷新；移动端关注 overdraw，全屏半透明叠加要节制。
- 用 RenderTransform 做位移动效，不触发布局重算（与第 20 题同理）。

### 20. 高帧率下 UI 跟随鼠标会跟不上，如何解决？

**答案：**

先定位原因：多数是位置更新走了布局流程（改几何属性触发失效重排），或更新时机挂在 Tick／低频轮询上，输入采样与 UI 更新节奏错位。解决：

1. 在 `OnMouseMouseMove` 事件里直接 `SetRenderTransform`（RenderTranslation）更新位置：Render Transform 不参与布局，只影响绘制，开销最低且与输入事件同帧生效。
2. 屏幕坐标换算考虑 DPI 缩放比例，避免高 DPI 下偏移。
3. 跟随元素与被重建的父级隔离，避免父级失效把它一起拖进重绘；必要时设置 volatile 绘制路径。
4. 仍要更顺滑时，在渲染级做一阶平滑（按帧插值到目标点），但保持目标点由输入事件驱动。

原理一句话：输入事件驱动＋绕过布局的绘制级更新，天然与帧率同步，不存在"跟不上"。

### 21. 聊天框因为消息高度不同，滚动条长度如何动态计算？

**答案：**

滚动条比例的通式：`滑块长度 = 视口高度 / 内容总高度`，位置由滚动偏移决定。关键在内容总高度的获取：

- 使用 ScrollBox 时引擎自动测量并更新滑块；自定义列表才需要手算。
- 手算方案：对每条消息用 Slate 字体测量服务（GetFontMeasureService）按当前内容宽度做折行测量，`行数 × 行高 + 内边距` 得到单项高度，累加成总高度并缓存。
- 监听重算时机：新增／删除消息、窗口宽度变化（折行宽度变了每条高度都可能变）、字体或字号设置变化。
- 大量消息不要每次全量重测：缓存单项高度，增量消息只测新增项；测量是文本 shaping 级开销，热路径要防抖。

### 22. UE 富文本只支持字号、颜色等基础样式，如何实现 Markdown 的删除线效果？

**答案：**

富文本的可扩展点在装饰器（Decorator）：继承 `FRichTextDecorator`（或参照 `URichTextBlockImageDecorator` 写一个图片装饰器变体），注册进 RichTextBlock 的装饰器集合，识别自定义标签如 `<strike>文字</strike>`。

实现要点：

1. 解析：装饰器按标签匹配文本片段，创建对应的 Slate 子控件。
2. 渲染横线：在文字上叠加一条笔刷。长度要跟随文字实际宽度——用字体测量服务取该段文字像素宽，设置笔刷尺寸；横线素材做细长条，用动态材质配合 TextureCoordinate 按宽度平铺（shader 里乘以重复次数），避免拉伸变形。
3. 通用化：多个标签（下划线、高亮）可做一个参数化装饰器＋样式表，而不是每个标签写一套。

成本提醒：自定义装饰器绑定了项目内富文本用法，引擎升级与本地化（标签内文字折行）要回归测试。

### 23. UE 文本换行的原理是什么？中英混排的长串字母不换行怎么解决？

**答案：**

文本更新链路：`SetText` → 文本布局标记脏 → 装配器解析文本，由断行分析产出断行候选（BreakCandidates，中文按字、英文按词与标点）→ `TextLayout` 的流式布局逐候选测量像素宽度，超出宽度边界就在该候选处断行。

问题成因：`"嘻嘻aaaaaaaa…"` 这串 `a` 没有任何断行候选，整串被当成一个"单词"，第一行放不下就整串挪到下一行，第一行只剩"嘻嘻"。

解决方案：继承富文本装配器／自定义文本布局接口，重写文本准备阶段——从每行行首开始逐字符累积截取子串，用字体测量服务测量像素宽度，超过换行宽度的那个字符处插入零宽空格（U+200B）等无宽度符号；它本身是合法断行候选，流式布局就会在那里正常断行。该方案逐字符测量有成本，只对无断点的长串触发即可。

## 七、系统设计与排查

### 24. 设计一个资源加载接口：本地存在则本地加载，不存在则向服务器请求，怎么做？

**答案：**

```text
LoadAsync(path, version, callbacks)
  ├─ 命中内存缓存 → 直接回调
  ├─ 本地磁盘存在（缓存目录 + 版本校验）→ 异步加载 → 回调
  └─ 未命中 → 请求队列 → HTTP 下载 → 校验（hash／版本号）
       ├─ 成功 → 写入本地缓存目录 → 加载 → 回调
       └─ 失败 → 超时重试（带退避）→ 失败回调
```

设计要点：接口统一返回请求句柄（可取消、查进度），回调保证主线程执行；同一路径的并发请求合并为一次下载与一次加载，引用计数管理句柄；下载并发数限流；缓存目录带版本或 hash 命名，支持增量更新与清理；磁盘满、断网、包损坏都要有明确失败路径。UE 内实现对应：软引用／AssetManager 做异步加载，FHttpModule 下载，PersistentDownloadDir 做缓存，FStreamableManager 管理句柄。

### 25. 同一个 Image 频繁更换图片资源，加载接口怎么设计避免冲突？

**答案：**

核心是"最新请求优先＋过期回调作废"：

1. 每次设置图片生成自增 token（或代际号），回调触发前校验 token 是否仍是当前值，不是则丢弃——乱序完成的异步加载不会把旧图盖回来。
2. 同路径的 in-flight 请求合并：引用计数挂在路径上，完成时分发给所有等待者。
3. 加载完的纹理走 LRU 缓存，频繁切换的两张图命中缓存零成本；配合占位图避免闪白。
4. 真正高频轮播（序列帧）不逐张 SetBrush，改为预加载整套后用材质／Flipbook 方案渲染。

面试官想听的陷阱意识：异步回调时序、内存缓存上限、以及"取消"其实是"作废回调"而不是中断加载本身。

### 26. 排行榜系统客户端与服务器如何协作？轮询时机怎么定？

**答案：**

协议设计：拉取模型比推送简单——打开界面时请求一次，参数化范围（前 N 名、我的名次附近区间、翻页），响应带数据版本号或时间戳；玩家自己的名次变化可由服务器在结算点主动推一条轻量事件做脏标记。

轮询时机：界面可见时按固定周期轮询（30–60 秒量级，带随机抖动避免集群同步请求），后台／不可见时停止；拿到版本号与本地一致就跳过渲染。周期取决于业务对实时性的要求：结算型排行榜可以只在打开与结算时拉，实时竞技榜才需要短周期＋推送。客户端缓存上次数据做先显示后更新，避免每次打开都白屏等待。防止请求风暴的手段：抖动、缓存 TTL、分页与区间查询，绝不做"打开界面拉全榜"。

### 27. 类三角洲背包（格子固定、物品占格不同）如何设计，支持快速排序、定位与拖拽表现？

**答案：**

数据层：

- 物品配置表：占格 W×H、图标、类型、品质等静态数据；实例表：uid、配置 id、锚点左上角格坐标、数量、强化词条等动态数据。
- 网格：`TArray<FCell>` 记录每格被哪个 uid 占用（空为 0）；`TMap<uint64, FItemInstance>` 按 uid 定位实例——"通过物品 ID 快速定位"就是这张哈希表，O(1) 免遍历。
- 放置查询：从锚点检查 W×H 区域占用，可按行位图加速；放置即写锚点与占用标记。

排序：对实例列表按类型／品质／等级排序后整体重新摆放（按行优先贪心装箱），客户端与服务端用同一套摆放规则或由服务端下发结果，保证一致。

拖拽表现：代理模式——拖起时生成幽灵控件跟随指针，原格数据标记"拖拽中"（逻辑上已移出但可取消回滚）；悬停时用占格查询实时高亮合法／非法落点，支持旋转预览；落点提交才真正改数据并播放动画。数据与视图分离后，排序、网络同步与拖拽共用同一套占用查询。

### 28. 设计子弹对象池时，池大小从哪些方面考虑？

**答案：**

- 峰值并发估算：Σ(各武器射速 × 弹道存活时间) × 同屏参战单位数 × 技能密度倍率，取战斗最激烈场景（Boss 战、大规模团战）为上限口径。
- 单对象成本：Actor＋碰撞＋特效＋音频组件的内存与 tick 开销；移动端内存预算直接封顶。
- 池空策略：达到上限时拒绝、复用最旧还是临时扩容——竞技项目倾向固定上限＋复用最旧，行为确定不抖。
- 预热：加载场景时实例化全部对象，避免战斗中首次分配尖峰；归还时重置状态（碰撞关闭、特效回收）而不是销毁重建。
- 数据驱动＋监控：上限做成可配置，线上统计获取失败／复用最旧次数，超阈值调参。

回答时给出"先估峰值、再卡内存、预热上限、留监控"的顺序，比直接报一个数字可信。

### 29. 游戏在某个场景突然卡顿，怎么排查？

**答案：**

1. 定位线程：`stat unit` 看 Game／Draw／GPU 哪个超预算，`stat unitgraph` 抓尖峰；确认是单帧尖峰（卡顿）还是均值超标（掉帧）。
2. 用 Unreal Insights（Timing／Memory Insights）或前端 Profiler 对尖峰帧采样，打开 named events 对齐代码区域。
3. 按高频嫌疑缩小：
   - GC：`stat gc`、对象数量（`obj list`），尖峰与 GC 触发对齐则查分配源（大量 spawn、UPROPERTY 大容器）。
   - 同步加载：Streaming 日志与 Loading 线程占用，查同步 LoadObject／构造函数加载。
   - Shader／PSO 编译：新材质首次出现导致编译卡顿，检查 PSO 预缓存。
   - 物理、动画、蓝图热点：对应 stat 逐项排除；日志刷屏也常是隐形大头。
4. 复现路径固化 → 修复前后用同一工具对比数据 → 长期接入 hitch 监控在 CI 与真机上报警。

答题节奏：先说"分类到线程"，再说工具，再说嫌疑清单，最后落到流程（复现、量化、对比），避免一上来报菜名。

### 30. Lyra 的输入与多平台适配、UI 框架有什么可借鉴的？

**答案：**

- 输入：基于 Enhanced Input，按平台与操控方案组织 Input Mapping Context（键鼠、手柄、触屏各自 IMC），运行时按设备动态叠加／移除；输入动作带修饰器与触发器，输入被赋予 Tag 便于技能与玩法层查询。借鉴点：输入与玩法解耦，加新设备=加 IMC，不改玩法代码。
- 资源多平台：Asset Manager 管理主资产（Primary Asset）与平台覆盖规则，同一逻辑资产按平台出不同资源与打包分块；Pawn Data 等配置资产决定角色整套配置。借鉴点：平台差异收敛在资产规则层。
- UI：基于 CommonUI 的 UI Extension 机制，控件按 Tag 注册进由 PrimaryGameLayout 管理的分层栈，键鼠／手柄焦点自动切换。借鉴点：UI 由注册表解耦，界面之间不互相持有。

面试话术：不背 Lyra 细节也能答好——说清"输入 IMC 分平台、资产平台覆盖、UI 分层注册"三个机制与各自的工程动机即可。

### 31. UE 的内容本地化方案了解多少？

**答案：**

- 三种文本类型：`FName` 是标识符不做显示；`FString` 是原始字符串；面向显示一律 `FText`——支持本地化查找、参数格式化（`FText::Format`）、数字日期的文化相关格式化，还有 Culture Invariant 模式给"永不翻译"的文案。
- 取文案宏：`LOCTEXT`／`NSLOCTEXT` 带命名空间参与收集。
- StringTable：字符串表资产集中管理文案，文本以表＋键引用；重复文案去重、翻译批量导出导入，适合大量系统提示。
- 流程：Localization Dashboard 配置收集目标 → Gather 提取所有 FText → 翻译 → 编译归档 → 打包按语言分文化数据；支持运行时切语言并刷新 UI。

易错点：拿 FString／FName 直接上 UI 会绕过本地化；拼接出来的句子在不同语序语言下会出错，应整句作为词条＋占位符参数化。
