# Unity 性能与工具开发岗位学习路线

> 根据提供的实习岗位 JD 制定。目标是能完成一个小范围问题的复现、测量、定位、修改和验证，并讲清与客户端、TA、美术协作的过程。下列优先级是对 JD 的判断，不代表公司实际题单。

[返回题库总目录](面试题库总目录.md) · [岗位专项问答](性能分析与工具开发专项题.md)

## 一、这个岗位重点考察什么

岗位围绕性能分析、资源与加载基础设施、渲染支持、工具链和规范执行展开。准备时应形成三类证据：**扎实的 C# 基础、可解释的排查过程、一个可展示的小工具或优化案例**。

| 职责 | 需要掌握的知识 | 能做到什么才算掌握 |
| --- | --- | --- |
| 多端性能定位 | Profiler、CPU/GPU 帧时、等待、GC、真机对比 | 给出复现条件与数据，区分瓶颈和表面症状 |
| 资源与加载能力 | 资源所有权、依赖、异步状态、缓存与释放 | 解释失败、取消、重复请求和场景退出如何收尾 |
| 渲染优化 | Draw Call、批处理、Overdraw、纹理、阴影、UI | 在画质约束下定位最贵的 Pass 或资源，并验证方案 |
| 工具开发 | EditorWindow、AssetDatabase、Importer、数据报告 | 扫描资源，输出可定位问题，支持可控修复和重复运行 |
| 跨团队落地 | 预算、规范、负责人、例外与回归 | 把“太卡／太大”变成可复现、可量化、可验收的问题 |

现有题库中的热重载、复杂 ECS-like、深层无锁算法可留到核心内容之后。对这个实习岗位，不需要先以“能造一套完整引擎”为准备目标。

## 二、建议投入顺序

以下为可调整的学习时间比例，包含阅读、动手和复盘，并非考试分值。

| 顺序 | 方向 | 建议投入 | 重点 |
| --- | --- | --- | --- |
| 1 | 性能分析与优化验证 | 25% | 帧预算、Timeline、Hierarchy、GC、快照、基线与回归 |
| 2 | C# 与数据结构 | 20% | 值与引用、装箱、集合、委托、生命周期、异步、复杂度 |
| 3 | 资源与加载 | 15% | Addressables/AB、引用归属、加载阶段、并发合并、内存峰值 |
| 4 | 渲染与 UGUI | 15% | CPU 提交、GPU 像素成本、材质、纹理、阴影、UI 重建 |
| 5 | 编辑器与诊断工具 | 20% | 资源扫描、规则配置、结果导出、日志、自动检查 |
| 6 | Lua、英文文档与表达 | 5% | Lua 基本模型、读 API 文档、英文摘要、项目复盘 |

网络先掌握异步消息、超时、重试与下载校验。JD 没有强调联网对战，不必优先投入复杂同步框架或协议细节。

| [算法题库](算法高频题整理.md) | 复杂度、排序、DFS/BFS；再看 A* | 能处理边界输入，解释空间与时间取舍 |

## 四、建议做一个什么项目

建议把“资源检查工具”和“优化案例”放在同一个已有小项目中，做成 **资源扫描 → 问题定位 → 改动预览 → 修复 → 数据对比** 的闭环。只展示实际完成的内容与测量结果。

### 资源规范检查工具

最小范围选择纹理，避免一开始同时覆盖所有资源类型。

1. 选定 Assets 下的目录，扫描纹理资源及目标平台设置。
2. 检查最大尺寸、Read/Write、MipMap、压缩/平台覆盖和命名规则；规则按 UI、角色、场景等用途区分。
3. 输出资源路径、规则 ID、当前值、期望值、原因和建议；支持点击定位以及 CSV/JSON 导出。
4. 默认只报告；对可安全自动修复的条目先显示差异，再按选中范围应用。重复运行不应反复改动已符合规则的资源。
5. 记录运行时长、扫描数量、取消/失败状态与例外规则；实际验证修复后的效果。

**展示材料：**工具界面或报告、几个误报处理实例、规则配置、修改前后差异、为什么某条规则没有自动修复。

### 一个可复现的性能问题

从自己项目里选一种确实存在的问题：列表大量实例、每帧分配、重复材质实例、切场景内存峰值、透明特效开销等。

**记录模板：**

| 字段 | 需要填写的真实信息 |
| --- | --- |
| 场景与步骤 | 怎样稳定触发，固定哪些变量 |
| 环境 | Unity/包版本、设备、分辨率、画质、限帧、运行模式 |
| 基线 | 帧时间分布、热点、分配/内存及可见异常 |
| 假设 | 怀疑什么；什么证据可以反驳它 |
| 修改 | 改了哪一处，为什么能减少成本 |
| 复测 | 同条件重复测试，改善多少，是否产生新问题 |
| 取舍 | 内存、加载、画质、复杂度或平台兼容成本 |
| 防回归 | 自动规则、性能阈值、复现流程与负责人 |

没有低端真机时，可先完成已有设备上的可复现案例，并明确覆盖范围。不要将 PC 数据包装成移动端结论。

## 五、可压缩的两周准备安排

假设尚未确定面试日期，下面是按学习轮次安排的两周参考；可根据实际时间合并，并非固定日程。

| 阶段 | 学习任务 | 当阶段产出 |
| --- | --- | --- |
| 第 1–2 天 | C# 核心、集合、分配与生命周期 | 解释 10 段常见代码；整理自己的薄弱点 |
| 第 3–4 天 | Profiler、帧时、CPU/GPU、GC | 一个可复现场景和一份基线记录 |
| 第 5–6 天 | AB/Addressables、加载阶段与失败路径 | 加载状态图、引用归属表、退出流程 |
| 第 7–8 天 | 渲染、UI、纹理预算 | 一次有依据的对照实验和画质对比 |
| 第 9–11 天 | Editor 工具、规则与报告 | 可使用的纹理检查工具或完整报告原型 |
| 第 12 天 | 算法与 Lua | 写出搜索/排序核心流程，解释 Lua 对象和 GC |
| 第 13 天 | 验证、整理项目材料 | 优化前后数据、误报/失败案例和限制 |
| 第 14 天 | 模拟面试与英文文档复述 | 3 分钟项目介绍、10 分钟排查讲解 |

如果只剩三天，先完成：C# 高频基础、Profiler 排查流程、资源所有权、合批与 Overdraw、一个真实案例。工具可展示已完成的最小功能，但不要把设计稿说成落地成果。

## 六、面试前自查

- 能解释“平均 FPS 正常但仍卡顿”，并列出需要采集的时间和内存数据。
- 能解释某个等待标记为何不直接证明 GPU 瓶颈。
- 能说清加载资源、实例化、激活分别由谁计时、由谁释放。
- 能说明一次资源规则扫描如何避免误报、反复导入和不可控修改。
- 能完成数组、哈希、队列/栈、排序与图遍历的基本推理。
- 能用英文文档确认某个 API 的输入、返回值、线程/生命周期限制与版本范围。
- 项目陈述中明确“我做了什么、数据说明什么、还有哪些限制”。

## 七、投递条件与沟通准备

JD 明确要求预计 2027 年内毕业的在校生、每周至少 4 天、CET4 及以上。投递前核对自己的预计毕业时间、英语资格、每周可到岗天数、开始时间和可持续实习时长，准备清晰回答。

岗位没有给出具体 Unity 版本、管线和目标设备。面试沟通时可了解这些约束，以及团队目前最关注的性能或资源问题；这样能将自己的案例连接到真实工作，而不是泛泛罗列技术名词。
