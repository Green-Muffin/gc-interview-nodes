## 一、协议基础

### 1. Socket、TCP、UDP、HTTP 和 WebSocket 有什么关系？

**答案：**

Socket 是网络通信接口／端点抽象；TCP 提供可靠有序字节流，UDP 提供数据报；HTTP 定义应用层请求响应，WebSocket 提供消息化双向通信。

HTTP/1.1、HTTP/2 通常基于 TCP，HTTP/3 基于 QUIC／UDP。游戏可按登录、下载、聊天、实时状态等需求分别选择。

### 2. GET 和 POST 有什么区别？

**答案：**

GET 用于获取资源，语义上安全且幂等；POST 让服务端处理提交内容，默认不保证幂等。GET 参数常放 URL，POST 常使用请求体，但这不等于保密差异。

安全传输依赖 HTTPS 等机制，POST 不自动加密；请求长度限制由具体组件决定，不是 GET 固定只有 2 KB。

### 3. 大 JSON 接口不常变化，如何利用 HTTP 缓存节省流量？

**答案：**

服务端返回 ETag 或 Last-Modified，并设置合适的 Cache-Control。客户端缓存正文和验证信息；过期后发送 `If-None-Match` 或 `If-Modified-Since`，内容未变时服务端返回 304，不再传输完整正文。

可将大数据拆为稳定基础数据和小型增量，启用内容压缩，并为离线场景设置 stale 策略。缓存键要包含真正影响结果的请求参数和用户身份，更新时通过版本／ETag 失效，避免无限缓存旧数据。

### 4. TCP 和 UDP 有什么区别？游戏中如何选择？

**答案：**

TCP 自动处理可靠、有序传输、重传和拥塞控制，适合需要完整结果的数据；UDP 保留消息边界，不保证到达／顺序，适合业务自行处理时效和容错的实时消息。

位置更新可能允许新状态替代旧状态，交易等操作则需要可靠交付与去重。UDP 自建可靠机制需考虑序列号、ACK、重传、拥塞和过期策略。

## 二、TCP 连接与消息

### 5. TCP 三次握手的过程是什么？为什么需要三次？

**答案：**

```text
客户端 → 服务端：SYN，seq=x
服务端 → 客户端：SYN+ACK，seq=y，ack=x+1
客户端 → 服务端：ACK，ack=y+1
```

双方交换初始序列号，确认彼此的发送／接收状态并协商相关选项。第三次确认让服务端知道自己的 SYN 已被对方收到，避免仅收到连接请求就认定双向连接已建立。

### 6. TCP 四次挥手和 TIME_WAIT 的作用是什么？

**答案：**

TCP 两个方向可分别关闭，常见为 FIN → ACK → FIN → ACK：先关闭一方发送方向，另一方发送完剩余数据后再关闭自己的方向。

主动关闭侧通常进入 TIME_WAIT，防止旧连接延迟报文影响新连接，并可在对方重发 FIN 时再次确认。ACK 与 FIN 可合并，所以抓包不一定总是恰好四段。

### 7. 什么是粘包和拆包？如何处理？

**答案：**

TCP 是字节流，一次读取可能只有半条业务消息，也可能包含多条；接收调用不对应发送调用。

常用长度前缀、固定长度或带转义分隔符定义消息边界。接收端维护缓冲：头不足就等待，正文不足继续收，完整后取出一条并循环解析剩余部分。检查最大长度、字节序和部分发送，避免非法长度导致超量分配。

## 三、游戏通信

### 8. 心跳、断线重连和请求重试怎么设计？

**答案：**

通过周期心跳和超时窗口判断连接活性，连续失败后重连；重连采用带抖动的退避，避免客户端同时冲击服务端。

请求设置 ID，区分重发和新请求。超时不代表服务端没处理，非幂等操作要有去重／结果查询。重连后恢复认证、订阅和状态版本，过滤旧请求响应。

### 9. 状态同步和帧同步有什么区别？

**答案：**

状态同步传递服务器状态／快照，客户端常用插值、预测和校正；帧同步主要传输入／指令，各端按统一时序推进，要求相应的确定性。

状态同步便于服务器权威，但消耗快照带宽；帧同步可少传状态，却更依赖时钟、输入等待及一致模拟。按游戏类型选择，并设计丢包、重同步和作弊校验。

逐维度对比：

| 维度 | 帧同步（Lockstep） | 状态同步（Server Authoritative） |
| --- | --- | --- |
| 同步内容 | 只同步玩家输入／指令 | 同步实体状态与快照 |
| 逻辑位置 | 全端各自确定性模拟 | 服务器权威模拟，客户端表现 |
| 带宽 | 随玩家数增长，极低 | 随实体数与状态量增长，高 |
| 确定性要求 | 严格：浮点、容器遍历、随机数全部一致 | 无硬性要求 |
| 表现 | 天然一致，易做回放与观战 | 需插值、预测与和解 |
| 断线重连 | 追帧（重放全部指令） | 直接下发当前快照 |
| 反作弊 | 逻辑在客户端，暴露严重 | 服务器权威，天然抗作弊 |

选型不是公式而是权衡：MOBA（英雄少、单位确定、需要回放与低带宽）经典选择帧同步，但也有 MOBA 用状态同步；MMO（世界规模大、实体不可枚举、反作弊要求高）几乎只能状态同步。射击游戏常见混合：核心状态走状态同步，命中判定视项目放服务器或客户端。回答时先说清两种方案的本质差异，再按“实体规模、反作弊、回放需求、团队确定性工程能力”给结论。

### 10. 游戏消息如何序列化并降低带宽？

**答案：**

明确消息类型、版本、长度、实体 ID 和时间／序列号，再选择合适的二进制或文本表示。接收端校验长度和取值，服务器还需校验业务权限。

可通过量化、差量、压缩、降低更新频率和 AOI 筛选减少传输。差量依赖双方共有基线，基线失效时要能恢复完整状态。

以 ProtoBuf 为例的代表优势：二进制 tag＋varint 编码，不传字段名与类型描述，同内容远小于 JSON／XML；编解码接近内存拷贝量级，字符串解析 GC 压力小；`.proto` schema 经 `protoc` 生成 C++／C#／Java 等多语言代码，客户端服务器共用一份契约；按字段编号识别，新增字段老端忽略、废弃字段保留编号不复用，向前向后兼容有明确规则。边界：ProtoBuf 不加密，保密靠 TLS；proto3 默认值字段不序列化，不能用“字段缺失”区分默认与未设置；UE／Unity 集成注意 AOT 下的反射裁剪，必要时用代码生成方案。
