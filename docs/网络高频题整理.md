## 一、协议与通信方式

### 1. Socket、TCP、UDP、HTTP 与 WebSocket 是什么关系？

**答案：**

Socket 是网络通信编程接口／端点抽象，不是物理连线，也不是与 HTTP 平级的一种独立传输协议。

TCP 提供可靠有序的字节流；UDP 提供数据报服务；HTTP 定义应用层请求与响应语义，HTTP/1.1、HTTP/2 常运行于 TCP，HTTP/3 基于 QUIC／UDP；WebSocket 提供消息化的双向通信协议。

游戏中可按登录／配置下载、聊天、实时状态同步等需求选择，不存在“所有游戏必须只用一种”。SOAP 属于基于消息格式与调用约定的更高层方案，不是 TCP 的替代传输层。

### 2. GET 与 POST 的核心区别是什么？POST 一定更安全吗？

**答案：**

GET 用于获取目标资源的表示，语义上是安全且幂等的方法；POST 请求目标资源按其语义处理请求内容，默认不保证幂等。安全指预期操作不改变服务端业务状态，不代表服务端不写日志。

不能用“GET 有固定 2 KB 上限，POST 无限制”概括，长度限制来自具体组件；POST 也不自动加密。保密性依赖 HTTPS 等机制，同时避免把敏感数据放进可能被记录的 URL。

GET 内容体没有普遍定义的语义，不应依赖所有服务器或中间件支持它；缓存行为也由方法及响应头等共同决定，不能说 POST 永远不可缓存。

参考：[RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3)。

## 二、TCP 连接与消息

### 3. TCP 三次握手交换了什么？

**答案：**

常见主动连接流程：

```text
客户端 → 服务端：SYN，seq = x
服务端 → 客户端：SYN + ACK，seq = y，ack = x + 1
客户端 → 服务端：ACK，ack = y + 1
```

双方同步初始序列号并确认彼此连接状态，相关选项也可在 SYN 中协商；SYN 占用一个序列号。不要把它只解释成“测试网络通不通”。第三步的 ACK 可以与数据一起发送。

TCP 握手不等于 TLS 身份验证，也不保证之后永不丢包。

参考：[RFC 9293 建立连接](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5)。

### 4. 为什么常说 TCP 四次挥手？TIME_WAIT 有什么意义？

**答案：**

TCP 两个方向可分别关闭。常见流程为一方 FIN、对方 ACK；对方发送完剩余数据后再 FIN；第一方 ACK。ACK 与 FIN 可以合并，也可能同时关闭，所以不是任何抓包都严格四个报文。

TIME_WAIT 帮助处理旧连接延迟报文，并在对端重发 FIN 时再次确认；不能简单删除它来“优化连接数”。具体时长与连接复用行为需结合协议与系统实现。

FIN 表示该方向没有更多数据；RST 是异常复位，语义不同。

参考：[RFC 9293 关闭连接](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)。

### 5. TCP 为什么会出现所谓粘包／拆包？如何设计消息边界？

**答案：**

TCP 提供字节流，接收调用与发送调用不一一对应。一次读到半条或多条业务消息属于正常情况，不是协议把消息“弄坏”。

常用长度前缀、固定长度或带转义的分隔符。接收端维护缓冲区：头不完整就等待，长度合法但正文不足就继续接收，完整后解析一条并循环处理剩余数据。

限制最大包长、校验整数溢出、处理连接关闭和部分发送，明确字节序及编码。UDP 保留数据报边界，但也仍需验证长度与内容。

## 三、游戏网络工程

### 6. TCP 与 UDP 如何选？UDP 上加可靠性要考虑什么？

**答案：**

TCP 自带可靠、有序传输和拥塞控制，但丢包后的按序交付可能让后续字节等待。UDP 不保证到达、顺序或去重，应用可根据实时性决定如何处理。

基于 UDP 的自定义可靠机制需考虑序列号、ACK、重传、去重、分片、拥塞控制和过期策略。位置更新可能允许新状态覆盖旧状态，交易结果则需要更强交付与去重语义；不要把所有消息一律可靠重传。

“UDP 一定更快”不是完整结论，真实效果取决于网络、包率、实现与业务容忍度。

### 7. 心跳、超时、重连和请求重试怎么设计？

**答案：**

心跳用于检测业务连接活性与维持部分网络状态，不代表一次未响应就一定断线。设置合理超时和容错窗口，重连使用带抖动的退避，避免大量客户端同步冲击服务端。

给需要追踪的请求设置唯一 ID，区分重发与新请求；非幂等操作不能在超时后盲目重试，因为服务端可能已经处理。重连后恢复认证、订阅和状态版本，对过期响应做过滤。

网络回调与主线程之间使用明确队列及背压，避免消息堆积造成内存增长。

### 8. 游戏状态同步与消息序列化要关注什么？

**答案：**

定义消息类型、版本、长度、ID、时间或序列号，并验证输入。序列化格式不能替代业务权限校验；服务端仍需验证客户端提交的状态与行为。

状态同步传递状态／快照，常配合插值、预测与校正；输入或帧同步传递指令，要求明确确定性、时钟和丢包处理。压缩、差量、量化与 AOI 能降低带宽，但都要有基线失效和重同步方案。

不要把“用了 TCP”视为业务恰好执行一次，也不要把跨平台浮点计算默认视为完全确定。
