## 一、版本特性与类型基础

### 1. C++11 的核心特性有哪些？

**答案：**

- 类型与语法：`auto`、`decltype`、`nullptr`、范围 `for`、lambda、强类型枚举 `enum class`。
- 对象与资源：右值引用、移动语义、`unique_ptr`／`shared_ptr`／`weak_ptr`、委托构造与继承构造。
- 接口契约：`override` 检查重写签名，`final` 限制重写或继承，`= default` 请求默认定义，`= delete` 删除指定函数。
- 常量与模板：`constexpr`、`static_assert`、可变参数模板、列表初始化与 `std::initializer_list`。
- 标准库：`thread`、`mutex`、`condition_variable`、`atomic`、`future`，以及 `array`、`tuple`、`unordered_map/set`、`regex`、`chrono`。

`nullptr` 的类型是 `std::nullptr_t`，避免用整数空指针常量参与重载时的混淆；`NULL` 的具体宏定义由实现决定，不要认定总是字面量 `0`。

```cpp
enum class Color { Red, Green, Blue };
int* p = nullptr;
std::vector<int> values{1, 2, 3};
for (auto& value : values) value *= 2;
std::sort(values.begin(), values.end(),
          [](int a, int b) { return a > b; });

struct Owner {
    Owner() = default;
    Owner(const Owner&) = delete;
    Owner& operator=(const Owner&) = delete;
};
```

### 2. C++14 相比 C++11 补充了什么？

**答案：**

泛型 lambda、lambda 初始化捕获、普通函数返回类型推导、`decltype(auto)`、变量模板、二进制字面量、数字分隔符、`std::make_unique` 与 `[[deprecated]]`。

`constexpr` 函数体允许更多语句，例如局部变量、循环与分支，但仍受常量表达式规则约束。聚合初始化早已存在；C++14 的相关变化是放宽聚合类型条件，允许带默认成员初始化器的类仍满足聚合要求。

```cpp
auto square = [](auto x) { return x * x; };
auto add(int a, int b) { return a + b; }
template<class T> constexpr T pi = T(3.14159265358979);
int mask = 0b1010;
int count = 1'000'000;
auto value = std::make_unique<int>(42);
auto callback = [p = std::move(value)] { return *p; };
```

最后一个闭包拥有该资源，通常只能移动，不能复制。

### 3. C++17 的常见面试特性有哪些？

**答案：**

结构化绑定、`if`／`switch` 初始化语句、`if constexpr`、折叠表达式、类模板实参推导、内联变量，以及 `optional`、`variant`、`any`、`string_view`、`filesystem` 和 `scoped_lock`。

```cpp
if (auto it = table.find(key); it != table.end()) {
    use(it->second);
}
auto [id, score] = std::make_pair(1, 2.0);
std::pair pair(1, 2.0); // 类模板实参推导
```

- `optional<T>` 表达可能没有值，不负责承载任意错误详情。
- `variant<A, B>` 保存候选类型中的一个，通常配合 `visit` 访问；某些异常路径下可能无值。
- `if constexpr` 在模板实例化时可舍弃未选中的分支，但不代表该分支可以随意包含语法错误；非模板上下文仍有类型检查。
- `std::array` 属于 C++11，不能归为 C++17 首次引入。

### 4. C++20 的 Concepts、Modules、Ranges 等解决什么问题？

**答案：**

| 特性 | 主要用途 | 边界 |
| --- | --- | --- |
| Concepts／`requires` | 约束模板参数与操作 | 约束表达式成立，不自动证明业务语义正确 |
| Modules | 组织接口、隔离实现、减少文本包含依赖 | 工具链支持与项目迁移方式需具体评估 |
| Coroutines | 通过 `co_await`／`co_yield`／`co_return` 表达挂起与恢复 | 不自带任务调度器，详见第 61 题 |
| Ranges | 统一范围算法与视图，可组合管道操作 | 许多视图延迟执行，须注意底层范围生命周期 |
| `std::format` | 类型安全、可扩展的格式化接口 | 不保证所有场景都快于其他格式化方案 |
| `<=>` | 表达三路比较，支持默认化比较 | 比较类别可能是强序、弱序或偏序；默认化有条件 |
| `std::span` | 连续序列的非拥有视图 | 不管理底层存储 |
| `std::jthread` | 自动收尾的线程封装与协作式停止 | 停止请求需要工作代码配合 |

```cpp
template<class T>
concept Addable = requires(T a, T b) { a + b; };

template<Addable T>
auto add(T a, T b) { return a + b; }
```

### 5. `auto`、`auto&`、`auto&&` 与 `decltype(auto)` 如何推导？

**答案：**

普通按值 `auto` 接近模板按值参数推导：忽略初始化表达式的引用属性和顶层 cv 限定，数组、函数还可能退化。它不会移除指针所指类型的底层 `const`。

```cpp
const int x = 1;
auto a = x;                // int
auto& b = x;               // const int&
auto&& c = x;              // const int&，引用折叠
auto&& d = 1;              // int&&，但具名表达式 d 是左值
const int* source = &x;
auto p = source;           // const int*
decltype(auto) e = x;      // const int
decltype(auto) f = (x);    // const int&
```

`decltype` 对不加括号的名字有特殊规则；对一般表达式根据值类别产生 `T`、`T&` 或 `T&&`。`decltype(auto)` 采用这些规则，不能简单理解为“总保留引用”。花括号初始化另有规则，例如 `auto xs = {1, 2};` 推导为 `initializer_list<int>`。

### 6. `constexpr`、`const` 与 `static_assert` 有什么区别？

**答案：**

`const` 表达不可通过该访问路径修改，初始化值可以在运行时获得。`constexpr` 变量要求常量表达式初始化；`constexpr` 函数具备参与常量求值的能力，但普通调用仍可能在运行时执行。

`static_assert` 在翻译阶段检查常量条件，适合验证类型属性、布局要求和模板约束。C++20 的 `consteval` 声明立即函数，要求其相应调用产生常量表达式；`constinit` 约束静态／线程存储期变量的初始化，不意味着变量只读。

### 7. lambda 如何捕获？有哪些生命周期陷阱？

**答案：**

lambda 产生闭包对象，捕获通常对应其状态。`[x]` 按值保存，`[&x]` 引用外部对象，`[=]`／`[&]` 是默认捕获规则；C++14 初始化捕获可移动资源进去。

- 引用捕获不会延长被引用对象的生命周期，异步回调尤其要检查。
- 值捕获指针只复制地址，不延长指向对象的生命周期。
- `[this]` 保存的是 `this` 指针；C++17 的 `[*this]` 才是复制对象。`[=]` 也不能据此理解为复制整个当前对象。
- 值捕获默认不能在调用运算符中修改该副本；`mutable` 可放开这一限制，但不自动修改外部原变量。
- 无捕获 lambda 可在满足签名条件时转为函数指针；有捕获闭包可由 `auto`、模板或合适的包装器持有。

### 8. 四种显式类型转换如何选择？

**答案：**

| 写法 | 用途 | 风险／失败方式 |
| --- | --- | --- |
| `static_cast` | 数值转换、明确合法的类型转换、继承向上转换等 | 向下转换不检查实际对象类型 |
| `dynamic_cast` | 多态对象的向下／交叉转换 | 指针失败返回 `nullptr`；引用失败抛 `std::bad_cast` |
| `const_cast` | 调整指针／引用所指类型的 cv 限定 | 修改原本就为 const 的对象是未定义行为 |
| `reinterpret_cast` | 特定底层表示和指针转换 | 不保证可安全解引用，不解除别名、对齐与生命周期限制 |

检查动态类型的 `dynamic_cast` 通常要求源类型为多态类型；简单向上转换另当别论。能用类型安全接口表达的操作，不应通过底层强转掩盖所有权或布局问题。

### 9. `static` 的几种用法及线程安全边界是什么？

**答案：**

- 局部静态对象：静态存储期；需要动态初始化时通常在首次经过声明处初始化。C++11 保证并发首次初始化的同步，后续读写仍需单独同步。
- 命名空间作用域的静态函数／变量：具有内部链接，限制在当前翻译单元。
- 静态数据成员：属于类，所有对象共享，不占每个实例的成员空间；C++17 可用 `inline static` 在类内定义。
- 静态成员函数：无 `this`，不能声明为虚函数或带成员函数 cv 限定；仍可通过显式传入的对象访问其成员。

不要把“初始化线程安全”扩大为“此对象的所有操作线程安全”。

### 10. 顶层 `const`、底层 `const` 与 const 成员函数如何区分？

**答案：**

```cpp
const int* p = nullptr;       // 指向 const int，p 可改指向
int value = 1;
int* const q = &value;        // q 本身不可改指向，可通过 q 修改 value
const int* const r = &value;  // 两层限制都有
```

const 成员函数限制通过 `this` 修改非 `mutable` 成员，可被 const 对象调用；这不等于深度不可变，也不等于线程安全。`mutable` 常用于缓存或锁，但缓存并发访问仍需同步。

`const T&` 可避免复制，某些直接绑定会延长临时对象寿命；通过返回值或参数再传递引用，不会普遍继续延长寿命。

### 11. 引用与指针有什么区别？

**答案：**

引用必须绑定对象或函数，绑定后不能重新绑定；指针可以表示空值、改变指向并在合法数组范围内进行算术。给引用赋值是在修改被引用对象。

`sizeof(ref)` 得到被引用类型的大小，`sizeof(ptr)` 得到该指针类型的大小。语言没有可正常使用的“空引用”，但引用仍可能悬垂，不能仅因采用引用接口就省略生命周期分析。

小型值类型可按值传递，大对象只读输入可用 const 引用；可选对象适合指针或明确的可选值接口。

## 二、源码处理与链接

### 12. C++ 源码到程序经历什么阶段？与解释执行如何比较？

**答案：**

常见工具链可概括为四个阶段，实际工具可以合并步骤而不落盘中间文件：

1. 预处理：展开头文件、宏和条件指令。
2. 翻译与优化：分析语义，将代码转换为目标指令表示，常以汇编文本说明这一阶段。
3. 汇编：产生目标文件，例如 `.o` 或 `.obj`。
4. 链接：解析符号与重定位，整合目标文件和库，形成程序或库。

不能把语言机械划分为“一次直接变成机器码”和“逐行解释”。Python、Lua 常先生成字节码，JavaScript 常结合解释器和 JIT，C++ 也存在解释实现。执行效率和跨平台能力取决于实现、部署方式和工作负载。

### 13. 静态链接与动态链接有哪些取舍？

**答案：**

静态链接把需要的库目标代码纳入产物；部署依赖通常更少，但可能增大体积，更新库一般需要重新链接并分发程序。

动态链接依赖 `.dll`／`.so` 等共享库，由加载器在启动时或显式加载时处理。它利于共享代码页和独立分发，但要管理版本、搜索路径与 ABI 兼容性。

不能保证静态方案一定启动更快，也不能把动态链接等同于自动热更新：替换正在使用的代码还涉及活跃调用、对象布局、状态迁移和平台约束。

### 14. `extern "C"` 如何支持 C 与 C++ 互操作？

**答案：**

它指定 C 语言链接，影响符号与函数类型等链接约定；不是让一段 C++ 代码自动具备 C 语法。跨语言接口通常暴露普通函数和不透明句柄，由 C++ 包装层管理类与资源。

```cpp
#ifdef __cplusplus
extern "C" {
#endif

int library_init(void);
void library_shutdown(void);

#ifdef __cplusplus
}
#endif
```

跨 DLL／语言边界还应约定调用约定、数据布局、异常处理与内存释放方；不要让 C++ 异常直接越过不支持它的 C 调用边界。

## 三、内存与对象布局

### 15. 如何理解栈、堆、BSS、Data 与 Text？

**答案：**

这些是常见平台的实现模型，不是 C++ 规定的固定高低地址排列。语言层面更应区分自动、静态、线程和动态存储期。

| 区域 | 常见内容 | 注意 |
| --- | --- | --- |
| 栈 | 调用上下文、部分局部变量 | 值也可能在寄存器中或被优化掉 |
| 堆／动态分配区 | 动态存储期对象的存储 | 可由 RAII、分配器管理，不等于只能手动释放 |
| BSS | 常见的零初始化静态存储 | 显式初始化为零的对象也可能放入 |
| Data | 可写的已初始化静态数据 | 只读常量可能位于其他段 |
| Text／只读数据区域 | 指令及相关只读内容 | 虚表位置取决于平台、重定位与链接策略 |

共享库、内存映射、ASLR 与多线程栈都会改变地址空间布局。

### 16. 内存对齐为何存在？是否必然减少一半访存？

**答案：**

对象地址需满足其类型的对齐要求，成员间和对象尾部可能有填充。常见 ABI 下 `struct A { char c; int i; };` 在 `int` 大小和对齐均为 4 时通常占 8 字节；不是所有平台的固定答案。

规则基于 `alignof(T)`，不是简单按 `sizeof(T)` 对齐。类型也可通过 `alignas` 要求更强对齐；`#pragma pack` 属于实现扩展。

对齐有助于满足指令要求并避免跨缓存行／跨页访问，但现代 CPU 不统一按“一个机器字一次总线访问”处理。未对齐访问的代价取决于架构、指令、缓存位置与内存类型：某些情况开销很小，某些情况会拆分或异常。不能断言所有 ARM／MIPS 都不支持，也不能断言 x86 总需要两次访问或恰好慢一倍。

### 17. 指针、空类与含虚函数对象的大小如何判断？

**答案：**

常见 32 位／64 位 ABI 下普通对象指针分别为 4／8 字节，但这不是所有 C++ 实现的通用保证；函数指针与成员指针也不能直接套用相同大小。

完整空类对象大小非零，通常为 1，以支持对象身份和数组元素寻址。空基类优化可能消除空基类子对象的额外空间；C++20 `[[no_unique_address]]` 可用于允许某些成员布局重叠。

含虚函数对象常包含虚表指针，但对象大小还受基类、成员、填充、虚继承和 ABI 影响，不能统一用“8 字节加成员大小”计算。静态数据成员不计入单个对象大小。

### 18. `malloc/free` 与 `new/delete` 有什么区别？

**答案：**

| 维度 | `malloc`／`free` | `new`／`delete` 表达式 |
| --- | --- | --- |
| 职责 | 分配／释放原始存储 | 获取存储并初始化对象／销毁对象并释放存储 |
| 接口 | 字节数，返回 `void*` | 按类型工作，返回对应指针 |
| 构造与析构 | 不调用用户定义构造／析构 | 按对象类型执行初始化和析构 |
| 失败 | `malloc` 返回空指针 | 普通抛异常形式通常抛 `std::bad_alloc`；有 nothrow 形式 |
| 配对 | `malloc` ↔ `free` | `new` ↔ `delete`；`new[]` ↔ `delete[]` |

`operator new` 是存储分配函数，与完整 `new` 表达式不同；可为类型或全局提供相应重载。现代对象生命周期规则还包括部分隐式对象创建情形，不能把 `malloc` 等同于任意类型构造。

业务代码优先使用标准容器与智能指针，避免混用分配／释放家族。

### 19. 栈上缓冲区与 `alloca` 有什么风险？

**答案：**

固定数组如 `char buffer[1024];` 具有自动存储期。`alloca` 是平台扩展，通常从当前函数栈帧取得动态大小存储，函数返回时回收；它不属于标准 C++。

栈空间有限且大小可配置，不能依赖固定“几 MB”数值。避免未经约束的大输入、递归叠加和循环中反复 `alloca`；不要返回局部缓冲区地址。可变大小数据通常选择 `vector` 等拥有型容器。

### 20. 内存泄漏、悬垂指针和重复释放如何定位？

**答案：**

先区分“失去所有者而未释放”和“缓存仍持有资源”，以及分配器保留空闲内存造成的驻留量不下降。重复业务进入／退出后，观察存活分配、所有权链与释放路径。

常见问题包括裸资源的异常路径遗漏、`shared_ptr` 环、错误的删除方式、返回局部地址以及容器失效后继续使用旧指针。修复应明确唯一或共享所有者，并用 RAII 覆盖提前返回与异常路径。

工具可包括 Visual Studio 内存诊断、AddressSanitizer／LeakSanitizer、Valgrind 等，适用平台和能力不同。通过无虚析构的普通基类指针删除派生对象通常是未定义行为，不能仅描述为“少调用一次析构”。

### 21. placement new 与内存池如何管理对象生命周期？

**答案：**

标准 placement new 形式 `new (ptr) T(args...)` 在已有存储中初始化对象，不另外获取该对象的存储。调用者保证空间、对齐与生命周期合法，并负责销毁对象以及按原来源回收存储。

```cpp
#include <new>
struct Widget {
    explicit Widget(int n) : value(n) {}
    int value;
};

alignas(Widget) unsigned char buffer[sizeof(Widget)];
Widget* object = new (buffer) Widget(42);
object->~Widget(); // buffer 为自动存储，不能 delete object
```

内存池批量取得存储再分块复用；对象池还要处理对象构造、重置、归还与句柄有效性。收益是减少分配频率与碎片，代价是峰值内存保留、对齐、并发与生命周期复杂度；placement new 本身不等于内存池。

## 四、继承与多态

### 22. 静态多态与动态多态有什么区别？

**答案：**

重载、模板和 CRTP 等可根据静态类型选择实现；虚函数则支持通过基类指针／引用，根据对象当前的动态类型分派。

静态方案便于优化，但可能增加实例化代码和接口耦合；动态方案便于异构集合与扩展。把派生对象按值复制到基类会发生对象切片，不能保持完整派生行为。

### 23. vptr 与 vtable 的工作方式是什么？

**答案：**

常见 ABI 在多态对象内放置虚表指针，经虚表定位函数入口。多个同类型对象通常共享相应表结构，表并非每个对象复制一份。

但 C++ 只规定虚调用的语义，不规定指针一定在偏移 0、不规定表必在某个数据段，也不规定每个类恰好一张表。虚表组可含主表、次表、类型信息与偏移数据；“类数就是虚表数”不是通用计算公式。

面试应先描述动态分派，再说明所讨论的 ABI。参考：[Itanium C++ ABI：虚表布局](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#vtable)。

### 24. 多继承为何可能改变基类指针的地址？

**答案：**

派生对象包含多个基类子对象。转换到某个基类时，指针可能调整到该子对象的位置；多态基类子对象可能使用不同的虚表入口。

虚调用的适配入口（thunk）可调整 `this`，让目标实现获得正确的对象视图。通过具有虚析构函数的基类指针删除时，也需完成正确的析构和释放定位。

基类排列、主基类选择、表数量和指针调整细节依 ABI 而定；不能硬编码“每多一个基类固定多 8 字节”。参考：[Itanium C++ ABI：对象布局](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#class-types)。

### 25. 虚继承如何解决菱形继承？构造顺序是什么？

**答案：**

若 `B`、`C` 普通继承 `A`，`D : B, C` 含两份 `A` 子对象；把中间两条边改为虚继承后，最派生对象共享一份虚基类 `A`。

```cpp
struct A { int value = 0; };
struct B : virtual A {};
struct C : virtual A {};
struct D : B, C {};
```

最派生类负责初始化虚基类；先按规定遍历顺序初始化虚基类，再按声明顺序初始化直接基类，之后是成员，最后执行构造函数体；析构反向进行。

实现可能通过 MSVC 风格的 vbptr／vbtable 或虚表中的偏移数据定位虚基类，不能混为统一布局。共享状态不一定消除所有名称或最终重写者二义性，设计上仍需评估组合是否更清楚。

### 26. 构造与析构期间调用虚函数会怎样？

**答案：**

在对象构造／析构过程中，对该对象的虚调用按当前构造／析构类这一层的最终重写者分派，不会调用尚未构造或已析构的更派生层。常见实现会相应调整虚表状态。

这不是“所有虚调用机制都被关闭”。应避免在基类构造／析构中依赖派生类扩展行为，尤其不要虚调用纯虚接口。把需要扩展的流程安排在构造完成后的显式阶段；NVI 也不会自动改变构造期间的分派规则。

### 27. 哪些函数可以是虚函数？纯虚函数能有定义吗？

**答案：**

虚函数必须是符合要求的非静态成员函数。构造函数、静态成员函数、自由函数和成员函数模板不能声明为虚函数；**虚函数可以声明为 inline**，声明形式与最终是否内联是两回事。

纯虚函数用 `= 0` 声明，使未提供完整最终重写者的类保持抽象；它仍可在类外提供定义。纯虚析构函数也需要定义，因为派生对象析构会经过它。

```cpp
struct Base {
    virtual ~Base() = 0;
    virtual void run() = 0;
};
inline Base::~Base() = default;

struct Derived final : Base {
    void run() override {}
};
```

允许通过基类接口删除对象时，通常应提供公开虚析构；不允许该操作的基类可采用受保护非虚析构等设计。参考：[C++ 草案：虚函数](https://eel.is/c++draft/class.virtual)。

### 28. 大项目使用虚函数有什么成本与替代方案？

**答案：**

成本可能包括间接分派、对象布局开销、优化机会受限和 ABI 维护。若能确定调用目标，去虚拟化仍可产生直接调用甚至内联；性能影响应结合热点和数据布局判断。

公开二进制接口中随意调整虚函数或类布局可能破坏兼容性；跨模块更应明确 ABI 与版本策略。

可选方案包括模板／CRTP、函数对象、`variant`＋`visit` 或类型擦除包装器。它们各有代码体积、扩展能力与分派成本，`std::function` 也不保证可内联。游戏热路径先测量，接口层与扩展点可继续使用合适的虚接口。

## 五、所有权与异常安全

### 29. RAII 管理什么？与垃圾回收有何区别？

**答案：**

RAII 把资源的持有与释放绑定到对象生命周期：构造或明确的接管操作建立所有权，析构释放。它适用于内存、锁、文件、socket、图形资源等。

| 类型 | 资源／析构行为 |
| --- | --- |
| `unique_ptr` | 销毁所拥有对象，调用对应删除器 |
| `shared_ptr` | 减少强引用计数，最后一个强所有者释放所管理对象 |
| `lock_guard`／`scoped_lock` | 解锁所管理的互斥量 |
| `unique_lock` | 若仍拥有锁则解锁 |
| `fstream` | 关闭文件相关资源 |

正常离开作用域及异常栈展开会销毁已完成构造的自动对象；强制终止、崩溃等不保证执行清理。对象自身构造失败时，其已构造的成员／基类会销毁，但不会调用该完整对象的析构函数。

GC 主要依据可达性回收托管内存；RAII 强调所有权结束时的清理。两者不是语言能力上的绝对互斥，也不能说 RAII 一定零开销或全部释放时刻在静态阶段确定。堆上的 RAII 对象同样有意义，前提是它自身受可靠所有者管理。

### 30. 三种智能指针如何选择？如何打破循环引用？

**答案：**

- `unique_ptr<T>`：独占所有权，可移动不可复制，通常作为默认选择；自定义删除器可能改变对象大小。
- `shared_ptr<T>`：多个所有者共享控制块，最后一个强所有者释放所管理资源；典型实现有对象指针与控制块指针，但布局不是固定标准。
- `weak_ptr<T>`：观察共享对象，不增加强引用计数；使用 `lock()` 一次性获取可用的强引用，失败得到空指针。

`shared_ptr` 环会让强引用计数无法归零，应把非拥有方向改为 `weak_ptr`。弱引用仍可能保留控制块；`make_shared` 常将对象与控制块共同分配，需区分对象析构与整块存储回收。

优先用 `make_unique`（C++14）和 `make_shared`（C++11）。不要从同一个裸指针独立构造两份拥有型 `shared_ptr`；它们不会自动合并控制块。

### 31. `shared_ptr` 的线程安全保证覆盖哪些层？

**答案：**

共享同一控制块的**不同** `shared_ptr` 实例，可以分别修改而不破坏引用计数管理。同一个 `shared_ptr` 变量若被并发读写或写写，需要同步；C++20 可使用 `std::atomic<std::shared_ptr<T>>` 等合适接口。

被管理对象的字段完全是另一层问题：引用计数安全不代表 `ptr->value++` 安全。对象销毁发生在哪个线程、析构是否需要特定线程，也应由资源设计明确。

### 32. 浅拷贝、深拷贝与默认拷贝的关系是什么？

**答案：**

默认拷贝按成员执行拷贝：裸指针成员复制地址，但 `string`／`vector` 会执行各自的值语义拷贝，`shared_ptr` 会共享所有权，`unique_ptr` 会使相应默认拷贝不可用。因此不能把所有默认拷贝一律称为浅拷贝。

拥有裸资源的类若复制地址后让两个对象都负责释放，就可能重复释放。解决方案是明确禁止复制、实现深拷贝，或用已有 RAII 成员表达所需语义。深拷贝也要定义共享子对象与循环结构的处理方式。

### 33. 三法则、五法则与零法则如何应用？

**答案：**

三法则提示拥有原始资源的类应一起审视析构、拷贝构造和拷贝赋值；五法则再加入移动构造、移动赋值。它们要求一致的所有权设计，不要求所有类机械手写五个函数。

用户声明析构／拷贝等特殊成员会影响隐式移动函数生成；声明移动操作也会影响隐式拷贝。`= default` 后仍可能因某个成员不可操作而被定义为删除。

零法则优先把资源交给 `vector`、`string`、智能指针等成员，使业务类不用手写资源清理。默认结果仍取决于成员语义：例如含 `unique_ptr` 的类通常可移动、不可复制。

### 34. 异常安全等级与 `noexcept` 应如何回答？

**答案：**

| 等级 | 承诺 |
| --- | --- |
| 不抛保证 | 操作不以异常退出 |
| 强保证 | 失败时可观察状态保持不变 |
| 基本保证 | 失败后维持不变量且不泄漏资源 |
| 无保证 | 失败后的资源与状态无法依赖 |

异常传播通常伴随栈展开，RAII 负责释放已构造对象的资源。异常逃出 `noexcept` 函数会调用 `std::terminate`；此前是否展开部分栈由实现决定，不应统一断言完全跳过展开。

析构函数的隐式异常说明通常是不抛，但受基类与成员析构的异常说明影响。不要从清理路径向外抛异常，尤其不要在已有异常展开时再次逃出异常。`noexcept` 应建立在实现确实不抛的前提上。

参考：[C++ 草案：异常终止](https://eel.is/c++draft/except.terminate)。

## 六、值类别与移动语义

### 35. 左值、纯右值、将亡值与右值引用怎么区分？

**答案：**

值类别描述表达式，不能仅根据出现在赋值号哪侧或是否“看起来临时”判断。

- 左值（lvalue）：标识对象或函数，例如具名变量表达式 `x`。
- 将亡值（xvalue）：标识资源可被复用的对象，例如普通对象的 `std::move(x)`。
- 纯右值（prvalue）：用于初始化对象或计算操作数值，例如 `42`、返回非引用类型的普通函数调用。
- 广义左值（glvalue）包含 lvalue 和 xvalue；右值（rvalue）包含 prvalue 和 xvalue。

```cpp
int&& reference = 42;
// reference 的声明类型是 int&&，表达式 reference 却是左值
auto&& again = reference; // int&
```

右值引用是类型属性，值类别是表达式属性；const 左值不能赋值，位域等左值也不能按普通对象方式取地址。

### 36. `i++` 与 `++i` 有什么区别？

**答案：**

对内建整数，前置自增修改对象并产生指向该对象的左值，后置自增产生旧值的纯右值，再完成自增。自定义运算符的返回类型由实现决定，通常遵循这一约定。

不需要旧值时，迭代器等类型优先用前置形式，可避免不必要的副本；优化后的内建整数两种写法往往没有差别，不能保证后置形式必然多一次实际内存操作。

### 37. `std::move` 是否执行移动？移动后的对象还能用吗？

**答案：**

`std::move` 本质上进行类型转换，产生适合选择移动重载的表达式；真正转移资源的是随后选中的构造／赋值等操作。

```cpp
std::string source = "hello";
std::string target = std::move(source); // 选择 string 的移动构造
source = "reuse";                     // 可重新赋值

const std::string fixed = "world";
std::string copy = std::move(fixed);   // 通常选拷贝，move 不移除 const
```

没有可用移动重载时可能选择拷贝；若匹配到显式删除的移动重载，则不能直接依赖拷贝兜底。标准库对象移动后一般处于有效但未指定状态，除非该类型另有保证；不能普遍假定为空。用户类型应自行定义移动后契约。

### 38. 转发引用、引用折叠与完美转发如何配合？

**答案：**

在适用的参数推导情境下，未加 cv 限定的模板参数 `T&&` 是转发引用；并非任何 `T&&` 都是，例如固定类型的 `Widget&&` 和 `const T&&`。

| 组合 | 折叠结果 |
| --- | --- |
| `&` 与 `&` | `&` |
| `&` 与 `&&` | `&` |
| `&&` 与 `&` | `&` |
| `&&` 与 `&&` | `&&` |

```cpp
template<class T>
void relay(T&& value) {
    consume(std::forward<T>(value));
}
```

传入 `U` 左值时，`T` 推导为 `U&`，参数折叠为 `U&`；传入 `U` 右值时，`T` 通常推导为 `U`，参数类型为 `U&&`。具名参数 `value` 本身是左值，`forward<T>` 按原推导结果恢复相应值类别。不能误记成“右值传入时 T 推导为 U&&”。

### 39. RVO、NRVO 与 `return std::move(local)` 有什么关系？

**答案：**

C++17 起，同类型纯右值直接初始化返回对象的常见场景，不需要先生成一个中间对象再拷贝／移动；但析构函数等仍须满足相应要求。返回合适的具名局部对象时，可进行 NRVO，这是可选优化。

```cpp
struct Widget {};
Widget direct() { return Widget{}; }
Widget named() {
    Widget result;
    return result;            // NRVO 候选；未消除时按相关规则考虑移动
}
Widget discouraged() {
    Widget result;
    return std::move(result); // 不再是 NRVO 所要求的直接返回名字
}
```

返回函数参数不满足 NRVO 的局部对象条件；多分支返回不同局部变量会影响实现能否优化，但不能笼统断言所有这类函数或异常分支都绝无优化。不要为了返回局部对象而习惯性添加 `std::move`。

参考：[C++ 草案：拷贝消除](https://eel.is/c++draft/class.copy.elision)。

### 40. 为什么移动构造的 `noexcept` 会影响 vector 扩容？

**答案：**

扩容需要在新存储中构造已有元素。若移动可能抛异常，旧元素可能已被改变，回滚更困难；当可拷贝时，容器常选择拷贝来维持异常保证。

若类型只能移动，容器并不会凭空获得拷贝能力；移动抛异常时，某些情况下强保证不再适用。不能概括为“没有 noexcept 就一定拷贝”。

资源转移确实不抛时，应表达 `noexcept`；成员操作可能抛时，可采用条件异常说明。`std::is_nothrow_move_constructible_v<T>`（C++17）可检查属性，但不是给任意操作加无条件承诺的理由。

## 七、容器与视图

### 41. STL 包含什么？常见容器如何选择？

**答案：**

传统 STL 六组件为容器、算法、迭代器、函数对象、适配器和分配器。重载 `operator()` 的对象可作为算法策略；整个 C++ 标准库的范围比传统 STL 更广。

| 容器 | 典型特点／复杂度 | 适用场景 |
| --- | --- | --- |
| `array<T, N>` | 固定长度连续存储，随机访问 O(1) | 大小已知的值语义数组 |
| `vector<T>` | 连续存储，尾插摊还 O(1)，中间插删 O(n) | 默认动态序列；`vector<bool>` 是特殊实现 |
| `deque<T>` | 随机访问 O(1)，两端插入 O(1)，不保证整体连续 | 双端增长的序列 |
| `list<T>` | 双向链表，已知位置插删 O(1)，查找 O(n) | 需要稳定节点及频繁已知位置操作 |
| `forward_list<T>` | 单向链表，常在前驱位置之后操作 | 更精简的节点链 |
| `map`／`set` | 有序关联容器，查找和常见插删 O(log n) | 有序遍历、范围查询；常用平衡树实现 |
| `unordered_map`／`unordered_set` | 哈希关联容器，查找平均 O(1)、最坏 O(n) | 无排序要求的键查询 |
| `stack`／`queue`／`priority_queue` | 容器适配器，限制访问方式 | 后进先出、先进先出、优先级处理 |

复杂度不等于真实耗时，连续内存的局部性可能胜过理论操作次数更少的节点结构。

### 42. vector 如何扩容和缩容？

**答案：**

`size()` 是元素数，`capacity()` 是当前存储可容纳的元素数。超出容量时，vector 获取更大存储，移动或拷贝构造旧元素，再释放旧存储；具体增长倍率不是标准保证，不能固定记成某个工具链永远 2 倍或 1.5 倍。

- `reserve(n)` 请求容量，不改变 size；超过当前容量时重分配。
- `clear()`、`pop_back()` 销毁相应元素，但不会自动降低 capacity。
- `shrink_to_fit()` 是不具强制性的缩容请求，若发生重分配则旧引用等失效。
- 对默认分配器的 vector，可与空临时 vector 交换以交还原存储；自定义分配器需满足交换要求，且交还分配器不保证操作系统驻留内存立即下降。

事先合理 reserve 可降低重复分配，不能每次插入前都只 reserve 当前所需的一点空间而破坏摊还收益。

### 43. 哈希表何时 rehash？默认负载因子是 0.75 吗？

**答案：**

`load_factor()` 是元素数除以桶数；`max_load_factor()` 规定负载上限策略。标准无序关联容器默认最大负载因子为 **1.0**，不能把其他语言容器常见的 0.75 套过来。

插入需要维持相应桶数条件；`reserve(n)` 按元素容量请求桶数，`rehash(n)` 按桶数请求。重哈希会重新组织桶和迭代顺序，令迭代器失效，但不使仍存在元素的指针／引用失效。

哈希函数与等价关系必须一致：相等键必须具有相同哈希。碰撞、负载与分配开销都影响实际查询效率。

参考：[C++ 草案：无序关联容器要求](https://eel.is/c++draft/unord.req)。

### 44. 容器操作后哪些迭代器、指针和引用会失效？

**答案：**

必须区分迭代器、元素引用与尾后迭代器；下表讨论普通插删和重分配，交换／移动赋值等另有规则。

| 容器与操作 | 失效规则 |
| --- | --- |
| vector 发生重分配 | 全部元素迭代器、指针、引用及旧 `end()` 失效 |
| vector 尾插未重分配 | 旧 `end()` 失效，原有元素引用等保持有效 |
| vector 中间插入未重分配 | 插入点及之后的迭代器、指针、引用失效 |
| vector erase | 删除位置及之后的迭代器、指针、引用失效，包括旧 `end()` |
| deque 两端插入 | 所有迭代器失效，已有元素的引用／指针仍有效 |
| deque 中间插入 | 所有迭代器及元素引用／指针失效 |
| deque 仅删除开头且不含最后元素 | 仅被删元素的迭代器、引用／指针失效 |
| deque 删除尾部 | 被删元素的迭代器、引用／指针及旧 `end()` 失效 |
| deque 删除中间元素 | 所有迭代器及元素引用／指针失效 |
| list／map／set 插入 | 原有元素的迭代器、引用／指针有效 |
| list／map／set 删除 | 仅被删元素的迭代器、引用／指针失效 |
| unordered 容器 rehash | 所有迭代器失效，已有元素引用／指针有效 |
| unordered 容器 erase | 仅被删元素的迭代器、引用／指针失效 |

```cpp
for (auto it = values.begin(); it != values.end(); ) {
    if (*it < 0) it = values.erase(it);
    else ++it;
}
// vector 的 erase-remove 写法
values.erase(std::remove_if(values.begin(), values.end(),
                           [](int x) { return x < 0; }),
             values.end());
```

`remove_if` 重新排列保留元素并返回逻辑尾部，不直接改变容器 size；C++20 还提供适用容器的 `std::erase_if`。参考：[C++ 草案：deque 插删规则](https://eel.is/c++draft/deque.modifiers)。

### 45. `emplace_back` 一定优于 `push_back` 吗？

**答案：**

`push_back` 接收已存在的元素值并复制／移动进容器；`emplace_back` 转发构造参数，在目标位置构造元素，某些场景能省去临时对象。

```cpp
std::vector<std::pair<int, std::string>> values;
values.push_back(std::make_pair(1, "hello"));
values.emplace_back(1, "hello");

struct Point {
    Point(int x_, int y_) : x(x_), y(y_) {}
    int x, y;
};
std::vector<Point> points;
points.emplace_back(10, 20);
```

若直接传已有对象，两者仍可能进行同样的拷贝／移动；扩容也仍需处理旧元素。emplace 使用直接初始化，可选中 `explicit` 构造函数，调用方更要注意参数语义。不要先 `new` 裸资源再把所有权寄托在后续容器构造上，优先先生成智能指针。

### 46. `string_view` 与 `span` 能否保存和返回？

**答案：**

`string_view`（C++17）是非拥有字符串视图；`span<T>`（C++20）是非拥有连续序列视图，支持静态或动态 extent。它们不会延长底层对象生命周期。

**可以**保存或返回视图，前提是底层数据持续有效且未被相关操作使地址失效；不能返回指向局部 string／vector 的视图。`string_view` 不保证以 `\0` 结尾，不能直接充当所有 C 字符串 API 的输入。

```cpp
int sum(std::span<const int> values) {
    int result = 0;
    for (int value : values) result += value;
    return result;
}
std::vector<int> values{1, 2, 3};
int array[] = {4, 5, 6};
// sum(values) 与 sum(array) 都读取现有存储，不复制整个容器
```

只读字符串／连续数组参数可分别使用视图；需要延长生命周期时，应传递或保存拥有型对象。视图构造不分配，不代表创建其来源临时 string 的过程也不分配。

## 八、模板与可调用对象

### 47. 全特化、偏特化与重载有什么区别？

**答案：**

全特化为特定模板实参组合提供定义；偏特化匹配一类参数模式，例如指针类型或固定的某个参数。类模板和变量模板可以偏特化，函数模板不能偏特化，通常使用重载、约束或辅助类模板实现。

```cpp
template<class T> struct Traits { static constexpr bool pointer = false; };
template<class T> struct Traits<T*> { static constexpr bool pointer = true; };
template<> struct Traits<void> { static constexpr bool pointer = false; };
```

模板选择规则与普通函数重载规则并不相同；接口行为只依赖少量条件时，`if constexpr` 或 Concepts 有时比复杂特化层次更清楚。

### 48. 可变参数模板与折叠表达式如何展开？

**答案：**

`template<class... Args>` 声明类型参数包；可通过递归调用、包展开或 C++17 折叠表达式处理。递归版本需要终止重载，空参数包也需明确支持策略。

```cpp
template<class... Args>
auto sum(Args... values) {
    return (0 + ... + values); // 二元左折叠，空包得到 0
}

template<class... Args>
void print_all(const Args&... values) {
    ((std::cout << values << ' '), ...);
}
```

`(values + ...)` 是一元右折叠，三个参数相当于 `a + (b + c)`；`(... + values)` 是一元左折叠，相当于 `(a + b) + c`。不要把左右结合方向写反；结合方式还可能影响浮点结果和重载行为。

变参转发用于 `make_unique`、`make_shared`、tuple 与 emplace 等接口。参考：[C++ 草案：折叠表达式](https://eel.is/c++draft/expr.prim.fold)。

### 49. 函数指针、函数对象与 `std::function` 有何取舍？

**答案：**

函数指针表达匹配签名的函数入口，本身不携带捕获状态；调用可能有间接分派成本，不能一律称为零开销。

具体函数对象／lambda 配合模板可保留静态类型，便于优化。`std::function<R(Args...)>` 使用类型擦除，可统一保存符合要求且可复制的可调用对象，可能存在间接调用与动态分配。

仅可移动的捕获闭包不能直接装进 C++11–20 的普通 `std::function`。热路径优先考虑保持具体类型；需要统一回调接口时，再权衡类型擦除的灵活性与成本。

## 九、多线程与协程

### 50. 进程与线程有什么区别？

**答案：**

进程是常见操作系统中的地址空间与资源隔离容器；同进程线程共享地址空间等资源，各自持有栈、寄存器状态和线程局部存储。进程间可通过管道、共享内存、Socket 等通信，线程间共享数据仍需同步。

进程隔离通常可限制崩溃影响，线程的非法访问通常会影响整个进程；共享资源与外部依赖仍可能传播故障。切换成本取决于内核、地址空间、缓存与调度策略，不是固定的线程／进程倍率。

### 51. `std::thread` 的创建、join、detach 与析构有什么陷阱？

**答案：**

```cpp
void worker(int id) { /* 处理任务 */ }
std::thread thread(worker, 42);
thread.join();
```

参数通常以衰减后的值保存，需要引用语义时显式使用 `std::ref`／`std::cref` 并保证来源存活。`join()` 等待线程完成，`detach()` 放弃通过该 thread 对象等待和管理它，不会停止线程。

析构时仍 `joinable()` 的 `std::thread` 会调用 `std::terminate`；线程已经执行完也可能仍 joinable。若中途异常跳过 join，应采用可靠的 RAII 包装；C++20 `jthread` 在相应析构情形下请求停止并 join，工作函数须配合停止协议。

线程入口未捕获的异常不会自动传回创建线程，应在线程内处理或通过 promise 等传递。

### 52. mutex 与几种 RAII 锁封装如何选择？

**答案：**

| 类型 | 用途 |
| --- | --- |
| `mutex` | 普通独占互斥 |
| `recursive_mutex` | 同线程递归加锁，需匹配释放次数 |
| `timed_mutex` | 支持限时尝试 |
| `shared_mutex`（C++17） | 共享读／独占写，适合合适的读多写少负载 |
| `lock_guard` | 简单作用域持锁，不支持手动解锁与移动 |
| `unique_lock` | 可移动、延迟加锁、手动解锁、配合条件变量 |
| `scoped_lock`（C++17） | 管理一个或多个锁，多锁获取采用死锁避免机制 |
| `shared_lock`（C++14） | 管理支持共享所有权的锁；可配合 `shared_timed_mutex` |

读写锁不保证一定更快或写线程不会饥饿；递归锁也不能替代明确的锁层级设计。

### 53. 死锁、活锁与饥饿如何避免和定位？

**答案：**

经典资源模型中的死锁条件包括互斥、占有且等待、不可剥夺和循环等待；实际排查重点是线程持有什么、等待什么，是否形成无法解除的依赖环。

统一锁顺序，避免持锁调用外部回调或等待另一任务；需要同时获取多个互斥量时使用 `std::lock`／`scoped_lock`。限时重试需定义退避与失败路径，否则可能转成活锁或饥饿。

死锁是无法前进的等待环，活锁是不断活动却不完成工作，饥饿是某参与者长期拿不到资源。可通过调试器线程栈、等待链、日志和时间线定位；不要把所有检测工具都当作通用死锁证明器。

### 54. 条件变量为何必须检查谓词？

**答案：**

通知不保存业务条件，且等待可能虚假唤醒。共享状态应由同一互斥协议保护；`wait(lock, predicate)` 等价于反复检查条件，不满足时释放锁并等待，被唤醒后重新获取锁。

```cpp
std::queue<int> queue;
std::mutex mutex;
std::condition_variable changed;
bool stopped = false; // 读写都持有 mutex

void produce(int value) {
    {
        std::lock_guard<std::mutex> lock(mutex);
        queue.push(value);
    }
    changed.notify_one();
}

bool consume(int& value) {
    std::unique_lock<std::mutex> lock(mutex);
    changed.wait(lock, [] { return stopped || !queue.empty(); });
    if (queue.empty()) return false;
    value = queue.front();
    queue.pop();
    return true;
}

void stop() {
    {
        std::lock_guard<std::mutex> lock(mutex);
        stopped = true;
    }
    changed.notify_all();
}
```

停止前由调用方保证生产者不再提交任务。`condition_variable` 使用 `unique_lock<mutex>`，`condition_variable_any` 可使用其他满足要求的锁类型；也可显式 while 循环检查谓词，不必只认一个重载。信号量持有计数，语义与条件变量不同。

### 55. atomic、内存序与 volatile 的区别是什么？

**答案：**

原子操作对相应原子对象提供不可分割的访问，但多个原子操作组成的业务事务未必整体原子。`fetch_add` 是单个读改写操作，而先 load 再 store 不等价于原子自增。

- `relaxed`：提供原子性与该对象的修改顺序，不用于发布其他普通数据。
- `release`／`acquire`：当读取满足对应关系时，可建立同步与 happens-before；不是任意两次操作标上标签就自动配对。
- `seq_cst`：默认顺序，额外要求相应操作满足单一全序；实际性能开销依架构与操作而定。

```cpp
int payload = 0;
std::atomic<bool> ready{false};
// 单次发布示例，两侧分别在生产者和消费者中执行
// 生产者：
payload = 42;
ready.store(true, std::memory_order_release);
// 消费者：
// if (ready.load(std::memory_order_acquire)) use(payload);
```

此示例要求生产者在发布后不再无同步地修改 payload。C++ `volatile` 用于特定可观察访问语义，不提供线程同步或原子性；不要套用 C# 的 volatile 规则，也不要仅把它解释成“不缓存到寄存器”。

### 56. future、promise、async 与 packaged_task 如何协作？

**答案：**

`promise` 是手动设置值／异常的一端，`future` 是接收结果的一端；`packaged_task` 包装可调用任务并把执行结果或异常写入共享状态。`std::async` 负责按策略执行任务并返回 future。

```cpp
auto result = std::async(std::launch::async, [] { return 42; });
int value = result.get();
```

显式 async 策略异步执行；deferred 策略把执行推迟到相应等待／取值操作，默认策略可能选择其中之一。`future::get()` 通常只能取一次，保存的异常在 get 时重抛；多方读取结果可采用 `shared_future`。

普通 future 析构不等于自动等待所有任务。与 async 异步执行关联的共享状态在满足特定条件时释放可能阻塞；不能把这条行为推广到 promise 返回的 future。线程生命周期、任务取消与等待仍应有明确设计。

### 57. `thread_local` 是否意味着绝对线程安全？

**答案：**

线程局部变量为各线程提供独立实例，适合每线程随机状态、临时缓存或错误信息，减少直接共享。

但其指针可以逃逸到别的线程，对象内部也可能引用共享状态；线程退出会结束相关对象生命周期。线程池中线程会跨任务复用，因此 TLS 不等于任务局部变量，业务上下文应及时重置。

### 58. 数据竞争与伪共享有什么区别？用什么工具排查？

**答案：**

不同线程之间冲突访问同一内存位置、至少一个为写且存在非原子访问，又缺乏所需同步时，可能构成数据竞争，导致未定义行为。即使没有数据竞争，逻辑上的竞态和顺序错误仍可能存在。

伪共享则是线程修改不同变量，却因它们落在同一缓存一致性单元而反复争用缓存行，主要是性能问题。可调整布局、减少共享写或使用适当填充；缓存行大小不能在所有平台都固定为 64 字节，需考虑目标平台与 `hardware_destructive_interference_size` 等信息。

ThreadSanitizer／Helgrind 适合相关并发问题；ASan 主要定位越界、释放后使用等内存错误。工具结果应与复现步骤、调用栈和同步关系一起分析。

### 59. CAS、无锁与 ABA 的真正含义是什么？

**答案：**

CAS 在当前值符合预期时更新它，否则把实际值写回 expected；weak 形式允许伪失败，通常放入重试循环。

```cpp
std::atomic<int> counter{0};
int expected = 0;
bool success = counter.compare_exchange_strong(expected, 1);
```

无锁（lock-free）是进展保证：整体系统持续有操作取得进展，不等于源码没出现 mutex。原子类型也未必底层无锁，可查询相应属性；用原子实现的自旋锁仍是锁，且可能长期占用 CPU。

ABA 指值从 A 变 B 再变回 A，单纯相等比较无法识别中间变化。需根据算法结合版本标签与安全内存回收，例如 hazard pointers／epoch；它们解决的问题并不完全相同，延迟回收也不是所有逻辑 ABA 的万能解法。

### 60. 线程池与游戏任务系统设计要考虑什么？

**答案：**

线程池复用工作线程，从任务队列获取工作，减少反复创建线程的成本。基础组成是队列、互斥／等待机制、停止协议、工作线程，以及通过 packaged_task／future 等提供的结果通道。

需要明确队列容量和背压、异常传播、取消策略、关闭时排空还是丢弃任务、任务依赖与等待死锁。细粒度任务可配合任务窃取，但过小任务也可能被调度开销淹没。

CPU 密集型线程数以硬件与实际负载为参考，`hardware_concurrency()` 只是提示且可能为 0；还要给主线程和其他系统留余量。I/O 负载可结合异步接口，不能只靠增加线程数。渲染线程归属由引擎和图形 API 契约决定，不应统一断言提交只能在主线程。

### 61. 协程与线程、有栈与无栈协程有什么区别？

**答案：**

协程表达可挂起与恢复的执行过程，本身不规定操作系统线程调度或并行能力。多个协程可交错运行于一个线程，也可由运行时安排在多个线程；单线程仍可能有跨挂起点的逻辑竞态。

| 维度 | 有栈协程的典型实现 | C++20 无栈协程 |
| --- | --- | --- |
| 状态 | 保存独立调用栈与执行上下文 | 保存协程帧中的参数、局部状态和挂起点 |
| 挂起 | 可由运行时支持更深调用栈切换 | 在语言允许的协程挂起机制处进行 |
| 内存 | 栈空间与增长策略由库决定 | 帧可能动态分配，部分情形可消除分配 |
| 调度 | 库／运行时提供 | 由 awaiter、调用方及执行器等组织 |

对称／非对称描述恢复与让出控制的关系，与是否有栈是不同维度。不能给所有协程规定固定栈大小、寄存器切换成本或最大数量。

C++20 通过 promise 类型、协程句柄和 awaiter 协议提供机制，`co_await`、`co_yield`、`co_return` 不等于自带线程池。协程句柄及其帧需要正确销毁，引用捕获和参数生命周期要覆盖实际使用期。

优点是异步控制流更易表达；代价包括取消、调度、帧所有权和跨挂起点调试的复杂度，不能笼统称为零开销。Lua 的恢复／让出见 [Lua 专题](Lua高频题整理.md)，C# 状态机见 [C# 专题](CSharp高频题整理.md)。参考：[C++ 草案：协程定义](https://eel.is/c++draft/dcl.fct.def.coroutine)。

## 十、STL 高频补充

### 62. 怎样理解容器底层结构，而不把实现细节当标准？

**答案：**

vector 连续存储、deque 支持随机访问和两端操作、list 支持双向遍历，这些接口与复杂度保证比内部字段名字更重要。

常见实现中，vector 用三个指针或指针＋长度／容量管理存储，deque 用分块缓冲与索引表，list 用带哨兵的双向链表，map／set 用红黑树，unordered 容器用桶与节点。标准不要求它们都采用相同字段、树形或节点布局。

链表已知位置插删的链接操作可为 O(1)，定位仍可能 O(n)，还要支付分配和缓存未命中成本；vector 中间插删需移动后续元素，却有良好局部性。失效规则、扩容与复杂度对照见第 41–44 题。

### 63. map 和 unordered_map 如何选择？

**答案：**

| 维度 | map | unordered_map |
| --- | --- | --- |
| 查询 | O(log n) 次比较量级 | 平均 O(1)，最坏 O(n) |
| 顺序 | 按比较器有序 | 不保证业务顺序 |
| 区间查询 | 成员 lower_bound／upper_bound | 没有相应有序查询能力 |
| 键要求 | 比较器构成严格弱序 | 等价键必须给出相同哈希 |
| 成本 | 节点、比较、树访问 | 桶、节点、哈希与 rehash |

按键查询且不要求有序时可考虑 unordered_map；有范围查询或稳定键序需求时考虑 map。小数据也可用排序 vector，不能用“数据少必选 map”代替测量。字符串哈希／比较成本还取决于键长度。

`operator[]` 在键不存在时会插入元素；只查询可用 `find`，需要缺失时报错可用 `at`。比较器等价不必等于 `operator==`，map 也不强制必须有 `operator<`。

### 64. stack、queue 与 priority_queue 的复杂度和比较器如何记？

**答案：**

stack／queue 默认基于 deque，也可换满足所需接口的容器；vector 可承载 stack，但不满足 queue 所需的 pop_front。适配器隐藏部分操作，不是新发明一种底层布局。

priority_queue 默认 vector＋堆，`std::less<T>` 时最大元素在顶；`std::greater<T>` 常用于小顶堆。top 通常 O(1)，堆调整 O(log n)，底层 vector 扩容仍可能产生一次 O(n) 搬移；批量建堆可为 O(n)。

```cpp
std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;
minHeap.push(3);
minHeap.push(1);
int smallest = minHeap.top(); // 1
minHeap.pop();               // pop 不返回被删元素
```

取 top／front／pop 前先满足非空条件。优先队列不提供一般元素的任意更新／删除，可通过索引堆或懒删除等另行设计。

### 65. sort、stable_sort、partial_sort 与 nth_element 怎样选择？

**答案：**

| 需求 | 算法 | 关键性质 |
| --- | --- | --- |
| 全排序，不需稳定 | sort | O(n log n) 比较，不保证稳定 |
| 全排序，保留等价元素原顺序 | stable_sort | 稳定；额外空间不足时复杂度可能上升 |
| 前 k 个按序，其余不关心 | partial_sort | 典型比较量 O(n log k) |
| 找第 k 小或划分前 k 个 | nth_element | 普通重载平均线性比较，不把两侧完整排序 |

Introsort 是 sort 的常见实现，具体快排策略、小数组阈值及内部函数不是标准契约。`list` 不满足 sort 所需的随机访问迭代器，应使用自己的成员 sort。

比较器必须表达严格弱序，不能用 `a <= b`；浮点 NaN、会变化的排序字段也需明确规则。参考：[C++ 草案：排序算法](https://eel.is/c++draft/alg.sort)。

### 66. lower_bound 与 upper_bound 的边界和复杂度是什么？

**答案：**

升序默认比较下，lower_bound 找第一个“不小于目标”的位置，upper_bound 找第一个“大于目标”的位置，两者可组成等价值区间 `[lower,upper)`。没有结果时返回 end，使用前不能直接解引用。

这些算法要求区间满足对应比较的分区条件；按同一比较器排序是常见充分条件。比较次数为对数量级，但非随机访问迭代器可能需要线性次数的递增；map／set 应优先用成员查找，而非在其迭代器上套通用 lower_bound。

参考：[C++ 草案：二分查找算法](https://eel.is/c++draft/alg.binary.search)。

### 67. Allocator、内存池与容器线程安全有哪些共同陷阱？

**答案：**

Allocator 管理容器使用的存储分配协议，对象构造和存储取得是不同职责。内存池可减少重复分配，代价是内部碎片、存储保留与生命周期复杂度；SGI 旧实现的“两级、128 字节、16 条链”不代表现代 STL 通用机制。

C++17 的 `std::pmr` 可通过 memory_resource 切换分配来源；资源必须活得比使用它的容器及其存储更久，批量 release 前先处理活对象。跨资源交换／移动也要满足分配器契约。

容器不自动为并发修改提供锁。并发只读、操作不同元素与结构性修改要区分；push／erase／rehash 可能改变共享元数据。`vector<bool>` 还可能让不同逻辑元素共享同一存储字，不能直接套普通元素的并发写假设。

## 易错点速查

- `std::move` 是转换，不保证真正移动；具名右值引用表达式仍是左值。
- `std::array` 属于 C++11；聚合初始化并非 C++14 才出现。
- 虚函数可以 inline；纯虚函数可以有定义；虚表数量与布局属于 ABI 细节。
- 非虚析构基类指针删除普通派生对象通常是未定义行为。
- 局部 static 初始化的同步，不代表后续访问自动同步。
- deque 两端插入会使迭代器失效，但已有元素引用有效。
- 无序容器默认最大负载因子为 1.0，rehash 不使已有元素引用失效。
- 无锁是一种进展保证；原子自旋锁不等于无锁算法。
- C++20 协程是无栈机制；视图和协程句柄都需要明确生命周期。
