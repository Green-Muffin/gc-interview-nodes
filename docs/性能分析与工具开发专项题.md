## 一、性能测量与定位

### 1. 接到“某设备很卡”的反馈，第一步做什么？

**答案：**

先把反馈转成可复现问题：设备/系统、应用与资源版本、场景、操作、分辨率、画质、目标帧率、持续时间、是否首次加载，以及发热或后台状态。

随后采集相同流程的帧时、主线程/渲染线程、GPU（平台支持时）、GC 和内存。先判断持续低帧、偶发尖峰、加载阻塞或热降频，再针对最可能的路径做可反驳的实验。

不要在没有证据时同时改画质、对象池与加载策略，否则即使变快也无法解释原因。若本机无法复现，应增强必要日志与诊断采样，而不是宣布问题不存在。

### 2. 为什么不能只看平均 FPS？P95、P99 帧时间如何解释？

**答案：**

帧预算可近似为 `1000 / 目标 FPS`：60 FPS 约 16.67 ms，30 FPS 约 33.33 ms。平均值可能掩盖少量长帧，玩家仍会感到卡顿。

P95 帧时间表示约 95% 的采样帧不超过该值；P99 更关注尾部。还应查看最大值、超预算帧比例及时间序列，区分首次加载与稳定运行。

必须说明采样窗口、样本量和统计口径。对单帧倒数直接取平均不等于按总帧数/总时间得到的平均 FPS。CPU 与 GPU 可流水重叠，不能把两者耗时简单相加当作最终帧时。

### 3. Profiler 的 Timeline、Hierarchy、Total 与 Self 怎么用？

**答案：**

Timeline 看线程、阶段、相互等待及工作的先后关系；Hierarchy 适合按聚合耗时和调用次数找热点，再下钻调用栈。

Total 通常包含子调用耗时，Self 排除子调用。某父节点 Total 很高，不代表父函数自身很慢；重复调用很多次的短函数也可能形成热点。GC Alloc 则是分配证据，不等于此处已经触发回收。

Deep Profile、调用栈记录和大量日志会增加测量负担。先常规定位，再对小范围增加诊断，最后在接近实际使用的配置中复测。

### 4. `Gfx.WaitForPresentOnGfxThread` 很高就一定 GPU Bound 吗？

**答案：**

不一定。等待可能与 GPU 工作、呈现同步、VSync、限帧以及线程间配合有关；标记名称本身不是完整因果证据。

结合 Timeline 中渲染线程与相邻帧、目标刷新率、GPU 采样和实际帧间隔判断。`WaitForTargetFPS` 也可能表示有意等待目标帧率，不能把它当作应全部消除的运算。

可在同条件下调整分辨率、特定 Pass 或限帧做对照，检查计算时间和等待是否随假设变化。GPU 模块不支持时，用目标平台工具及受控实验补证据。

参考：[Unity 常见性能标记](https://docs.unity3d.com/6000.0/Documentation/Manual/profiler-markers.html)。

### 5. 如何保证优化前后的数据可比较？

**答案：**

固定场景、输入、设备、分辨率、画质、版本、运行模式和采样设置，明确预热、冷/热缓存、网络与温度条件。重复多轮，保留原始数据和代表性采样区间，避免只挑最佳一轮。

报告绝对值和变化：例如某项耗时的毫秒数，而不是只说提升百分比；同时观察长帧、内存峰值与视觉效果，确认瓶颈是否转移。

只有低样本或条件不完全一致时，应降低结论强度。Editor 的定位结果需要在目标设备环境验证，不能直接外推所有平台。

### 6. 如何用 `ProfilerMarker` 给业务打点？异步流程怎么计时？

**答案：**

对高价值阶段使用稳定、可复用的标记，避免动态拼接大量名称。

```csharp
using Unity.Profiling;

private static readonly ProfilerMarker ParseMarker =
    new ProfilerMarker("Loading.ParseConfig");

void ParseConfig()
{
    using (ParseMarker.Auto())
    {
        ParseConfigCore(); // 示例业务方法
    }
}
```

同步采样作用域应正确配对，不能随意跨 `await` 或跨线程保留。异步端到端时延可用请求 ID 与单调时钟记录开始/结束；另给各线程上的实际工作打点，区分排队、等待 I/O 和 CPU 运算。

ProfilerRecorder 等计数采集接口可用于诊断，但需检查目标环境支持的计数器、单位、采样频率与释放要求；诊断本身也要有预算。

参考：[ProfilerMarker](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Unity.Profiling.ProfilerMarker.html)。

## 二、资源与加载基础设施

### 7. “场景加载慢”应该拆成哪些阶段？

**答案：**

拆分为请求排队、Catalog/依赖解析、下载或磁盘读取、解压、反序列化、资源准备、实例化、组件初始化、激活和首帧呈现。具体阶段由使用的系统决定，不能假定所有阶段都在后台。

分别记录端到端时延、实际主线程占用、峰值内存和失败率。异步接口能减少等待时阻塞，不保证激活阶段没有长帧。

进度条应反映可测的阶段进度，不将一个 API 的 progress 值直接当成全部工作进度；还需处理场景激活被延迟时的状态与队列影响。

### 8. 如何设计统一加载器的状态和所有权？

**答案：**

用稳定键定位资源，维护未请求、加载中、已就绪、失败、释放中等状态。每次获取返回明确的租约/句柄，记录谁负责释放；直接复制资源引用不等于增加框架计数。

加载器负责并发请求合并、失败收尾和资源依赖；实例所有者负责实例生命周期。对象池持有实例时，相关资源租约可能仍需有效。

为重复释放、非法状态、漏释放和退出时仍有使用者提供诊断。不要让每个调用点自己决定底层 Bundle 何时卸载，否则共享依赖很难保持一致。

### 9. 多个调用者加载同一资源，一个取消了，应该怎么办？

**答案：**

共享底层操作与单个等待者分开管理。某窗口取消等待，只解除该窗口的需求，不能自动终止其他调用者仍需使用的操作。

最后一个调用者取消时，也要看底层 API 是否支持真实取消；不支持时可让其完成后立即回收，避免出现没人处理的结果。失败、同步完成和取消与完成同时发生，都需要避免双重交付或双重释放。

对象池复用或页面重新打开时，除了对象存在性还应检查请求版本，防止旧结果写入新业务状态。

### 10. 缓存和对象池如何避免“性能优化后内存越来越大”？

**答案：**

缓存保存可复用数据，对象池保存可复用实例，两者都用常驻内存换取部分时间收益。需要明确最大数量/字节、闲置回收、场景作用域、失效规则与资源所有权。

LRU 可用字典加双向链表管理访问顺序，平均常见操作 O(1)；被租用资源不能只因到达容量就强制销毁。模型大小不同的缓存应优先关注字节预算，而非只限制条数。

监测命中率、逐出率、峰值和频繁载入/卸载。如果工作集本来就大，极小缓存可能造成反复加载，应与内存预算一起取舍。

### 11. 怎样检查资源依赖、重复引用和孤立资源？

**答案：**

将资源视为节点、引用视为边，区分直接依赖与传递依赖。可从场景、配置、Addressables 条目等交付入口建立可达集合，结合反向索引寻找某个资源由谁引用。

`AssetDatabase.GetDependencies(path, false)` 查询直接依赖；递归模式还包括间接依赖及输入自身，要处理自项。它看到的是编辑器可识别的引用，不自动证明运行时字符串路径或自定义提供者的全部依赖。

重复源文件、同资源进入多个 Bundle、多个实例加载同一内容是不同问题，应结合交付报告和运行时快照。扫描结果只可标注“疑似未使用”，没有覆盖动态入口时不能直接删除资源。

参考：[GetDependencies](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AssetDatabase.GetDependencies.html)。

## 三、渲染与内存预算

### 12. 如何估算纹理内存？为什么 PNG 文件大小不能代表显存？

**答案：**

未压缩 RGBA8 基准层可粗估为 `宽 × 高 × 4 字节`。2048×2048 约 16 MiB，理想完整二维 Mip 链约 21.33 MiB；只适用于相应格式与假设。

块压缩应按每个 Mip 的块数乘块字节计算，并考虑最小块、对齐、面数或数组层数。Read/Write 可能额外保留 CPU 可读数据，RenderTexture、MSAA 与深度缓冲还有各自成本。

PNG/JPG 是磁盘编码，导入后的 GPU 格式可能完全不同。估算用于预算与初筛，最终用目标平台测量确认，不将估算值标成精确运行时占用。

### 13. 降低分辨率有效，但减少 Draw Call 无效，说明什么？

**答案：**

这提示像素处理、带宽或屏幕空间 Pass 可能更重要，但仍需 GPU 时间与各 Pass 对照。Draw Call 优化通常主要帮助 CPU 提交，未必减轻最贵的 GPU 工作。

检查全屏后处理、透明层数、粒子尺寸、着色器采样、阴影过滤和渲染目标带宽。用逐项开关或等价简化版本定位，避免同时改变许多效果。

降低分辨率会改变画质，最终方案可能是动态分辨率、减少高成本效果或按设备分档，而不是永久统一最低画质。

### 14. UGUI 卡顿，怎么区分重建成本和 Overdraw？

**答案：**

CPU 上看布局计算、Canvas/几何重建和脚本更新；GPU 上看透明覆盖、片段着色与纹理带宽。相同“UI 很慢”的表现可能由不同瓶颈造成。

频繁变化内容可与静态内容拆 Canvas，批量合并数据通知，使用虚拟列表并减少反复 Layout 变更。透明层数多则需要减少遮盖面积、隐藏完全遮挡内容或简化材质。

拆 Canvas 不自动降低 Overdraw，图集也不自动消除布局重建。改动后同时检查 CPU、GPU 与批次数，防止一项下降另一项大涨。

### 15. 如何在保持效果的前提下制定多端画质档位？

**答案：**

与 TA、美术先确定必须保留的视觉目标，再按成本设计档位：阴影距离/级联、Render Scale、后处理、粒子数量与覆盖、纹理分辨率、LOD、动画更新等。

对关键场景固定视角对比，覆盖角色辨识、交互提示与暗部等容易受影响的内容，记录性能和视觉差异。适配设备能力、温度与持续运行，而不是只按平台名称一刀切。

运行时切档还需检查资源加载峰值、变体可用性和切换抖动。任何预算都应有对应设备、场景与验收条件。

## 四、编辑器与运行时工具

### 16. 一个资源检查工具应该如何分层？

**答案：**

建议分成扫描器、元数据读取、规则、报告和修复器。EditorWindow 提供选择范围和结果展示，核心规则尽量不依赖 UI，便于自动化复用。

统一问题记录：规则 ID、资源 GUID/路径、当前值、期望值、原因、修复建议和可否自动修复。先做单一资源类型的可靠闭环，再扩展模型、音频、Prefab 等。

扫描时支持进度、取消、异常隔离与结果导出，不在每次界面重绘时重新扫描全项目。主线程上的 AssetDatabase 操作与可后台处理的纯数据分析应明确分离。

参考：[EditorWindow](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/EditorWindow.html)。

### 17. 纹理检查应检查什么？为什么不能自动把所有 Read/Write 关掉？

**答案：**

检查用途、源尺寸、目标平台覆盖、压缩格式、最大尺寸、Read/Write、MipMap、sRGB/线性用途、Alpha 和图集策略。规则应区分 UI、颜色贴图、法线、遮罩和运行时可读纹理。

关闭不必要 Read/Write 可减少部分内存，但若代码仍使用需要 CPU 数据的操作就可能破坏功能。UI 是否用 Mip、遮罩是否使用 sRGB，也不能全项目一个值。

工具要说明违反规则的依据，允许有负责人和理由的例外。对无法从静态数据确认用途的资源，先报告建议，不伪装成确定可修复问题。

### 18. `AssetPostprocessor` 可以做什么？如何避免反复导入？

**答案：**

它提供资源导入前后回调，例如在 `OnPreprocessTexture` 中配置纹理导入设置。适合明确规则的默认配置和轻量检查，不适合每导入一个文件就扫描整个项目。

回调应具有幂等性：已符合条件时不再次改动。避免在导入回调内无条件 Refresh、SaveAndReimport 或改变依赖，防止循环和导入风暴。大规模规范迁移适合独立的显式批量流程。

规则与导入器版本变化需有受控的迁移安排，平台覆盖也要纳入判断；不要让工具悄悄重置美术有意保留的配置。

参考：[AssetPostprocessor](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AssetPostprocessor.html)。

### 19. 批量修复工具如何保证可控、可追踪？

**答案：**

默认 dry-run，先显示将修改的字段及差异，只处理用户选定的范围。对适合 Undo 的对象编辑按编辑器约定登记；文件/Importer 等修改还应结合版本管理和变更记录，不能保证一切都可由 Ctrl+Z 恢复。

将查询与修改阶段分开，避免边枚举边大范围改变资源集合。批处理 API 如有 Begin/End 配对，应在 finally 中收尾；取消和单项失败需要返回完整报告。

重新运行应只报告剩余问题。不要将“执行完了”视为成功，还要核对字段、资源导入状态及功能/画面。

### 20. 如何设计日志分析工具和轻量运行时诊断面板？

**答案：**

日志采用稳定字段：事件类型、单调时间或时间戳、会话/请求 ID、资源键、耗时、结果、线程及必要版本信息。按操作关联开始、完成、取消与错误，避免只依赖自然语言全文匹配。

诊断面板可显示帧时、分配、资源引用数、在途加载、池容量等，设置开关、频率、采样和有界缓冲。避免每帧拼接大量字符串、同步写磁盘或保存无限日志。

日志处理工具可用 C# 或 Python，输出分布、时间线与异常聚合；脱敏敏感信息。时钟来源不同或时间戳未对齐时，不应直接相减得出跨设备精确延迟。

### 21. 自动化资源检查怎样设计才能真正被团队使用？

**答案：**

让交互式工具与无人值守入口共用规则，接收扫描范围、目标平台和规则配置，输出机器可读 JSON/CSV、简短摘要与有意义的退出状态。

开始时区分历史存量与新增问题，建立基线；先验证误报，再逐步设置哪些违规需要阻断流程。例外应有原因、负责人和适用范围，规则变化也要有版本。

记录耗时，支持按变更及其依赖增量扫描，同时保留定期完整检查。自动化本身失败、资源违规和用户取消应区分，不能统一输出“检查通过”。

## 五、交付与协作

### 22. 为这个岗位准备哪些数据结构最划算？

**答案：**

| 数据结构/算法 | 岗位中的用途 | 常见追问 |
| --- | --- | --- |
| 数组/List | 扫描结果、连续数据、批量遍历 | 扩容、删除成本与缓存局部性 |
| Dictionary/HashSet | 资源查询、去重、访问记录 | 哈希冲突、键不变性、内存成本 |
| Queue/Stack | 加载队列、遍历与任务分解 | 边界、重复入队、容量限制 |
| 二叉堆 | 优先级调度 | 插入/弹出 O(log n)，优先级变化如何处理 |
| 二分查找 | 有序记录检索、虚拟列表偏移定位 | 左右边界、空输入、重复键 |
| DFS/BFS | 依赖可达性、反向引用查询 | visited、环、深度过大 |
| 拓扑排序 | 有向无环依赖执行顺序 | 有环怎么办，是否应该强行忽略 |

能解释为什么选这个结构，比只背复杂度更有价值。并发使用还要另外说明所有权与同步，不能因容器查询快就假定线程安全。

### 23. 优化方案如何与 TA、美术、客户端形成闭环？

**答案：**

提交具体问题：设备、复现步骤、资源路径、截图/数据、影响范围和可能原因。提出可比较的方案，例如降低纹理尺寸、修改效果实现或调整加载时机，并说明各自画质和工程成本。

共同确定负责人、完成标准与复测场景；修复后在同条件验证，保留需要接受的例外。最后将稳定规则写入检查工具或规范，减少相同问题反复出现。

避免把“全部资源不合规”直接丢给美术，也避免未经讨论把关键效果删除。技术指标要服务于实际画面与体验要求。

### 24. 面试时怎样讲清一个性能或工具项目？

**答案：**

按“目标和约束 → 如何复现 → 数据与假设 → 自己完成的改动 → 对照结果 → 代价和后续”展开。先用两三分钟讲完整链路，再根据追问展示 Profiler、报告或关键代码。

明确个人贡献、合作部分和未覆盖平台。没有真实数据就说明目前只验证了功能，下一步如何测量；不要用其他项目或教程的数字填充自己的成果。

被问到陌生底层机制时，先说已知边界，再提出如何查官方文档、源码或设计对照实验。岗位强调独立排查和交付，这种证据意识比不可靠地背出实现细节更有说服力。
