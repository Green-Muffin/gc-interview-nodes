## 一、性能定位

### 1. 如何排查游戏卡顿？

**答案：**

先记录设备、版本、场景、操作、分辨率和温度，建立稳定复现；再采集帧时间、主线程／渲染线程、GPU、GC 和内存，判断是持续低帧、偶发长帧、加载还是降频。

根据热点逐项修改并复测，固定其他条件。先验证原因，再选择对象池、画质调整或加载优化等手段。

### 2. FPS、帧时间、P95 和 P99 各反映什么？

**答案：**

帧时间是产生一帧的耗时，60 FPS 预算约 16.67 ms，30 FPS 约 33.33 ms。平均 FPS 可能掩盖少量长帧。

P95 表示约 95% 的采样帧耗时不超过该值，P99 更关注尾部卡顿；结合超预算比例和时间线判断。CPU／GPU 可重叠执行，不直接把两者时间相加。

### 3. Profiler 的 Timeline、Hierarchy、Total 和 Self 怎么用？

**答案：**

Timeline 看线程工作和等待的时序，Hierarchy 按耗时和调用次数找热点。Total 包含子调用，Self 排除子调用，可判断真正耗时落在哪层。

GC Alloc 表示分配，不等于已经回收。先常规采样，必要时缩小范围增加深度诊断，最后在目标运行环境复测。

### 4. 如何判断 CPU Bound 和 GPU Bound？

**答案：**

结合 CPU／GPU 时间线和受控实验：减少脚本工作／提交若明显改善，倾向 CPU 相关；降低分辨率、简化材质／后处理若改善，倾向像素或带宽相关。

等待标记还可能来自 VSync、限帧或线程同步，不能仅凭 Gfx.WaitForPresent 就断定 GPU 瓶颈。最终定位到具体 Pass 或函数。

### 5. 如何给业务流程打点和计时？

**答案：**

对解析、加载、实例化等稳定阶段使用可复用 ProfilerMarker；同步作用域配对开始和结束。

```csharp
using Unity.Profiling;
static readonly ProfilerMarker Marker = new("Loading.Parse");
void Parse() {
    using (Marker.Auto()) { ParseCore(); } // 业务函数
}
```

异步端到端时延用请求 ID 和单调时钟记录，各线程实际工作分别打点；不要把同一个同步采样作用域跨 await 保留。

### 6. 如何验证一次优化有效？

**答案：**

固定设备、场景、输入、画质和采样方式，分别记录预热前后、冷／热缓存和持续运行情况，多轮对比。

同时报告毫秒耗时、长帧、内存峰值和画面变化，确认没有把成本转移到另一阶段。保留复现步骤和基线，作为之后回归检查的依据。

## 二、加载与资源管理

### 7. 场景加载慢，怎么定位和优化？

**答案：**

拆成请求排队、依赖解析、网络／磁盘读取、解压、反序列化、资源准备、实例化、初始化、激活和首帧呈现，分别计时。

根据瓶颈采用缓存／预取、并发控制、资源分组、异步 IO、分帧实例化或延迟非必要工作。异步接口可减少等待阻塞，但激活和初始化仍可能造成主线程长帧。

### 8. 统一资源加载器怎么设计？

**答案：**

以资源键管理加载状态和依赖，合并同资源的并发请求；成功返回明确的句柄／租约，使用者按生命周期释放。

区分资源所有权与实例所有权，处理加载失败、取消、重复释放和缓存淘汰。对象池仍持有实例时，相关资源依赖也必须有效。

### 9. 多个调用者加载同一资源，某个调用取消怎么办？

**答案：**

把共享底层加载与每个等待者分开管理。一个调用者取消，只移除其需求；还有其他等待者时继续底层操作。

没有使用者后再决定是否取消或完成后释放。完成回调须检查请求版本和调用者生命周期，避免把过期结果交给已销毁窗口。

### 10. 缓存和对象池如何控制内存？

**答案：**

设置容量、字节预算、淘汰条件和空闲期限，区分预热量、当前使用量与空闲量。归还时重置事件、计时器和对象引用，超预算资源真正释放。

持续记录命中率、峰值和释放后存活量，判断缓存是否值得保留。缓存命中提高不代表内存可以无限增长。

### 11. 如何检查资源依赖和重复资源？

**答案：**

以稳定资源 ID 建依赖图，统计直接／间接引用和反向引用，检查重复打包、无入口可达资源及异常依赖链。

结合动态加载清单和资源分组规则，不仅扫描静态引用；“静态不可达”可能仍被运行时按键加载。报告资源路径、引用来源和估计成本，供人工或规则判断。

### 12. 如何估算纹理内存？

**答案：**

未压缩二维纹理约为 `宽×高×每像素字节数`，再计入层数、面数和 Mip；完整方形 Mip 链通常约为基础层 4/3。块压缩按块数乘每块字节数计算。

渲染目标还要考虑 MSAA 和额外副本，Read/Write 也可能保留 CPU 数据。PNG／JPG 是磁盘编码，不能直接代表 GPU 占用；估算后用目标平台工具核对。

## 三、渲染与工具

### 13. UI 卡顿怎么区分重建成本和 Overdraw？

**答案：**

CPU 上查看 Layout、Canvas／网格重建和脚本更新；GPU 上查看透明覆盖、材质与纹理带宽。

频繁变化区可拆 Canvas，列表做虚拟化，减少反复布局通知；透明覆盖高则减少遮挡面积和层数。拆 Canvas 主要缩小重建范围，不会自动减少像素叠加。

### 14. 多档画质怎么设计？

**答案：**

按功能提供可缩放参数：分辨率、阴影距离／级联、灯光、后处理、粒子、纹理、LOD 和动画更新频率。

在固定关键场景比较画质与帧时间，为设备能力和持续功耗选择组合。运行时切档还要检查资源峰值、变体可用性与切换抖动。

### 15. 资源检查工具如何设计？

**答案：**

分为资源扫描、元数据读取、规则判断、结果报告和修复五层，UI 负责选择范围和展示结果，规则可复用于自动化。

每条结果包含资源路径／ID、规则 ID、当前值、期望值和修复建议。支持进度、取消、异常隔离和导出；避免每次 UI 重绘都扫描全项目。

### 16. 纹理检查工具通常检查哪些设置？

**答案：**

检查尺寸、目标平台格式、压缩、Mip、Read/Write、sRGB、Alpha 和图集设置，并按颜色、法线、UI、遮罩等用途制定规则。

关闭不必要 Read/Write 可节省部分内存，但运行时代码需要 CPU 数据时应保留。无法静态确认用途的项给建议和例外入口，不直接统一修改。

### 17. AssetPostprocessor 有什么作用？如何防止重复导入？

**答案：**

它提供导入前后回调，可统一设置纹理、模型等导入参数，或做轻量检查。

规则要幂等：已符合条件不再修改，避免回调里无条件 Refresh／SaveAndReimport。大规模迁移放到独立批处理，控制范围并记录变更。

### 18. 批量资源修复工具需要哪些功能？

**答案：**

先扫描并预览差异，再按选择范围修改；记录修改前后值、成功／失败和原因，支持取消、适用的 Undo 与版本管理回退。

查询与修改分阶段执行，配对的批处理状态放 finally 收尾。修复后重新检查规则和实际功能，重复运行不应反复改同一项。

### 19. 日志分析和运行时诊断面板怎么设计？

**答案：**

日志使用时间、事件类型、请求 ID、资源键、线程、耗时和结果等结构化字段，按请求关联流程并聚合异常。

诊断面板展示帧时、内存、在途加载和池容量，设置有界缓冲及采样频率，避免每帧大量字符串分配或同步写盘。工具自身也应有可控的性能成本。

### 20. 自动化资源检查怎么接入团队流程？

**答案：**

交互工具与自动化入口共享规则，接收范围、平台和配置，输出 JSON／CSV、摘要与明确退出状态。

先建立历史问题基线，区分新增违规、工具失败和用户取消；验证误报后再设置阻断级别。支持增量扫描和定期全量检查，例外保留原因与负责人。

## 四、工程问答

### 21. 客户端研发面试中如何做自我介绍？

**答案：**

控制在一到两分钟，按“背景与方向 → 最相关项目 → 个人负责内容 → 一项可量化结果 → 与岗位的连接”组织。

项目部分说清问题、实现和结果，例如“负责资源加载模块，合并重复请求并补充引用诊断，将某场景峰值从实际测得的 A 降到 B”。不重复念简历，也不罗列自己无法继续解释的技术名词；结尾留下一个便于追问的具体项目。

### 22. 加载、缓存和依赖工具通常用哪些数据结构？

**答案：**

数组／List 保存扫描结果，Dictionary／HashSet 做定位和去重，Queue 管任务，堆按优先级调度，LRU 管缓存淘汰，图与拓扑排序处理资源依赖。

根据查询、更新和遍历方式选择，并明确容量、生命周期及并发同步。容器查询快不等于整个工具就快。

### 23. 如何向团队说明并推进一个性能优化方案？

**答案：**

给出复现步骤、设备和热点数据，说明候选改动及其画质／内存／维护代价；与相关人员确定验收场景和负责人。

同条件复测，保存对照结果，再将稳定规范加入工具或自动检查，减少同类问题反复出现。

### 24. 面试时如何介绍性能或工具项目？

**答案：**

按“问题与目标 → 定位依据 → 自己完成的实现 → 对照结果 → 代价和改进”说明。先讲完整链路，再按追问展示数据和关键代码。

区分个人工作、协作部分和未验证范围；没有测量数据的部分不要编造提升数字。
