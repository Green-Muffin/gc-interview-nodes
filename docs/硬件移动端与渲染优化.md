## 一、Tile 与附件生命周期

### 1. IMR、TBR 与 TBDR 的区别是什么？

IMR 可按提交顺序推进几何和光栅工作；Tile 架构先将图元按屏幕区域归类，再在片上空间处理各块，从而减少颜色／深度中间结果的外部访问。不同 GPU 还可能结合缓存、压缩和混合调度，分类不是两种毫无交集的实现。

TBDR 一般强调在 Tile 处理内利用更充分的可见性信息避免隐藏表面着色；不能把 HSR 统一说成在 binning 时就完成。Mali、Adreno、Apple、PowerVR 的具体实现不应直接互换描述，tile 尺寸和容量也非固定。

IMR 同样有片上缓存与压缩，不是每次写附件都立刻完整落 VRAM。Tile 中间数据也可能因格式、容量、依赖或 pass 边界被迫写出。

### 2. RenderPass、Subpass 与 Input Attachment 声明什么？

传统 Vulkan render pass 描述附件、load/store、subpass 使用与依赖。Input Attachment 用于在允许的范围读取当前 framebuffer 位置／样本的数据，常用于前一 subpass 写 G-buffer、后一 subpass 光照。

它不是可自由偏移 UV、过滤、访问任意邻域的普通纹理采样。按像素局部依赖可给驱动合并并保留 Tile 数据的机会，但不保证所有 subpass 都被合并；格式、样本数、存活附件量和依赖关系都影响结果。

两个独立 pass 若需要保留中间图像，会增加物化与存取的可能，不能把每个 API 边界都绝对等同一次完整 DRAM 往返。参考：[Khronos：Subpasses 示例](https://docs.vulkan.org/samples/latest/samples/performance/subpasses/README.html)。

### 3. LoadOp 和 StoreOp 怎样省带宽？

| 操作 | 语义 | 可能的优化 |
| --- | --- | --- |
| LOAD | 保留附件的已有内容 | 可能需读入旧数据 |
| CLEAR | 以给定值初始化 | 避免不必要的旧内容加载，可用快速清除 |
| DONT_CARE load | 旧内容无须保留 | 允许省去读入，但后续不能依赖未定义值 |
| STORE | 保留相应渲染结果 | 可能需写出供后续使用 |
| DONT_CARE store | 结果无须保留 | 允许省去保存，不是必然没有任何物理写入 |

它们关联附件在 render pass／rendering 实例中的生命周期，不是每个 subpass 开始和结束都重新触发一次完整 load/store。若深度只在该实例内部使用，可考虑 CLEAR＋DONT_CARE；若后续还做 SSAO／SSR，就不能随意丢掉。

参考：[Vulkan StoreOp 定义](https://docs.vulkan.org/refpages/latest/refpages/source/VkAttachmentStoreOp.html)。

### 4. Transient 与 Lazy Allocation 保证“不占外存”吗？

`VK_IMAGE_USAGE_TRANSIENT_ATTACHMENT_BIT` 表达相关临时附件用途，可配合支持的 `VK_MEMORY_PROPERTY_LAZILY_ALLOCATED_BIT` 内存类型。实现可按实际需要承诺物理 backing，适合某些临时深度／MSAA 附件。

仅把 load/store 设 DONT_CARE 不会自动为任意资源启用 lazy allocation；必须满足 usage、内存类型和绑定要求。即使 lazy，也不保证永远只在 Tile 上，实际承诺和写出行为由实现决定。不支持相应内存类型时要有常规分配方案。

### 5. MSAA Resolve 是一种 StoreOp 吗？

**不是。** Vulkan 没有原材料写的 `MULTISAMPLED_RESOLVE` StoreOp。传统 render pass 配置 resolve attachment；dynamic rendering 的 `VkRenderingAttachmentInfo` 使用 `resolveMode`、`resolveImageView` 等独立字段。

多采样颜色可在 Tile 内 resolve 成单样本目标，再保存结果，同时不保留原始 MSAA 附件。能否省掉多样本外存读写取决于实际路径，深度／模板 resolve 还需查询对应模式与限制。

参考：[VkRenderingAttachmentInfo](https://docs.vulkan.org/refpages/latest/refpages/source/VkRenderingAttachmentInfo.html)。

### 6. Dynamic Rendering 与 Local Read 如何理解？

Dynamic Rendering 在 Vulkan 1.3 引入核心接口 `vkCmdBeginRendering`，此前有 KHR 扩展，可减少显式 `VkRenderPass`／`VkFramebuffer` 对象管理。基础形式不是传统多 subpass 的逐项替身。

`VK_KHR_dynamic_rendering_local_read` 及支持该能力的核心版本允许相关局部读取语义，仍需正确声明映射、layout 和同步，不能因此任意读取相邻像素或同时无约束读写一个附件。

Local read 与 framebuffer fetch 相关但不应视为所有厂商扩展完全同义。Dynamic Rendering 也不必然性能更差，应根据设备和实际合并行为判断。参考：[Khronos：Dynamic Rendering Local Read](https://docs.vulkan.org/features/latest/features/proposals/VK_KHR_dynamic_rendering_local_read.html)。

## 二、内存与上传

### 7. Heap、Memory Type 和属性 Flag 各表达什么？

Heap 表示可分配内存池及相关属性，Memory Type 关联 heap 并声明访问属性；资源的 memoryTypeBits、对齐与使用方式共同决定可选类型。

| Flag | 主要语义 | 不能误解为 |
| --- | --- | --- |
| DEVICE_LOCAL | 对设备本地访问合适的内存 | 一定是 CPU 不可见的独立 VRAM |
| HOST_VISIBLE | 允许映射到主机地址空间 | 一定是慢速系统 RAM |
| HOST_COHERENT | 无需应用显式 flush／invalidate 来管理相关主机缓存一致性 | 自动解决 CPU／GPU 执行先后或数据竞争 |
| HOST_CACHED | 主机访问可缓存 | 无论 coherent 与否都必须 invalidate |
| LAZILY_ALLOCATED | 可按需承诺物理存储的特殊类型 | 任意 buffer／纹理都能使用 |

UMA 可同时具备 DEVICE_LOCAL 与 HOST_VISIBLE；独显通过可映射设备内存等也可能暴露这种组合。非 coherent 映射需遵守 flush／invalidate 与 `nonCoherentAtomSize` 范围要求，并避免与 GPU 并发冲突。

参考：[Vulkan 内存属性](https://docs.vulkan.org/refpages/latest/refpages/source/VkMemoryPropertyFlagBits.html)。

### 8. Staging、Persistent Mapping 与 Ring Buffer 如何工作？

常见离散 GPU 上传路径是 CPU 写 host-visible staging → 复制到合适的 device-local 资源 → 令后续消费者可见。UMA 或合适的小型动态资源可能直接写映射内存，需实测决定。

Persistent mapping 减少重复 map/unmap；Ring Buffer 用不同区间承载多帧数据，但区间复用前必须确认 GPU 已完成使用，不能因为“换了偏移”就永远不等待。

Transfer Queue 不保证独立硬件或一定更快。跨 queue family 时还需根据 sharing mode 管理所有权；上传完成信号、访问可见性及 image layout 都要正确连接。

### 9. Vulkan 是否要求每个资源单独分配内存？VMA 做什么？

Vulkan 允许多个资源在大块 `VkDeviceMemory` 中按要求绑定偏移，即子分配；某些资源另有 dedicated allocation 要求／偏好。原材料“每个 Buffer／Image 都必须独立 allocate”的说法不成立。

VMA 等分配器帮助处理内存类型、对齐、预算、块管理和碎片，但不是唯一合法方案。分配数量上限查询设备，不能把某个常见值硬编码为通用限制。搬迁／整理资源还涉及绑定、复制和描述符更新，并非所有活跃资源能随时无感迁移。

参考：[Khronos：Memory Allocation](https://docs.vulkan.org/guide/latest/memory_allocation.html)。

### 10. Memory Aliasing 有哪些条件？

生命周期不重叠的资源可在满足兼容性、对齐和别名要求时复用存储，减少峰值内存。Image aliasing 还需考虑创建标志、布局、初始内容以及必要的同步。

CPU 看来不同帧“先后用完”，不代表 GPU 异步执行已结束；跨队列和帧在途会拉长存活区间。RenderGraph 可以推导这些关系，但外部读写、历史纹理和异步任务必须被完整声明。

## 三、同步与布局

### 11. Execution Dependency 与 Memory Dependency 有何区别？

执行依赖规定哪些操作先完成、哪些可开始；内存依赖还规定写入的可用性与对后续访问的可见性。同步语义不等同于“强制数据写回 DRAM”，实现可以在缓存层级中完成要求。

RAW／WAW 等冲突通常需要对应内存依赖；某些 WAR 场景只需执行顺序。不能统一说“没有 access mask 就绝无有效 barrier”，应按具体资源访问类型判断。

### 12. Barrier 的 stage 与 access 怎样选择？

例如计算写 buffer 后给 indirect draw 读取：源 scope 覆盖 compute shader 与 shader write，目标 scope 覆盖 draw indirect 与 indirect command read。颜色附件写后片元采样，则匹配 color attachment output/write 到 fragment shader/sampled read，并处理所需 layout。

Stage 不是 GPU 一根管道上插入全局停顿点，而是定义同步范围。范围太窄漏同步，范围太宽可能减少重叠，但也不是“多写一个 stage 就必然多停一次”。多资源可在同次调用中批量组织，并考虑队列能力。

参考：[Khronos：Synchronization Examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html)。

### 13. Image Layout 的职责是什么？GENERAL 是否必然错误？

Layout 声明图像的合法访问状态／模式，常用 attachment、read-only、transfer、present、general 等，转换须与依赖关系配合。它不是应用直接指定“把缓存压缩开关设为某值”。

`GENERAL` 可合法支持相应访问，并不代表所有优化关闭，也不会因为普通采样使用它就必然读到乱码；专用 layout 可能给实现更多优化机会，具体性能需测量。usage、描述符中的声明、真实 layout 与访问方式必须匹配。

`UNDEFINED` 表示可放弃已有内容，不可在还需要旧像素时借它随意跳转；present 或跨 family 转移还要遵守各自规则。

### 14. Fence、Binary Semaphore 与 Timeline Semaphore 如何分工？

| 原语 | 主要用途 | 生命周期注意 |
| --- | --- | --- |
| Fence | 主机查询／等待提交完成 | 重新使用前按规则 reset，避免 GPU 使用期间重置 |
| Binary Semaphore | 队列提交或呈现等操作间等待／通知 | 信号会被相应等待消费，可以按合法生命周期反复使用 |
| Timeline Semaphore | 用单调递增值表达完成点，支持主机等待／信号 | 严格管理值与依赖，不能代替全部资源访问建模 |

Fence 不是 CPU 与 GPU 任意双向通信机制；Binary 也不是整个对象一生只 signal／wait 一次。Timeline 在 Vulkan 1.2 进入核心，功能可用性仍应查询，呈现相关接口有自身约束。

### 15. Synchronization2 改善了什么？

Vulkan 1.3 的 Synchronization2 让每条 barrier 更直接携带 stage/access，并提供更细粒度的标志和提交表示。`VkDependencyInfo` 聚合多种 barrier，`vkCmdPipelineBarrier2` 等接口提高表达清晰度。

它不取消执行与内存依赖，也不保证同义调用天然更少或更快。把旧标志换名却保留错误 scope，不会修复数据竞争；验证层和同步验证可帮助发现问题，性能仍需 GPU 捕获与时间线。

## 四、命令与资源绑定

### 16. Primary、Secondary 与多线程录制怎么安排？

Primary command buffer 可直接提交；Secondary 通常由 Primary 执行，用于组织并行录制或复用部分命令。每个工作线程可使用独立 command pool，遵守对象的外部同步要求。

Secondary 带来继承信息、组合和调用成本，过小任务不一定获益。OpenGL 也有驱动缓冲和异步执行，不能把它描述为每次 draw 都必须等 CPU 与 GPU 同步完成。

### 17. Descriptor Set、Pipeline Layout 与 Push Constant 是什么？

Descriptor 描述 shader 所用资源，Set Layout 定义绑定结构；Pipeline Layout 组织 set layout 与 push constant ranges。Descriptor Set 是资源接口，不会自动延长所引用对象的生命周期。

Push Constants 可随命令更新少量数据，设备保证的最小容量常见为 128 字节，实际上限需查询 `maxPushConstantsSize`，不是所有设备都只能≤128。其底层可能使用不同存储，不保证全部直达寄存器，也不保证总比 UBO 快。

### 18. Dynamic Descriptor 与 Descriptor Indexing 有何区别？

Dynamic Uniform／Storage Buffer 描述符在绑定命令中传入 dynamic offset，选择同一 buffer 的不同区间；不是 shader 自己设置这个 API offset。偏移要满足对齐、范围与计数顺序要求。

Descriptor Indexing 允许 shader 索引资源数组，部分能力在 Vulkan 1.2 核心化，仍需逐 feature 检查。Partially Bound 允许未使用位置不绑定，不能合法访问任意未初始化元素；Non-uniform Indexing、Variable Descriptor Count 和 Update After Bind 各有不同约束。

Bindless 可减少按材质重绑，但仍有描述符数量、资源驻留、同步和生命周期成本。Descriptor Buffer 是另一个需查询的可选能力，不能简单写成所有 Vulkan 1.3 设备默认具备。

### 19. Pipeline、Dynamic State 与 Cache 怎样影响卡顿？

Pipeline 对象封装相关状态与程序；部分状态固定，部分可声明为动态并由命令设置。因此不是所有状态都在对象创建时永久锁死，动态状态也只覆盖设备／API 支持的项目。

变体组合增多会增加创建、存储和首次使用成本。可减少不必要变体、提前准备常用组合并管理 Pipeline Cache；缓存数据与设备、驱动兼容性有关，磁盘有缓存不保证所有新组合完全免创建成本。

切换 Pipeline 的实际开销取决于驱动与状态组合，不宜一律说“极高”或“只是换指针零成本”。

### 20. Async Compute 与 Transfer Queue 是否必然并行？

Queue 是 API 调度抽象，多个队列／family 不保证对应独立执行引擎。Graphics 和 Compute 通常共享部分着色、缓存和内存资源，重叠可能提升利用率，也可能竞争导致整体更慢。

适合异步的工作需有足够独立性，并与主路径资源占用互补；同步点太密、占满相同执行单元或加大带宽都可能抵消收益。Transfer 同样要考虑真实硬件、所有权转移和数据消费时机。

## 五、GPU Driven

### 21. RenderGraph 如何帮助管理一帧？

节点表示 Pass，边表示资源及执行依赖；框架可根据声明进行死 Pass 消除、资源存活区间分析、barrier／layout 规划、别名和临时资源管理。

是否合并 subpass、如何调度异步、是否有外部资源导入／导出接口，依具体实现。历史帧数据、有副作用的 Pass、全局 buffer 隐式访问必须明确标注，不能认为画出 DAG 就能自动正确推导所有 Vulkan 细节。

### 22. Indirect Draw、GPU Culling 与 LOD 怎样连接？

GPU 读取实例数据，进行视锥／遮挡判断、LOD 与可见列表压缩，写入 indirect 参数和计数；后续 draw 消费这些数据。需正确连接 compute write 到 indirect read 及 shader read 的同步。

CPU 仍负责资源、调度、提交和部分场景管理；生成命令、排序、扫描和可见性本身也有成本，不等于 Draw Call 开销归零。使用上一帧 Hi-Z 时，应对相机突变和新显露物体保守处理。

### 23. Mesh Shader 替代了哪些工作？

Task／Mesh Shader 路线以工作组和 meshlet 组织几何生成，Mesh 输出顶点与图元，之后仍进行光栅化和片元处理。Task 阶段可选，支持情况和工作组／输出限制须查询。

它可取代传统顶点／细分／几何处理路径的相应组合，便于细粒度剔除与程序几何，但不是所有任务都自动更快，也不是“跳过所有固定功能”。Meshlet 大小要平衡数据复用、剔除粒度和占用。

### 24. VRS 与 Multiview 怎样节省工作？

VRS／Fragment Shading Rate 调整片元着色调用的空间频率，覆盖与深度样本并不因此一概同步减少。平滑、低细节区域更适合粗率；几何边缘、细纹理与文字 UI 通常需要谨慎保留质量。

Multiview 将绘制关联到多个视图，常用于 VR 或其他多视图场景，可减少 CPU 重复提交并给实现复用机会；每视图的变换、裁剪和着色仍可能重复，不能一律说“一次 draw 就省掉所有顶点工作”。

## 六、执行效率与移动预算

### 25. SIMT、Subgroup 与分支发散如何解释？

许多 GPU 以一组 lane 执行相关指令。NVIDIA 常见 warp 32，AMD 可有 wave32／wave64，其他架构和模式也不同；shader 不能普遍硬编码组宽。

同组走不同分支时，常以掩码分批执行相关路径，降低有效利用率，但具体调度并非永远严格锁步。subgroup ballot／shuffle／broadcast／reduce 让 lane 交换信息，须确认功能支持、活动掩码和一致控制流要求。

按数据类型或工作量分组可能减少发散，但排序本身有成本，不能只为消灭一个廉价 if 就破坏局部性。

### 26. Occupancy、寄存器压力与延迟隐藏有什么关系？

Occupancy 表示某执行资源上可驻留的 wave／warp 相对上限；受寄存器、共享内存、工作组大小和架构限制。足够多可运行工作能在等待访存时切换执行以隐藏延迟。

更高占用不总意味着更快：为减少寄存器而增加 spill 或重复计算可能更差；工作达到合适并行度后，瓶颈可能已转到 ALU、带宽或依赖链。应结合活跃 lane、缓存、指令、寄存器和实际 Pass 时间判断。

### 27. 移动端如何选择纹理格式与附件精度？

BC 常见于桌面，ETC2／EAC 常见于相应 GLES／移动能力，ASTC 在支持的设备上提供多种块大小，PVRTC 多见于部分历史设备。平台名不等于所有设备支持同一格式，ASTC 也不是任何设备都能直接采样。

检查压缩格式 feature、色彩／数据用途、alpha 质量、法线重建和回退包体。G-buffer 格式、HDR 精度、法线编码、深度和 MSAA 倍率共同决定附件带宽与 Tile 压力；压缩纹理与 Render Target 压缩是不同机制。

### 28. 移动端优化应按什么顺序测量？

先固定场景、分辨率、质量、设备和电源／温度条件，观察 CPU／GPU 帧时间及长帧，区分提交、几何、着色、纹理、附件带宽和同步等待。

可分别改变分辨率、材质复杂度、灯光／阴影、透明覆盖、附件格式和 pass 数来验证假设。降低分辨率明显改善常提示像素或带宽相关压力，但仍需捕获定位，不能凭单一实验下定论。

持续负载会受温控与频率变化影响；平均帧率之外要关注帧时间分布、功耗和画质。优化目标是整帧稳定性，不是单个计数器最大或某条 API 调用最少。

## 七、移动端实践与帧呈现

### 29. 移动端与 PC 的差异应该怎样回答？

从功耗／散热、带宽、内存共享、GPU 架构、驱动和功能支持分别比较。移动设备通常更受持续功耗约束，很多采用统一内存和 Tile 路线；PC 也有 UMA／低功耗设备，不能按平台名称硬套某个带宽数字。

先查询目标设备功能，再验证持续负载。硬件光追、Bindless 等不是“移动端一律没有”，也不能按手机品牌／GPU 系列粗略推断。热降频会使短时间跑分与稳定帧率相差很大。

### 30. 移动端 Deferred、透明和 MSAA 如何取舍？

Deferred 的关键是光源数量、G-buffer 附件总量、Tile 驻留机会与后续读取需求；Forward／Forward+ 可能在某些场景更省带宽。压缩材质贴图与压缩 G-buffer 不是同一个优化：普通实时颜色附件不能直接随意使用 ASTC／ETC2 块压缩格式。

可减少附件与精度、打包材质参数和编码法线，但格式须支持所需附件操作。半分辨率 G-buffer 还会损失几何边界、深度和材质信息，不能当作无代价降采样；较适合先试独立的 AO／反射等效果。

透明仍可被不透明深度淘汰，但多个可见透明层往往都需贡献，HSR 不会自动消除这部分成本。排序与不透明／透明逻辑分段不强制两个独立 render pass。MSAA 可在 Tile 中高效 resolve，延迟多采样也并非不可能，需一起衡量附件容量和着色成本。

### 31. 移动端 GI 与反射怎样分层选择？

| 方案 | 适用情况 | 保留的成本／限制 |
| --- | --- | --- |
| Lightmap＋光照探针 | 静态环境与动态物体间接光 | 纹理／系数存储、采样、插值，不是零开销 |
| 预过滤 IBL／反射探针 | 环境反射与低频照明 | 局部视差、遮挡及动态更新 |
| 平面反射 | 镜面、水面等平面 | 额外视图绘制，按分辨率／层／频率限预算 |
| SSR／AO／SSGI | 利用屏幕内信息增加局部细节 | 降采样、重建、离屏回退与时间伪影 |
| LPV／动态探针等 | 需要动态间接光且预算允许 | 网格／探针更新、精度、漏光 |
| 硬件／软件光追局部效果 | 对应功能可用并满足持续帧预算 | AS、射线数、重建与功耗 |

通过降低效果分辨率、采样／传播次数、更新频率来控制成本，并为无历史或离屏区域设置回退。递归／反弹数是算法与预算选择，不把“移动只能一次反弹”当 API 定律。

### 32. 双缓冲、三缓冲、VSync 与 VRR 有什么关系？

缓冲数量决定可同时持有多少图像，呈现策略决定何时选择哪张图像送显示。双缓冲本身不保证无撕裂；扫描输出过程中切换来源可能拼出不同帧。VSync 约束呈现时机，也可能引入排队／等待。

Vulkan 常见 FIFO 按队列在刷新时呈现；MAILBOX 用较新的待呈现图像替换旧候选；IMMEDIATE 允许立即切换，可能撕裂。支持情况需查询，MAILBOX 不等于固定三张图像，也不保证总是最省电。

更多缓冲／在途帧可能提高吞吐也可能加大延迟，不能简单说“三缓冲一定增加固定一帧”。VRR 在支持范围内调整刷新节奏，低于／高于范围仍需相应策略。优化帧率时同时测量 frame pacing 和输入到显示延迟。

参考：[Vulkan Present Mode 定义](https://docs.vulkan.org/refpages/latest/refpages/source/VkPresentModeKHR.html)。

### 33. CPU、顶点、片元与带宽瓶颈怎样分别处理？

| 瓶颈候选 | 验证与手段 | 避免误判 |
| --- | --- | --- |
| CPU 提交／场景更新 | 查线程时间线、剔除、合批、实例化与任务组织 | 把工作移到 GPU 可能增加同步或争用 |
| 几何／顶点处理 | LOD、剔除、简化蒙皮与公共变换 | 实例化减少提交，不会自动减少所有顶点执行 |
| 片元着色 | 降分辨率、缩减透明覆盖、简化材质／光照 | 有分支不必然慢，无分支也不必然快 |
| 纹理／附件带宽 | 压缩资产、Mip、格式与 Pass 生命周期优化 | 算力优化未必触及带宽瓶颈 |

顶点属性不足时先删除／打包冗余数据，或把每实例数据移到相应缓冲；vertex pulling 可利用内建顶点 ID 从 buffer 取数据，但要测量布局与访存，通常不需再专门添加一个 ID 属性。

程序化噪声改变顶点位置本身并不减少面数。网格合并会扩大包围体，可能削弱剔除；每项优化都要验证整帧收益，而非只盯 Draw Call 数。

### 34. 大世界、城市与虚拟纹理怎样组织资源？

按空间分块流式加载，设置网格、纹理、动画、阴影和 GI 的预算；近处保细节，远处采用 LOD／HLOD。城市可利用建筑遮挡，重复路灯／窗户可实例化；大型合并块仍需权衡剔除粒度，遮挡查询不应让 CPU 每帧阻塞等结果。

虚拟纹理将逻辑页面映射到有限物理缓存，根据反馈、预取与优先级流入数据。页面未到达时须有粗 Mip 回退，并处理边界、过滤、IO、解码与上传；替换策略可用 LRU 或其他方案，不是渲染时所有可见纹素总能即时命中。

资源提前加载与延迟释放应参考移动速度和在途 GPU 使用。突然转视角、跨区域移动、密集透明、交通／人群更新都是压力案例；CPU 逻辑、动画和渲染应各有分级策略。

## 易错点速查

- IMR 有缓存；Tile 数据不保证永不写外存；TBDR 的可见性阶段依实现。
- Resolve 与 StoreOp 分开配置；不存在 Vulkan `MULTISAMPLED_RESOLVE` StoreOp。
- Transient＋Lazy 是优化条件，不是绝对的“零外存”承诺。
- DEVICE_LOCAL 可同时 HOST_VISIBLE；HOST_COHERENT 不替代执行同步。
- Vulkan 原生允许子分配；VMA 是工具而非唯一合法方案。
- GENERAL 可合法采样；Layout、usage 和同步一致比口诀更重要。
- 多 Queue 不等于必然多硬件并行；高 Occupancy 不等于最高性能。
