## 一、PBR 渲染管线

### 1.1 前向/延迟双路径与金属粗糙度工作流

整体结构是**前向/延迟双路径共享同一套 PBR 核心**：

- **延迟路径**：`gbuffer_pass.frag` 写 6 张 G-Buffer（Albedo / WorldNormal / WorldPosition / Material(metallic, roughness, ao) / Emissive / Motion），`deferred_light_pass.frag` 逐像素读回做完整光照（deferred_light_pass.frag:173-216）；
- **前向路径**：`forward_lit_pass.frag` 单 pass 全做完，两边**核心函数逐字相同**（`evaluateDirectPBR` / `evaluateIBL` / `evalIrradianceSH`，见 forward_lit_pass.frag:120/168/85 与 deferred_light_pass.frag:104/149/69），保证两种路径视觉效果一致；
- 延迟光照 main 的流程：读 G-Buffer → 法线长度 < 0.1 判为天空早退 → IBL 环境光 → Emissive → 遍历灯光数组（平行光带 CSM 阴影、点光/聚光带衰减），全部累加后输出 HDR，再由 `tone_mapping_pass.frag` 做 ACES。

**金属粗糙度工作流**（deferred_light_pass.frag:179-181）：

- `metallic/roughness/ao` 打包在 Material 的 rgb；roughness 下限 clamp 到 **0.04**（防止 GGX 的 α²→0 时 D 项爆炸）；
- F0 统一用 `mix(vec3(0.04), albedo, metallic)`（106 行）——电介质固定 4% 反射率，金属直接用反照率当 F0，这是标准 UE/learnopengl 约定。

### 1.2 直接光：Cook-Torrance 逐分量

高光 = **NDF × 几何 × 菲涅尔 / (4·NdotV·NdotL)**（evaluateDirectPBR，deferred_light_pass.frag:104-119），三项分别是：

**D — GGX / Trowbridge-Reitz 法线分布**（83-90）：

```glsl
a  = roughness * roughness;          // Disney 重参数化：感知粗糙度平方
a2 = a * a;
D  = a2 / max(PI * (NdotH² * (a2 - 1) + 1)², 1e-5);
```

`NdotH²(a²-1)+1` 接近 0 时分母趋零产生镜面峰；`max(...,1e-5)` 防除零。roughness 越大峰越宽越暗。

**G — Smith 遮蔽阴影项**（92-102）：两个方向的 Schlick-GGX 相乘：

```glsl
r = roughness + 1.0;
k = (r * r) / 8.0;                    // 注意：这是 IBL 调校版 k
G(NdotV) = NdotV / (NdotV * (1-k) + k);
G = G(NdotV) * G(NdotL);
```

> ⚠️ 诚实细节：UE 对**解析光**惯用 `k = roughness²/2`，对 IBR 用 `(r+1)²/8`；这套代码两种场合都用了后者（BRDF LUT 生成处也是，texture_manager.cpp:471）。视觉差异很小，但面试被抠细节时要能说出来。

**F — Schlick 菲涅尔**（65-67）：`F = F0 + (1-F0)(1 - HdotV)⁵`，入射角用**半向量** H 与视线夹角（微表面模型的标准做法），掠射角时反射率趋向 1，这就是边缘高光增强。

**归一化**（111-113）：`specular = D·G·F / max(4·NdotV·NdotL, 1e-5)`，分母下限防平行光掠射时的数值爆炸。

### 1.3 漫反射：Lambert + 能量守恒耦合

```glsl
kS = F;                                // 被高光反射走的比例
kD = (1 - kS) * (1 - metallic);        // 剩下的进漫反射；金属没有漫反射
diffuse = kD * albedo / PI;
最终: (kD * albedo/PI + specular) * radiance * NdotL;   // 118 行
```

- `albedo/π` 是标准 Lambert 的 BRDF 归一化（球面积分守恒）；
- **能量守恒的关键在 kD 的 (1-kS) 因子**：出射能量不能超过入射，高光越强漫反射越弱；
- `(1-metallic)`：金属的电子结构没有次表面散射，漫反射直接归零，能量全进镜面项。

**光源模型**（applyPunctualLight，121-147）：

- 平行光：方向光 + radiance = color·intensity（CSM 阴影乘进去）；
- 点光/聚光：**平滑窗口衰减** `falloff = (1 - clamp((d - light_radius)/(range - light_radius)))²`（135-136，平方让边缘更柔而不是线性截断），聚光再乘 inner/outer 余角插值的锥形因子（139-144）。

### 1.4 IBL 环境光：Split-Sum 两张查找表

Split-Sum 把渲染方程的积分拆成两个可预计算的量。

#### 漫反射：球面谐波（SH9）

**烘焙（CPU，loadCubemapTexture）**：加载 cubemap 时逐纹素投影（texture_manager.cpp:635-648）：

```
sh_accum[b] += color · basis(dir) · (4π / 6·faceSize²)   // 每纹素立体角权重
```

basis 是 9 个 2 阶实球谐基函数（EvaluateSHBasis9，132-145，就是 shader 里那组常数 0.282095/0.488603/1.092548/0.315392）。然后乘**余弦卷积系数**（653-663）：`{π, 2π/3, 2π/3, 2π/3, π/4, π/4, π/4, π/4, π/4} / π`——这是 Ramamoorthi 2001 的结论：Lambert 余弦瓣与辐照度环境卷积后，每个 SH 系数只乘一个常数，**辐照度 = Σ irradianceSH[b] · basis(n)**，一次 9 个系数的点积就能算出任意法线方向的漫反射环境光（shader evalIrradianceSH，69-81，最后 max(0) 去负值）。

#### 高光：预滤波 cubemap + BRDF LUT

- **预滤波**：cubemap 每级 mip 在 CPU 上用 **GGX 重要性采样**卷积（PrefilterFaceGGX，147-215）：Hammersley 序列（基 2 的位反转出 ξ₁→φ，基 3 出 ξ₂），按 GGX NDF 的逆 CDF 采样半向量 `cosθ = √((1-ξ₂)/(1+(α²-1)ξ₂))`，α=roughness²，32 采样/纹素，N·L>0 才累计并以 NdotL 加权；每级 mip 的 roughness = mip/(mipCount-1)（668）——**mip 链本身就是“粗糙度→预滤波色”的查找表**；
- **BRDF LUT**：启动时 CPU 生成 128×128、512 采样（createBrdfLookupTexture，456-537），横轴 NdotV、纵轴 roughness，积分输出 Karis split-sum 的两标量：`scale = Σ(1-Fc)·GVH/(NdotL·NdotH)`、`bias = ΣFc·GVH/(NdotL·NdotH)`，存 RGBA32F。

#### 运行时合成（evaluateIBL，deferred_light_pass.frag:149-171）

```glsl
vec3 prefiltered = textureLod(skybox, R, roughness * max_lod);   // 第一张和：环境高光
vec2 env_brdf = textureLod(brdfLut, vec2(NdotV, roughness), 0);  // 第二张和：Fresnel·几何
specular = prefiltered * (F * env_brdf.x + env_brdf.y);
diffuse  = evalIrradianceSH(N) * albedo;
color = (kD * diffuse * diffStrength + specular * specStrength) * ao;
```

这就是完整的 split-sum：`∫ Li(l) f_s(l,v) dω ≈ prefilteredColor · (F0·scale + bias)`。两个 clamp `kIblMaxRadiance=3.0` 防环境贴图过曝烧穿。

### 1.5 法线贴图：无切线的屏幕空间扰动

`perturbNormal`（gbuffer_pass.frag:44-56，forward 同款）是 **Mikkelsen 切线无关法线映射**：不用顶点切线，而是用 `dFdx/dFdy(worldPos)` 在像素级现算表面梯度，叉乘构造 TBN；`slope = n.xy / max(n.z, 0.1)` 把切线空间法线转成高度梯度，按 det 符号翻转保证背面/镜像 UV 正确。在 G-Buffer 阶段就扰动好，延迟光照直接拿最终法线。白图 fallback（63 行）跳过扰动。

### 1.6 阴影：4 级 CSM + 旋转 Poisson PCF（PCSS 半实现）

`shadow_csm.glsl`：

- 4 cascade 打包成 2×2 atlas（`origin = (cascade&1, cascade>>1) * 0.5`），按视线深度选级，级间 10% 重叠区线性混合（shadow_csm.glsl:153-165）；
- **PCSS 的三段式其实写了一半**：`CsmFindBlocker`（33-56）实现了标准的 blocker search——16 个 Poisson disk 采样、逐像素随机旋转（`CsmRand2To1` 哈希角）、平均遮挡物深度；但当前 `CsmSampleCascade` **故意走有界 PCF**（122 注释写明：blocker search 在接收/遮挡深度范围偏离时会把整个 atlas 象限判成全黑，所以 filter radius 收敛到 1~4 texel，由 bias 负责消除 acne）；
- 偏移是三重组合：法线偏移（`normal_offset = world_texel*2`）+ 斜率比例 bias（`world_texel·1.5·(1+(1-NdotL)·8)`，110-113）；
- 无效深度保护（76：深度 ≤1e-5 或 ≥0.99999 视为未写，不算遮挡）。

### 1.7 ACES 色调映射

`tone_mapping_pass.frag:11-19` 是 **Narkowicz/Karis 拟合式 ACES**（不是完整 RRT/ODT）：

```glsl
(color * (2.51*color + 0.03)) / (color * (2.43*color + 0.59) + 0.14)
```

一个有理分式拟合 filmic 曲线，三次乘加完成，最后 clamp 到 [0,1]。整个管线是 HDR（RGBA32F 的 cubemap 和 LUT 都按线性浮点算）→ 光照累加完 → ACES → LDR。

### 1.8 算法链总结

**一句话总结算法链**：高光走 Cook-Torrance 三件套（GGX 分布 + Smith-Schlick 几何 + Schlick 菲涅尔），漫反射走能量守恒 Lambert（`kD=(1-F)(1-metallic)`）；环境光拆两张表——漫反射用 9 阶 SH（CPU 投影 + 余弦卷积常数），高光用 GGX 重要性采样预滤波 mip 链 × BRDF LUT 的 (scale,bias)；法线贴图用 Mikkelsen 屏幕空间导数法；阴影是 4 级 CSM atlas + 旋转 Poisson PCF（PCSS blocker search 已实现但默认关闭）；最后 Narkowicz ACES 拟合出图。

## 二、多线程渲染架构

### 2.1 游戏线程 / 渲染线程分离

- 游戏线程每帧 `RenderSystem::submitFrame()` 打包 `RenderFramePacket`（FrameCommand 快照 + 资源/场景命令），move 进 `SpscQueue<RenderFramePacket, 4>`，唤醒渲染线程（render_system.cpp:121-174）；
- `RenderThread` 是纯帧泵：`loop()` 里 CV 等待 → 执行 `renderFrame()` → 归还在飞计数（render_thread.cpp:59-93）。`kMaxFramesInFlight = 2`（render_thread.h:16）——游戏线程最多超前 2 帧，这是**帧预算的第一道闸门**；
- 单线程模式保留同一条 packet 数据流，只是 `executeFrameOnce()` 原地执行（render_system.cpp:169-173）——两种模式行为一致，调试方便。

### 2.2 帧内渲染任务并行录制

两层并行：

- **RenderGraph 层**：`topologicalSort` 产出的每个 level，用 `ThreadPool` 给每个 pass 发独立 `DrawCommandList` 并行录制，`WaitGroup` 等齐后按层序 append（render_graph.cpp:551-590）——这就是“帧内渲染任务并行录制”，pass 级粒度；
- **Pipeline 层**：`RenderPipeline::Create({std::thread::hardware_concurrency(), ...})`（render_system.cpp:48-52），整个渲染管线持有一个大小等于硬件线程数的线程池做视锥剔除、图元收集这类任务。

注意 OpenGL 后端会**强制退化串行**（`direct_mode`，render_graph.cpp:405）——GL 只有一个 context 不能并行录，这是设计边界而非缺陷。

### 2.3 双命令队列：任务预算与负载平衡

对应代码里的两级队列：

1. **跨线程 packet 队列**（SpscQueue，4 深 + 2 在飞）：控制游戏侧生产预算，渲染慢了游戏线程自动被压住，负载天然平衡；
2. **渲染线程内 ThreadPool 任务队列**（thread_pool.h）：承载帧内并行录制任务，任务粒度 = pass/feature，负载由任务队列自然摊到各 worker；

另外硬件层 D3D12 backend 开了 **graphics / compute / copy 三条硬件队列**（d3d12_backend.cpp:181-201），NVRHI 的 `executeCommandLists(queue)` 把不同类型工作分流——copy 上传不占图形队列，这是更细粒度的“平衡负载”。

### 2.4 Tracy 接入与瓶颈定位

- 宏层封装（instrumentor.h:216-256）：`DO_PROFILE_SCOPE_CATEGORY` → `tracy::ScopedZone`（zone 级火焰图）、`DO_PROFILE_THREAD_NAME` → `tracy::SetThreadName`（RenderThread/worker 线程命名）、`DO_PROFILE_MARK` → `TracyWriteMessage`（帧阶段标记，代码里到处都是 `DO_PROFILE_MARK("...swapchainAcquired", "frame")`）；
- **内存 profile**：全局分配器钩子里 `TracyAllocS/TracyFreeS` 带 16 层调用栈（memory.cpp:12, 122, 160）——Tracy 里能看内存分配火焰图；
- **GPU 数据**：双缓冲 GPU timer query 测帧 GPU 耗时（render_system.cpp:354-378）+ `FrameTelemetry`（game_thread_ms/render_thread_ms/draw_call_count/barrier_count，frame_telemetry.h）→ `recordTelemetry` 汇总，配合 Tracy plot 定位 CPU/GPU 瓶颈——瓶颈判断逻辑：游戏线程被 `submitFrame` 背压卡住 = GPU/CPU 渲染瓶颈；渲染线程 `tryPop` 常空转 = 游戏侧瓶颈。

## 三、跨平台 RHI 与 OpenGL 后端

### 3.1 cutie-rhi：NVRHI 衍生 fork 与引擎侧封装

`engine/external/cutie-rhi`（cutie-rhi.cmake）就是 NVRHI 改名二开的库：目录结构 `src/{d3d11,d3d12,vulkan,opengl,validation}`、`DeviceDesc.pGraphicsCommandQueue/pComputeCommandQueue/pCopyCommandQueue`（gfx_context.cpp:181-183）都是 NVRHI 的 API 形状。cmake 开关控制编译哪些后端（DX11 OFF、DX12/Vulkan/OpenGL ON）。

**引擎侧封装**：

- `GfxContext` 持有 `GfxBackend`（三选一）+ `GfxDeviceHandle`，构造时走 `initializeVulkan/OpenGL/D3D12`（gfx_context.h:96-98）；
- `DrawCommandList : CommandList<GfxCommandList>`（draw_command_list.h:25）——**录制式**命令列表，`recordCommand` 把命令记进 block allocator，渲染线程再重放到真 cmd buffer；`m_record_mutex` 保证多线程录制安全；
- 引擎永远只写 RenderGraph/DrawCommandList 层代码，后端差异全部沉到 RHI 下面。

### 3.2 统一着色器编码规范

着色器统一 GLSL（450 core），用 `DOE_SET_GLOBAL/VIEW/PASS/PRIMITIVE/MATERIAL/BINDLESS` 常量约定 set/binding（shader_parameter_sets.glsl）——正好对应 NVRHI 的 registerSpace/slot：

- Vulkan/D3D12：直接吃 SPIR-V，set/binding 原生对齐；
- OpenGL：没有描述符集概念，GL 后端在**管线创建时解析映射表** `GLBindingMapping {registerSpace, slot → location/textureUnit/imageUnit}`（opengl-backend.h:239-247），每帧 `applyGraphicsBindings` 把 UBO/SSBO 绑到 binding point、纹理绑到 texture unit；
- `supportsSpirv = false`（opengl-device.cpp:154）——GL 路径用 `Shader::compileGLSL` 直接编译源码，跨 API 靠“同一份源码 + 两种绑定落地方式”。

### 3.3 Bindless 与自动降级

- Bindless 只在 Vulkan/D3D12 可用：引擎侧 `DescriptorTable` 管理大描述符表（texture_manager.cpp:353-362 每个纹理占一个 descriptor index），shader 里 `u_Textures[1024]` 按索引取；
- GL 后端 `createBindlessLayout` 返回 **nullptr**、`DescriptorTable::getCapacity()` 返回 0（opengl-backend.h:556, 330）——能力缺失直接暴露给上层；
- 降级机制在引擎层闭环：`RenderSettings::IsBindlessActive()` 决定加载哪套 shader 变体（`gbuffer_pass.frag` vs `gbuffer_pass_nobindless.frag`，**同一渲染逻辑两份编码**），fallback 纹理/descriptor 分配失败走保守路径；
- 更细的特性探测在 `queryGLCapabilities`（opengl-device.cpp:131-154）：每个能力都是“版本号**或**扩展”双通道——`supportsMultiDrawIndirect = GL4.3 || ARB_multi_draw_indirect`，`drawIndirect` 内部按 flag 切 `glMultiDrawArraysIndirect` 或循环单 draw；上层 `RenderSettings` 探测失败直接 `forcing CpuOnly`（render_settings.cpp:141-143，GPU-driven 剔除降级）。

### 3.4 OpenGL 后端难点与考量

自研 GL 后端 = 把一个 2016 年的 immediate API 硬塞进 NVRHI 这个为 D3D12/Vulkan 设计的抽象里。逐个难点：

**1. 上下文线程亲和 —— 最先撞上的墙**

GL context 只属于创建它的线程。整个引擎的双线程架构在这崩溃。解法：

- `OpenGLBackend` 记录 `m_context_owner` + `m_context_mutex`（opengl_backend.h:20-21），提供 `acquireContext/releaseContext`；
- 引擎层把 context 当“可迁移资源”：启动时主线程创建 → `releaseOpenGLContext` → 渲染线程第一帧 `acquireOpenGLContext`（render_system.cpp:186-208）→ shutdown 时渲染线程的 shutdown task 释放、主线程重新 acquire（render_system.cpp:67）；
- `GfxRenderScope` + `IsInRenderScope()` 静态断言“当前线程是否持有 context”，防止游戏线程误触 GL 调用。

**2. 用 immediate 模拟“录制-提交”模型 —— 架构级妥协**

RHI 的模型是 open（录）→ close → executeCommandLists（提交），D3D12/Vulkan 里录制和执行分离，这是并行录制的前提。GL 没有命令缓冲。这里的实现是**记录时立即执行**：

- `setGraphicsState` 只缓存状态（`m_CurrentGraphicsState = state`，opengl-commandlist.cpp:236），真正 `draw()` 时做状态 diff 再发 GL 调用（applyGraphicsBindings/applyBlendState...）——状态差分避免冗余 GL 调用，这是 immediate API 的经典优化；
- `open/close` 只翻 bool（94-95），`executeCommandLists` **直接 return 1**（opengl-device.cpp:712）——提交是 no-op，因为执行已经发生了；
- **连锁反应**：既然录制即执行，“并行录制”就不可能——引擎检测到 GL 后端就强制 `direct_mode` 单线程录 + `RenderSettings::IsSingleThread()`。这是 GL 后端对整个渲染架构的最大约束，必须在设计期就接受。

**3. 资源状态跟踪 / 屏障语义差异**

D3D12/Vulkan 有显式资源状态 + barrier，GL 只有 `glMemoryBarrier`（针对 image/SSBO 的内存可见性，没有布局转换概念）。做法：

- **状态跟踪照常保留**：`setTextureState/beginTrackingTextureState` 全套接口都实现，RenderGraph 的 `deriveBarriers` 三个后端跑同一套逻辑；
- `commitBarriers`（opengl-commandlist.cpp:380）把 NVRHI 状态位翻译成 `glMemoryBarrier` 的 bit 组合；纹理“布局转换”类 barrier 在 GL 是 no-op（GL 纹理无布局）；
- 收益：上层 RenderGraph 代码完全后端无关，GL 上只是 barrier 变得便宜。

**4. Bindless 彻底缺失 → 双编码降级**

GL 没有描述符索引（除非 ARB_bindless_texture，兼容性差没采用）。考量是**降级路径要在架构层预留**：

- RHI 层诚实地返回 nullptr/0，不假装支持；
- 引擎层 `IsBindlessActive()` 分流 + `*_nobindless.frag` 变体（nobindless 版用 texture array 或逐 draw 绑定）；
- 代价是 shader 双份维护，收益是 GL/低端机上整条管线（包括 GPU-driven 剔除、间接绘制）仍然能跑。

**5. 绑定模型映射**

NVRHI 的 `registerSpace/slot` → GL 的三种东西（uniform location / texture unit / image unit / binding point）。`GLBindingMapping` 在**管线创建时解析一次**（链接后用 glGetUniform 之类查 location，存进 `GraphicsPipeline::bindingMap`），运行时每 draw 按 map 落绑定——把每帧的字符串查找/location 查询成本挪到创建期。

**6. 零碎但必须做的模拟**

- **Push constants**：GL 没有 → `m_PushConstantBuffer` uniform buffer 模拟（opengl-backend.h:488-490）；
- **Swapchain**：GL 没有 swapchain 对象 → `createDefaultFramebuffer` + backbuffer 作为 `ImportedBackBuffer` 资源导入 RenderGraph，引擎对它有特判（禁 Clear、必须独占，render_graph.cpp:420-423）；
- **同步原语**：`EventQuery = GLsync fence`（opengl-backend.h:354）、`TimerQuery = GL_TIME_ELAPSED`——正好把 RenderFrameScheduler 的“event query 驱动槽位退休”机制无缝适配到 GL；
- **能力探测表**：GLContext 里 12 个 bool + 各种 max 限制（maxTextureSize/maxArrayTextureLayers/maxComputeWorkGroupCount...，opengl-backend.h:43-66），每个能力“核心版本 || ARB 扩展”双通道，indirect draw、copy image、debug marker 都按 flag 走不同实现——这就是简历“硬件特性自动降级”的底层。

### 3.5 难点总结

**一句话总结**：OpenGL 后端的本质难度不在“写 GL 调用”，而在**把一个 immediate、单 context、无显式状态机的 API 塞进为 parallel-record + explicit-barrier + descriptor-indexing 设计的抽象里**——代价是并行录制不可用（架构上显式接受）、bindless 降级双编码、状态跟踪做给别人看（GL 自己便宜），收益是一套代码三后端、低端机/调试环境可跑、以及逼着上层架构把“特性降级”做成一等公民。

## 四、反射系统

引擎的反射分**两层**，而且两层用的是完全不同的技术路线——这本身就是面试时最值得讲的架构决策。

### 4.1 总设计：两条技术路线

| | C++ 侧 | C# 侧 |
|---|---|---|
| 路线 | **注解 + libclang 离线解析 + Mustache 代码生成**（编译期） | **System.Reflection**（运行时，.NET 原生能力） |
| 动机 | C++ 语言没有运行时反射，RTTI 只能给类型名拿不到成员布局 | 托管侧天生有，直接用 |
| 开销 | 运行时零解析成本，只有 lambda 间接调用 | 反射结果按类型缓存，热路径无反射 |

### 4.2 C++ 侧：四步链路

#### 第 1 步：注解层 —— 业务代码零侵入（reflection.h:13-21）

```cpp
#if defined(__REFLECTION_PARSER__)
#define META(...)   __attribute__((annotate(#__VA_ARGS__)))
#define CLASS(name, ...) class __attribute__((annotate(#__VA_ARGS__))) name
#define STRUCT(name, ...) struct __attribute__((annotate(#__VA_ARGS__))) name
#else
#define META(...)          // 正常编译展开为空
#define CLASS(name, ...) class name
#endif
```

关键技巧：**宏有两副面孔**。给 metaparser 编译时（定义了 `__REFLECTION_PARSER__`），`META(WhiteListFields, ScriptBind)` 变成 Clang 的 `__attribute__((annotate(...)))`，注解被**记进 AST**；正常编译时是空宏，二进制里什么都没有。业务代码写法：

```cpp
REFLECTION_TYPE(TransformComponent)
STRUCT(TransformComponent, WhiteListFields, ScriptBind)
{
    REFLECTION_BODY(TransformComponent)
    Vector3f position;
    ...
};
```

`REFLECTION_TYPE/REFLECTION_BODY`（reflection.h:23-32）是给生成的 Operator 类开 `friend` 的前置声明。属性标志定义在 meta_data_config.h:3-17：`WhiteListFields / WhiteListMethods / ScriptBind / Enable`——**白名单制**，不标注的类完全不被解析。

#### 第 2 步：解析器 —— 自研 DodoeParser（engine/src/metaparser）

基于 **libclang**（LLVM 官方 C API，带在仓库里 `3rd_party/LLVM`）：

- 构建 ordering：CMake 自定义 target `DodoePreCompile`，先于业务目标跑——汇总所有带注解的头文件喂给解析器；
- 内部三层抽象：`Cursor`（封装 CXCursor，遍历 AST 节点）、`CursorType`（类型信息）、语言模型（`Class/Field/Method/Enum_def`，language_types/）；
- 核心动作：`clang_visitChildren` 深度遍历，遇到 `CXCursor_AnnotateAttr` 就把注解字符串解析成属性集合，按白名单收集类的字段/方法/枚举值，组装成 `MetaInfo` 数据结构。

#### 第 3 步：代码生成 —— 一个解析器挂三个生成器

`parser.cpp` 注册三个生成器，共用同一份解析结果（**单一事实源 = C++ 头文件本身**）：

| 生成器 | 产物 | 消费方 |
|---|---|---|
| `ReflectionGenerator` | `{file}.reflection.gen.h` + 汇总的 `all_reflection.gen` | C++ 运行时反射 |
| `SerializerGenerator` | `{file}.serializer.gen.h/.ipp` | 场景序列化 |
| `ScriptBindingGenerator` | `NativeComponents.generated.cs`（C# 代理类）+ `NativeCalls.generated.cs` + `script_glue.generated.cpp` | C# 脚本系统 |

渲染用 **Mustache 模板**（template_manager + `3rd_party/mustache`，reflection_generator.cpp:139/164），把收集到的类/字段数据填进模板。`_generated` 目录是构建产物，不进版本库。

#### 第 4 步：运行时 API —— 五个静态 map + 访问器

**数据结构核心**（reflection.cpp:15-19）：

```cpp
static std::map<String, ClassFuncTuple*>     class_map;    // 类级：基类列表/JSON构造/JSON写出
static std::multimap<String, FieldFuncTuple*> field_map;   // 字段级，multimap：同名字段多条（继承）
static std::multimap<String, MethodFuncTuple*> method_map;
static std::map<String, ArrayFuncTuple*>     array_map;
static std::map<String, EnumValueList>       enum_map;     // 枚举名→值列表
```

**生成的代码长什么样**（以 TransformComponent 为例，每个字段一组 lambda）：

```cpp
// reflection.gen.h 生成内容示意
static void TypeTransformComponentOperator::Register() {
    // 类级三元组：{取基类反射实例, 从JSON构造, 写出JSON}
    REGISTER_BASE_CLASS_TO_MAP("TransformComponent", new ClassFuncTuple(
        [](ReflectionInstance*& out, void* ins) -> int { ... },
        [](const Json& j) -> void* { return new TransformComponent(j); },
        [](void* ins) -> Json { ... }));
    // 每字段一个 8 元组
    REGISTER_FIELD_TO_MAP("TransformComponent", new FieldFuncTuple(
        [](void* o, void* v) { static_cast<TransformComponent*>(o)->position = *(Vector3f*)v; },  // Set
        [](void* o) -> void* { return &static_cast<TransformComponent*>(o)->position; },          // Get
        []() { return "position"; }, []() { return "Vector3f"; }, []() { return "TransformComponent"; },
        []() { return false; },                                     // is_array
        []() { return FieldType::Vec3; },                           // 类型枚举（驱动 Inspector 控件）
        [](std::vector<std::pair<const char*, const char*>>& out) { /* 附加属性 */ }));
}
```

这正是 reflection.h:95-99 定义的：

```cpp
using FieldFuncTuple = tuple<SetFunc, GetFunc, GetNameFunc×3, GetBoolFunc, GetFieldTypeFunc, GetAttrsFunc>;
using ClassFuncTuple = tuple<GetBaseClassListFunc, ConstructorWithJson, WriteJsonByName>;
```

**为什么存 lambda 元组而不是 `offsetof` 成员指针**？三个原因：① `void*` 类型擦除后能统一塞 map，支持任意非平凡类型（含 std::string、自定义 struct）；② 天然携带元信息（字段名/类型名/FieldType 枚举/属性表），成员指针给不了；③ 反射路径不是热路径，一层 `std::function` 间接调用可接受。

**面向用户的门面**（reflection.h:112-231）：

- `TypeMeta`：按类名从 map 拉出全部字段/方法构造访问器列表（reflection.cpp:76-97，`equal_range` 遍历 multimap 天然处理继承链）；
- `FieldAccessor`：`get/set(void* instance)` 按名字读写任意字段；`getFieldType()` 返回 `FieldType` 枚举（Bool/I32/F32/String/Vec3/Color/Struct/Ptr/Array...，reflection.h:55-75）；还带**属性系统**——`hasAttribute/attributeRange/isHidden/isReadOnly`（reflection.h:166-171），这就是 `META` 里写的附加参数；
- `ReflectionInstance`：`TypeMeta + void*` 的反射实例对；
- `ReflectionPtr<T>`：带类型名字符串的智能指针（reflection.h:232-330）——**多态容器序列化的钥匙**：容器里只存 `ReflectionPtr`，序列化时靠 `getTypeName()` 找回具体类型，`newFromNameAndJson` 动态构造。

### 4.3 消费方：Inspector、序列化、脚本绑定、动态构造

1. **编辑器 Inspector**：遍历 `TypeMeta::get_field_list`，按 `FieldType` 自动选控件（float→拖条、Color→取色器、Enum→下拉），`attributeRange(min,max)` 定拖条范围，`isHidden/isReadOnly` 控制编辑性；
2. **场景序列化**：`ConstructorWithJson`（从 JSON 按字段名构造）+ `WriteJsonByName`（按字段名写出）+ `ReflectionPtr` 类型名，支持嵌套结构和多态指针的完整往返（serializer.cpp）；
3. **脚本绑定**：标 `ScriptBind` 的类交给 `ScriptBindingGenerator`，三方生成（C# 代理/C# 调用封装/C++ glue）——改一个 C++ 组件头文件，反射、序列化、脚本绑定全部自动再生；
4. **编辑器动态构造**：`newFromNameAndJson("SpriteRendererComponent", json)` 按字符串类型名创建组件——C++ 做到“按名字 new 对象”。

### 4.4 C# 侧：直接用 System.Reflection

托管侧不需要任何生成，.NET 原生反射够用（scriptcore 里的用法）：

- **类型扫描**：`ScanAssemblyTypes` 反射遍历 AppDomain + App ALC 的程序集，找 `CakeComponent/CakeSystem` 子类建类型表（ScriptHub.Types.cs）——对应 C++ 侧“类注册”的概念；
- **字段访问**：`GetFields(Public|Instance)` + `GetField/SetValue`，两个出口：编辑器动态读写（`GetField/SetField` 命令，ScriptHub.Fields.cs:10-113）和热重载快照恢复（ScriptHub.Snapshot.cs）；
- **特性驱动调度**：`[Reads]/[Writes]` 特性反射读取**一次后按类型缓存**（CakeSystemAccessCache.Resolve），依赖图构建不做重复反射；
- **序列化**：`System.Text.Json` + `IncludeFields`，字段快照直接序列化。

**两侧反射如何对接**：C++ 侧编译期生成的字段表保证“哪些字段存在、什么类型”是唯一真相；C# 侧运行时反射读托管对象自己的字段——两边**不需要互相知道对方的反射系统**，通过 UUID/句柄 + 值拷贝交互。

### 4.5 高频对比问题（面试向）

- **为什么不用 RTTI？** `typeid` 只有类型名，拿不到成员列表/布局；且需要开 `/GR` 且对模板不友好。
- **为什么不用宏注册（每字段手写一行）？** 每加字段要手写注册、易漏易错；libclang 方案的头文件本身就是注册表，重构改名自动跟随。
- **对比 Unity？** Unity 的 C++ 反射同样是代码生成路线（他们的 binding 生成器），C# 侧也是运行时反射——这个引擎的分层和 Unity 本质相同，区别在于 Unity 是黑盒私有工具链，这里是白盒自研（libclang + Mustache），并且和 C# 脚本绑定共享同一份解析输出。
- **代价？** 构建流程多一步（DodoePreCompile target）；生成代码编译时间；`std::function` 元组的内存开销（每字段 8 个 lambda）；但运行时收益是 Inspector/序列化/绑定零手工。

### 4.6 一句话总结

**一句话总结**：C++ 侧 = “注解宏双面孔（parser 编译时变 Clang annotate、正常编译为空）→ libclang 离线吃 AST → Mustache 生成 lambda 元组表 → 静态 map 注册 → TypeMeta/FieldAccessor 门面”的编译期反射；C# 侧直接用 System.Reflection + 特性缓存；两层通过 ScriptBindingGenerator 的三方生成代码桥接，头文件是唯一事实源。

## 五、资源管线

资源管线的全链路（`runtime/resource/` 全目录 + 渲染侧 `render_command_queue/realizeTexture` 的衔接）。这个系统本质是**三层身份 + 两条管线**：资产层（编辑器）→ Object 层（运行时）→ GPU 层（渲染线程）。

### 5.1 总览

```text
源文件(.png/.fbx/.json)                    编辑器/磁盘侧
   │ ImporterRegistry 按扩展名分发导入器
   ▼
AssetDatabase (.meta 元数据库: UUID/mtime/签名/依赖)
   │ registerAsset / discoverAssets / refreshAssets
   ▼
AssetManager (m_assets: UUID→Asset, 加载状态机)
   │ loadAssetSync / loadAssetAsync(TaskScheduler)
   ▼
ResourceManager::loadObject<T>              运行时侧
   │ findLoaded → ObjectID→InstanceID 查活对象; 未加载则物化
   ▼
运行时 Object (Texture2D/Mesh/Material... InstanceID+generation)
   │ ResourceCommand / SceneCommand
   ▼ (SPSC packet 队列, 跨线程)
RenderSystem 渲染线程: realizeTexture → GPU handle + slot/描述符 → 上传
```

### 5.2 身份系统：三层 ID（整个管线的主线）

| ID | 内容 | 用途 | 位置 |
|---|---|---|---|
| `FileID` | 路径 intern 成 `uint32`（file_id.h:12-27） | 轻量路径引用、序列化里的相对路径 | 资产引用字段 |
| `ObjectID` | `{UUID asset_id, uint32 local_id}` | 资产的稳定标识；**local_id 支持子资产**（一张纹理切出多个 Sprite） | AssetHandle / AssetMetaData.ref |
| `InstanceID` | 运行时对象句柄**+ generation 代数** | 活对象查找、过期检测（`isAlive(id, gen)`） | Object 层 |

- `AssetHandle<T>` 是**弱句柄**：只包一个 ObjectID，`get()` 时现查 AssetManager（resource_manager.h:174-187）——不持有对象生命周期，可以随便存进组件里，和 Unity 的 GUID 引用同思路；
- 子资产解析走 `resolveSubObjectRef(file_id, local_id)`，普通资产走 `resolvePathToRef`（asset_manager.h:77-78）——比如 Sprite 从纹理资产里按 local_id 切出来。

### 5.3 导入管线（编辑器侧，Unity 风格 .meta）

**导入器注册表**（asset_importer.h:35-47）：`ImporterRegistry` 按扩展名注册导入器（texture/sprite/model/audio/tiled_map），每个导入器实现：

```cpp
Json getDefaultSettings();                      // 默认导入设置
Scope<Asset> import(const ImportContext&);      // 执行导入
Bool isDirty(const ImportContext&);             // 是否需要重导
```

**脏检测是三重指纹**（asset.h:41-54 的 `AssetMetaData`）：

- `source_file_mtime / asset_file_mtime / meta_file_mtime` 三个时间戳；
- `import_signature = hash(导入设置 JSON)`（`ComputeImportSignature`）——**改导入设置（如 ppu、翻转）就自动触发重导**，不用改源文件；
- 加上 `dependencies: DynamicArray<ObjectID>`——依赖图存在元数据里，`getDependents/getDependencies`（asset_manager.h:160-161）支持“改了这张纹理，哪些资产要重导/哪些 Sprite 失效”。model_importer 导入时还会递归 `ensureImported` 依赖文件（model_importer.cpp:59）。

**扫描与刷新**：`discoverAssets()` 递归扫资产目录 → `importSourceFile` 按扩展名挑导入器 → 注册 UUID；`refreshAssets(progress_callback)` 支持**进度回调 + 取消令牌**（`m_refresh_cancelled`，asset_manager.h:43）——编辑器里能边扫边显示进度、随时取消。元数据持久化在 `AssetDatabase`（ObjectID→meta + 路径索引，dirty 才落盘，asset_database.h:12-38）。

### 5.4 运行时加载：状态机 + 同步/异步双通道

每个 Asset 带加载状态机（asset.h:33-39）：`Unloaded → Loading → Loaded / Failed / Reloading`。

- **同步**：`loadAssetSync<T>`（asset_manager.h:99-118）——状态检查（Loading 中直接返回 null 防重入）→ `loadFromSource(绝对路径)` → 置 Loaded。子类各自实现解析（TextureAsset 解析出 `TextureBlob` 像素、SceneAsset 走 JSON）；
- **异步**：`loadAssetAsync` = `TaskScheduler::Self().async(...)` 包一层返回 `std::future<T*>`（121-125）——引擎全局任务调度器，不阻塞调用线程；
- **批量**：`loadAssets()` 启动时全量加载 / `loadAssetsAsync()` 后台加载；
- **JSON 文本资产**：`loadAssetFile<T>`（166-189）读文件 → `nlohmann::json::parse` → **`Serializer::read`**——这里直接消费了模块四的 C++ 反射系统：资产文件能按字段名反序列化回任意反射类型，加字段自动兼容（旧文件缺新字段就保持默认值）。

### 5.5 Object 物化：资产 → 运行时对象（以纹理为例）

`ResourceManager::loadObject<T>`（resource_manager.h:100-131）是类型分发的编译期 switch：

1. **先查活对象**：`findLoaded` 把 ObjectID → `Object::FindInstanceID` → `FindObjectFromInstanceID`，还要校验对象类型名（87-97）——已加载直接返回，**这就是运行时对象的“缓存”层**（InstanceID 注册表，带 generation 防悬空）；
2. **未加载则物化**（loadTexture2D，resource_manager.cpp:84-118）：
   - 从 AssetManager 查资产源路径 → `TextureBlob` 解码像素（stb）；
   - `new Texture2D(ObjectID{asset_id, local_id})` ——运行时对象**继承资产的 ObjectID**，资产和对象因此能互查；
   - **关键一步**：不直接碰 GPU！组装 `ResourceCommand{CreateTexture, texture对象, 像素数据}` → `GetRenderSystem()->enqueueResourceCommand(cmd)`（114-116）。

### 5.6 与渲染线程的衔接（呼应模块二的双线程架构）

`render_command_queue.cpp:17-35` 是统一入口，**按模式分流**：

```cpp
if (RenderSettings::IsSingleThread())
    rs->realizeResourceCommand(cmd);            // 单线程：立即执行
else
    rs->enqueueResourceCommand(std::move(cmd)); // 多线程：进录制包
```

多线程模式下命令随帧 packet 走 SPSC 队列，渲染线程 pop 后：

- `realizeResourceCommand`（render_system.cpp:419-437）→ `TextureManager::realizeTexture`（texture_manager.cpp:304-371）：创建 GPU 纹理（HDR→RGBA32F，LDR→RGBA8）→ 上传像素 → **分配 slot + bindless 描述符索引**（`m_slot_lut` + `m_descriptor_table->createDescriptor`）；
- buffer 类资源同理走 `RenderResourceQueue::CreateBuffer`（render_command_queue.cpp:38-51），数据随命令拷贝过去；
- 启动期资源（BRDF LUT、fallback 纹理）走 `submitStartupUploads` 专用通道。

**GPU 资源生命周期归渲染侧管理**：游戏线程持有的 `Texture2D` 只是 CPU 侧壳，GPU handle 由渲染线程填回（`texture->setGpuHandle`），删除走 DeferredDeletionQueue 按帧号延迟销毁——和帧调度正确性那套是同一机制。

### 5.7 场景引用链（把上面串起来）

场景 JSON 里的组件字段存 `FileID` 相对路径 → 反序列化时按需 `resolvePathToRef` → `loadObject<T>` 物化 → 渲染命令入队。例子：`native_tilemap_add_tileset` 里 `ResourceManager::getAssetManager()->resolvePathToRef(FileID(source))` → `Tileset::Create(ref, source)`（script_glue.cpp:776-783）——C# 脚本传来的路径字符串也走同一条链。

### 5.8 设计特点与诚实边界

**特点**：

1. **GUID 句柄化**（UUID + local_id 子资产）——引用稳定、路径改名不破引用（路径只是索引）；
2. **导入器可扩展** + 设置签名驱动的增量重导；
3. **资产/对象/进程三层生命周期分离**：AssetManager 管资产、InstanceID 注册表管运行时对象、渲染线程管 GPU 资源，各自独立加载/卸载；
4. 反射序列化直接复用，资产格式全 JSON 文本。

**诚实边界**（被追问时）：

- 纹理像素**拷贝两跳**（blob → ResourceCommand.resource_data → 上传），没有 staging 环形缓冲/常驻映射，大纹理会有内存峰值；
- 没有资产打包（pak/bundle），Shipping 也是散文件 + JSON；
- `loadAssetSync` 在 Loading 状态直接返回 null 而不是等待——没有“等异步加载完成”的同步点，调用方要自己轮询；
- 异步粒度是整个资产文件，没有分块/流式加载。

### 5.9 一句话总结

**一句话总结**：路径 → FileID → UUID ObjectID（+local 子资产）→ Asset（状态机，JSON+反射序列化，导入器签名增量重导）→ Object（InstanceID+generation 注册表缓存物化）→ ResourceCommand 跨线程 → 渲染线程 realizeTexture 上传 GPU 并分配 bindless slot——一条“编辑器导入、运行时懒加载、GPU 延迟物化”的三段式管线，每一段的跨线程正确性都复用了模块二的双线程架构。

## 六、线程间数据正确性

游戏线程 ↔ 渲染线程的数据正确性怎么保证——核心模型是**“拷贝快照 + 命令流 + 单向所有权转移”**，两个线程之间**不共享任何可变状态**。

### 6.1 帧数据打包：值快照，不是引用

游戏线程每帧结束时 `RenderSystem::submitFrame()`（render_system.cpp:121-174）组装一个 `RenderFramePacket`：

- `FrameCommand`：窗口尺寸、frame_time/delta、每个视点的 **view/proj 矩阵按值拷贝**（141-150）——提交后游戏侧随便改相机，渲染线程用的是本帧快照；
- `ResourceCommand[]` / `SceneCommand[]`：本帧积累的资源/场景命令。

### 6.2 命令录制与“换缓冲”

游戏帧过程中，世界侧产生的命令通过 `enqueueResourceCommand / enqueueSceneCommand` 进 `m_recording_packet`，用 `m_record_mutex` 保护（render_system.cpp:97-105）；submitFrame 时在锁内把两个 vector **move 进新 packet**、清空录制缓冲（160-166）——锁只在这两条短路径出现，临界区极小。

### 6.3 单生产者单消费者队列

packet 推进 `SpscQueue<RenderFramePacket, 4>`（render_system.h:76）：

- SPSC 保证**严格 FIFO** + 无锁 fast path：push 用 `release` 写 tail，pop 用 `acquire` 读 head（spsc_queue.h:55, 73），release/acquire 配对保证 packet 内容对消费方可见；
- 队列满时 push 阻塞（CV + 100µs 轮询，43-52），**背压**防止游戏线程无限超前导致 packet 堆积内存爆炸。

### 6.4 双重帧数上限

- 队列容量 4；
- `RenderThread::submitFrame()` 还有一层 `kMaxFramesInFlight = 2` 的信号量（render_thread.h:16, render_thread.cpp:44）：在飞帧数 ≥2 时**游戏线程睡眠等待**——渲染落后最多 2 帧，延迟有上界。

### 6.5 所有权单向转移：渲染侧镜像场景

渲染线程 pop 出 packet 后独占它，然后（render_system.cpp:260-292）：

- `realizeResourceCommand`：创建 GPU 纹理/缓冲——**只有渲染线程碰 GPU 对象**；
- `applySceneCommand`：把 Add/Remove/Update Primitive/Light/Sprite 命令应用到 `RenderScene`——这是游戏世界的**渲染镜像**，只归渲染线程写，所以 apply 过程**零锁**；
- 游戏世界（EnTT World）渲染线程永远不碰，游戏线程也永远不碰 RenderScene——正确性靠**所有权隔离**而不是互斥。

一个细节：游戏线程调用的 `GDrawCommandList` 是延迟录制列表，渲染线程开头 `detachRecordedCommands()` 取出并重放到真命令列表（273-283）——游戏侧“看起来”在录 GPU 命令，实际录制数据也走同一所有权转移。

### 6.6 渲染线程空转兜底

队列空时 `tryPop` 失败就复用 `m_last_frame_command` 上一帧的 FrameCommand 重绘（216-221）——游戏帧率 < 渲染帧率时渲染线程不清空、不阻塞、不读脏数据。

### 6.7 GPU 侧正确性（防止“CPU 已翻页 GPU 还在用”）

`RenderFrameScheduler`（render_frame_scheduler.h:23）维护 **3 个 frame slot**：每槽独立的 staging 分配器、transient 资源池、命令列表、`completion_query`（event query）；每帧 `beginFrame` 轮转槽位，`retireCompletedFrames` 用 event query 确认 GPU 跑完才复用槽；资源删除进 `DeferredDeletionQueue`，按帧号延迟销毁（render_system.cpp:302 `processDeferredDeletions(frame_ctx.frame_number)`）。双缓冲 GPU timer query 同理（358-377）。

### 6.8 特殊平台的线程亲和

OpenGL 上下文是线程绑定的：多线程模式下主线程 `releaseOpenGLContext`、渲染线程 `acquireOpenGLContext`（186-194, 198-208），shutdown 时主线程重新 acquire（67）；GL 后端还强制单线程渲染 + RenderGraph 走 `direct_mode` 串行录命令（render_graph.cpp:405）。

窗口 resize 只在渲染线程做：`waitForIdle → retire → recreateSwapchain → pipeline->onResize`（247-258），避免多线程重建 swapchain 的竞态。

### 6.9 总结

**线程正确性** = 值快照（矩阵/时间）+ 命令流 move 进 SPSC 队列（release/acquire 保序可见）+ 渲染镜像场景所有权独占 + 4 深 queue × 2 在飞帧双重背压 + GPU 侧 3 slot 帧调度 + event query 确认后延迟删除。

## 七、RenderGraph 剔除算法

剔除在 `RenderGraph::compile()`（render_graph.cpp:371-392），五步：`buildDependencyGraph → validateAccesses → cullUnreachablePasses → deriveBarriers → topologicalSort`。剔除的核心是**从“有副作用的汇点”反向可达性传播**（Frostbite FrameGraph 那套 pass culling）。

### 7.1 先建依赖 DAG（buildDependencyGraph，289-330）

按 pass 声明顺序扫描，每个资源维护 `writer_passes / reader_passes`：

- **Read**：从该资源最后一个 writer 连边 `writer → 本pass`（RAW），登记自己为 reader（310-315）；
- **Write/ReadWrite**：从最后一个 writer 连边（WAW），**再从所有 pending readers 逐个连边**（WAR hazard），然后清空 readers、把自己登记为新 writer（318-327）；
- 没有任何 access 且无 `NeverCull` 标志的 pass **直接预剔除**（296-299）。

### 7.2 反向可达性剔除（cullUnreachablePasses，199-278）

**种子（汇点）**：`is_exported` 的资源 + 后备缓冲（backbuffer）标记为可达入队（205-210）——这些是“渲染结果真正被外部消费”的地方，即副作用。

**工作列表迭代到不动点**（222-242）：

- 弹出一个可达资源 → 它的**所有 writer pass 和所有 reader pass** 标记可达；
- 每个新可达 pass 调 `propagatePassResources`（212-220）：它碰过的**所有资源**也变可达、入队——直到没有新东西。

这一步等价于 **liveness 反向传播**：从输出往回找“谁对最终图像有贡献”。任何资源只要最终被消费，它的生产链（writer）和消费链（reader）全存活。

**再沿 DAG 边正向补传播**（244-268）：从可达 pass 出发顺着 7.1 建的边把下游 pass 也标记可达，并顺带把它们的读资源标记可达——覆盖纯依赖边连上的 pass。

**落刀**（270-277）：带 `NeverCull` 标志的 pass 豁免（比如 present、拾取这类有外部副作用的）；其余 `!reachable_passes[i]` 全部 `m_culled_passes[i] = true`。

### 7.3 配套的正确性校验（validateAccesses，115-158）

- “有 reader 没 writer” → 未初始化读，assert；
- “有 writer 没 reader 且未 export” → 写了没人读（白做），报错——这正是剔除算法的理论兜底：如果这种 pass 活下来说明 seed 漏了；
- **UAV 冲突**：两个 pass 对同一资源都是 ReadWrite → assert（Vulkan 里无屏障并发写未定义）。

### 7.4 剔除后：屏障推导 + Kahn 分层

- `deriveBarriers`（160-197）：跳过被剔除 pass，按序跟踪每资源状态机（`accessToRequiredState` 把 Read/Write/ReadWrite × Stage 映射成 ShaderResource/RenderTarget/DepthWrite/UAV/Copy…），状态变化就给该 pass 挂 pre-barrier——**被剔除的 pass 不产生任何屏障**；
- `topologicalSort`（332-369）：Kahn 分层出 `m_levels`，环检测 assert（详见模块八）；
- 执行（394-592）：**同层并行**——ThreadPool 给每个 pass 发独立 `DrawCommandList` + `WaitGroup`，层间按序 append 合并（551-590）；GL direct 模式退化串行（527-549）。被剔除的 pass 既不执行也不占层。

### 7.5 总结

**RenderGraph 剔除** = 从 exported 资源/backbuffer 这些副作用汇点做**资源↔pass 双向不动点反向可达传播**，没被染到的 pass 整体裁掉（NeverCull 豁免），剔除结果同时决定屏障推导与并行分层的执行集。

## 八、Kahn 分层拓扑排序

`RenderGraph::topologicalSort`（render_graph.cpp:332-369）值得单独讲透，因为它不是教科书的“排一条线性序列”，而是 **Kahn 分层变体**——输出的是“并行层”，这直接决定了渲染的并行执行结构。

### 8.1 它解决什么问题

编译 RenderGraph 后手里有一张 DAG：节点 = pass，边 = 资源依赖（模块七 `buildDependencyGraph` 产出的 RAW/WAR/WAW 边）。执行必须满足：**任何 pass 开跑前，它依赖的所有 pass 都已完成**。拓扑排序就是把 DAG 变成合法执行顺序。

普通拓扑排序给的是一条线性序列，但这里浪费信息——两个互不依赖的 pass（比如 ShadowPass 和 GBufferPass）排成先后纯属人为串行。所以这里用 **Kahn 算法的分层版本**：算出每个节点的“依赖深度”，**深度相同的放一层，层内天然无依赖、可并行**，层与层之间严格串行。这和 C# 侧 CakeTaskGraph 的调度是同一个算法思想。

### 8.2 算法逐步拆解

**输入**：

- `edges[i]`：pass i 的所有后继（模块七 buildDependencyGraph 建的边表）；
- `indegree[i]`：pass i 的**前驱数量**——每条 `from→to` 边让 `indegree[to]+1`（AddEdge，render_graph.cpp:16-22）。语义：indegree = 有多少个资源写者/读者冲突对象排在我前面。

**第 1 步：找起点（入度 = 0 的 pass）**

```cpp
for (i = 0; i < pass_count; i++)
    if (indegree_work[i] == 0) current_level.push_back(i);
```

入度 0 = **不读任何“之前被写过”的资源，也不和任何 pending reader 冲突**——通常是 ShadowPass、GBufferPass 这种纯生产者。它们构成第 0 层。

**第 2 步：逐层剥洋葱**

```cpp
while (processed < pass_count) {
    DO_ASSERT(!current_level.empty(), "RenderGraph has cyclic dependency");  // 环检测
    next_level{}, execution_level{};
    for (node : current_level) {
        if (!m_culled_passes[node])        // 被剔除的 pass 不进执行层
            execution_level.push_back(node);
        for (to : edges[node]) {
            indegree_work[to] -= 1;        // 前驱完成一个
            if (indegree_work[to] == 0)    // 前驱清零 → 毕业进下一层
                next_level.push_back(to);
        }
    }
    if (!execution_level.empty()) m_levels.push_back(execution_level);
    processed += current_level.size();
    current_level = std::move(next_level);
}
```

核心不变量：**一个节点的入度减到 0，当且仅当它的全部前驱都已进入之前的层**——这时它才被放进 `next_level`。每轮循环剥掉一层“当前无依赖”的节点，像剥洋葱一样层层深入。

两个关键细节：

1. **被剔除的 pass 仍然参与入度传播**：`if (!m_culled_passes[node])` 只挡 `execution_level`，下面的 `indegree_work[to] -= 1` **照常执行**——被剔除的 pass 作为“直通节点”把依赖关系继续传递给下游，否则下游节点的入度永远减不到 0，整张图卡死。这是剔除和排序能共存的关键一行；
2. **环检测**：如果 `processed < pass_count` 但 `current_level` 空了，说明剩下的节点互相等待（环），assert 炸掉——对 RenderGraph 来说环 = 资源读写形成循环等待，必须在上游建图时修。

**第 3 步：产物**

`m_levels: [[第0层...], [第1层...], ...]`。注意 `if (!execution_level.empty())`——某一层全是被剔除的 pass 时**不产生空层**，执行时直接跳过。

### 8.3 走一个具体例子

```text
P1 ShadowPass   : 写 ShadowMap
P2 GBufferPass  : 写 GBuffer
P3 DeferredLight: 读 ShadowMap, 写 GBuffer→读, 写 HDR      ← 边: P1→P3, P2→P3
P4 SkyboxPass   : 写 HDR（和 P3 WAW 冲突）                 ← 边: P3→P4
P5 PostProcess  : 读 HDR, 写 LDR                          ← 边: P4→P5
P6 Present      : 写 BackBuffer(exported)                 ← 边: P5→P6
```

初始入度：P1=0, P2=0, P3=2, P4=1, P5=1, P6=1。

| 轮次 | current_level | 处理 | 执行层 |
|---|---|---|---|
| 0 | {P1, P2} | P3 入度 2→0；其他不变 | **[P1, P2] 并行** |
| 1 | {P3} | P4 入度 1→0 | [P3] |
| 2 | {P4} | P5 入度 1→0 | [P4] |
| 3 | {P5} | P6 入度 1→0 | [P5] |
| 4 | {P6} | 无后继 | [P6] |

假设 ShadowPass 被剔除了（比如场景没有投影灯光，`is_exported` 不成立也没被 backbuffer 链到达）：P3 的入度在 P1 被剥掉时照样减到 0（**边照 Relax**），只是 P1 不出现在第 0 层执行集合里——P3 照常毕业。

### 8.4 产物怎么被消费

`execute()`（render_graph.cpp:519-592）按层迭代：

- **层内并行**：ThreadPool 给每个 pass 分配独立 `DrawCommandList`，`pool.enqueue` 全部扔出去，`WaitGroup` 等齐（551-586）——因为同层无依赖，GPU 录制可以乱序并发；
- **层间串行**：`wg.wait()` 之后按层顺序 `out_commands.append(...)`（588-590）——命令列表的 append 顺序保证了下游 pass 录制的命令在上游之后提交，GPU 端看到的顺序满足拓扑约束；
- GL 后端 `direct_mode` 退化为逐 pass 串行（527-549）。

### 8.5 复杂度和对比

- **复杂度**：O(V + E) 时间（每个节点进队一次、每条边 Relax 一次），O(V + E) 空间（边表 + 工作副本）；
- **vs DFS 拓扑排序**：DFS 版给线性序，且天然序是“逆后序”，要再反转；Kahn 分层直接给并行结构，还顺带免费送环检测（DFS 版要另做颜色标记）；
- **语义**：每个节点的层号 = 从源点到它的最长路径长度（critical path 深度），即**最早可能开始时间**——这是 GPU 帧构建里最想要的调度性质：任何 pass 一旦依赖就绪立刻可录。

### 8.6 一句话总结

**一句话总结**：这就是 Kahn 算法的分层形态——入度数组 + 逐层剥离，入度清零即毕业进下一层；被剔除的 pass 照样传递入度但不进执行层；产物不是一条序列而是 `[[并行层]]`，直接映射成 RenderGraph 执行时“层内 ThreadPool 并行录命令、层间有序合并”的调度结构。
